### 三.1 CreditApi 幂等模型说明（2026-05-22 修订，按 P3 §5）

**❌ 旧伪代码（v1，曾出现在本文档与 docs/P4/05）—— 不要再用：**
```java
// freezeId 句柄模型（与数据库实际不一致）
String freezeId = creditApi.freeze(userId, points, bizId);  // 返回句柄
creditApi.settle(freezeId, payeeId);                         // 用句柄结算
```

**✅ 真实契约（v2，与 P3 §5 + schema `credit_record.biz_id UK` 对齐）：**
```java
// bizKey 幂等模型 —— 调用方自己构造 bizKey，重放同 key 不会重复扣
creditApi.freeze(userId, points, "task:" + taskId + ":freeze");
creditApi.unfreeze(userId, points, "task:" + taskId + ":unfreeze");
creditApi.settle(userId, points, "task:" + taskId + ":settle");
creditApi.deduct(userId, delta, ReasonCode.BAD_REVIEW, "review:" + reviewId);
```

**bizKey 命名约定（schema.sql line 169 注释样例）：**
- 任务相关：`task:<taskId>:freeze` / `task:<taskId>:unfreeze` / `task:<taskId>:settle`
- 交易相关：`trade:<orderId>:freeze` / `trade:<orderId>:settle`
- 申诉/扣分：`review:<reviewId>:deduct` / `appeal:<caseId>:refund`

> ⚠️ **关键陷阱**：`uk_credit_record_biz` 是数据库唯一索引。
> 同一笔业务的 freeze / unfreeze / settle **必须用不同后缀**（如 `:freeze` / `:unfreeze` / `:settle`），
> **不能复用同一个 bizKey**，否则第二次调用会因 UK 冲突写不进流水。

**术语对照（同一个值在不同层的叫法 — 不是 bug，注意识别）：**
| 层 | 名字 | 来源 |
|---|---|---|
| Java API 方法参数 | `bizKey` | P3 §5 line 136 / 类图 line 497-503 |
| 数据库列 | `biz_id` | schema.sql line 169 |
| 前端 VO 字段 | `bizId` | frontend/src/types/credit.ts |

三个名字**指同一个字符串**（"task:123:settle" 之类）。Repository 把方法参数 `bizKey` 写入 DB 列 `biz_id`；查询返回时 VO 字段名映射成 `bizId`。

**为什么是 bizKey 不是 freezeId：**
1. 数据库里没有"freeze 句柄表"，只有 `credit_record` 流水表 + `biz_id` 唯一索引 → 句柄无处存
2. 重放安全：网络重试导致同一笔 freeze 调用 2 次，第 2 次因 `biz_id` UK 冲突被吞掉，不会重复扣
3. 跨模块清晰：bizKey 是业务方语义构造的，credit 模块不需要懂 task / trade 的内部结构

| `TaskCompletedEvent` | taskId, version | 解冻悬赏 + 转移给接单方 | publisherId, accepterId, rewardPoint |
| `TaskCanceledEvent` | taskId, version | 解冻悬赏 + 押金 | publisherId, accepterId, rewardPoint, depositPoint |
| `TaskExpiredEvent` | taskId, version | 进入仲裁队列 | （够用，不动） |
| `BadReviewSettledEvent` | reviewId, outcome | 申诉成功→回滚扣分 | userId, deductedDelta |

**listener 不能反查 TaskRepository**（违反 INV-01），TaskApi 也只暴露 `getTaskStatus / getPublisherId` 两个方法。
→ **结论：必须扩事件字段**。

**A 建议的扩展（供 B / D 在 W10 末敲定时参考）：**
```java
public record TaskAcceptedEvent  (Long taskId, Long publisherId, Long accepterId,
                                  Integer depositPoint, long version) {}
public record TaskCompletedEvent (Long taskId, Long publisherId, Long accepterId,
                                  Integer rewardPoint, long version) {}
public record TaskCanceledEvent  (Long taskId, Long publisherId, Long accepterId,
                                  Integer rewardPoint, Integer depositPoint, long version) {}
public record BadReviewSettledEvent(Long reviewId, Long userId, Integer deductedDelta,
                                    String outcome) {}
```

3. 群内 @全员同步最终字段
4. A 同步更新 docs/P4/05 §八 listener 示例代码
