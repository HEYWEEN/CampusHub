## 2. AI 助力分析（Q1）

### 2.1 本阶段 AI 最大的贡献

1. **"一组任务批量出"代替"一个接口一来一回"，效率翻倍。**
   - 典型例子：AUTH-02 一次性产出 `/api/auth/token` + `/api/auth/register` + `/api/auth/token/password` 三个接口。三个接口共用 `AuthService` 编排、共用 `AuthUser` entity、共用 `TokenPairVO` 返回结构。如果按看板原拆分一次只做一个，AI 要重复读 P3 / OpenAPI 三遍，工时多 30%。
   - 这一发现影响后续节奏：USER-01~04 也是一个 Service 编排 4 个端点 + 共用 `UserMeVO`，半小时收工。

2. **"先写测试断言，再写实现"的反向引导让 AI 不容易跑偏。**
   - 例：AUTH-02 单测里先写 `assertFalse(stored.getPhoneHmac().contains(phone))` —— 这条断言把"DB 不能含明文手机号"翻译成代码后，AI 在实现 `AuthService.loginOrRegisterByCode` 时**主动**用 `aes.encrypt(phone)` 而不是直接存 phone。
   - 反过来 USER-01 我先写实现再补测试，AI 第一版 `updateProfile` 漏掉了"同值不写审计"的优化，加测试后才补上。

3. **AI 作为"枯燥但易错"代码的批量供给者。**
   - 大量样板代码：DTO 的 getter/setter、VO 的字段映射、JPA `@Column` 注解、Repository 方法签名 —— 这些代码人工写**正确率反而比 AI 低**（容易漏 nullable / 写错 length）。
   - 数据印证：USER 模块 4 个 DTO + 2 个 VO + 2 个 Repository 共 ~200 行，由 AI 一次出，0 修订就编译通过。

4. **设计取舍的"显式化"：AI 给的方案我先 challenge 再确认。**
   - 例：`SecurityConfig` 是否引入 `spring-boot-starter-security`？AI 第一版会引入，但用户挑战"CSRF / default 401 会和我们的拦截器打架吗？"后，AI 切换到"占位 + 注释说明启用条件"的方案。
   - 这种**"AI 给方案 → 用户压力测试 → AI 修正"** 循环比"AI 直出"质量更高。

### 2.2 不同 Prompt 策略下 AI 回答质量（延续 P2/P3 框架，新增 P4 观察）

| 策略 | 对应使用场景 | 模型 | 输出质量观察 |
|---|---|---|---|
| **A：零上下文要 AI 实现** | 没用过 —— P4 已不再用 |  | （P3 之后弃用） |
| **B：详细约束注入** | INF / AUTH / USER 全部代码 | Claude Opus 4.7 | **基准策略**。投喂 P3 详细设计 + OpenAPI + schema.sql 后 AI 出码可用率 90%+ |
| **C：reviewer 角色** | DOC-06 代码审查指南 | Claude Opus 4.7 | AI 自审能识别"`@Column(unique)` + `@Index(unique)` 双声明可能生成两条约束"这种**只有审查模式才会想到的**细节 |

> **关键观察（P4 阶段新发现）：** "**测试断言 → 实现**"的顺序在 AI 协作中**比人工编程更重要**。人工写代码时记得住"DB 不能存明文手机号"；但 AI 写代码时除非测试断言直接拍在脸上，否则会"忘记"。这是因为 AI 没有项目级长期记忆，它的"约束"全靠 prompt 注入；测试断言是最强的注入方式，因为它是**可执行的约束**。

## 3. AI 误导分析（Q2）

### 3.1 P4 阶段新增的 AI 误导问题

#### 问题 1：AI 跨工具版本生成 lock 时无环境感知（最严重）

- **如何发现**：INF push 后 frontend CI `npm ci` 红，错误是 `@emnapi/core@1.10.0` 缺失。我让 AI 修，AI 在本地 node 25 / npm 11 跑 `npm install` → 推送 → CI 仍红，这次缺 `1.10.0`，本地 lock 是 `1.9.1`。
- **根因**：CI 用 node 20 / npm 10.8.2；本地 npm 11.6.2。npm 10 / 11 对 transitive `optional` 依赖（emnapi 链）解析不一致。
- **AI 的失误**：第一次修复方案**完全没读 `.github/workflows/main.yml`**，只看了 error log 就拍脑袋"跑 npm install 重生 lock"。
- **修复**：docker `node:20` 镜像里跑 install → 拿到 CI 期望的 lock；同时加 `frontend/.nvmrc=20` 锁定版本。
- **可迁移启示**：**AI 默认认为"工具版本不影响输出"**。任何涉及版本敏感工具（npm/pip/maven 都是）的修复，prompt 必须显式说"先读 CI 配置确定运行版本"。本阶段已加入 §4.2 改进措施 #1。
- **数据**：3 个 commit 才修好（其中 1 个是错的），等价于 1 个工时的浪费 + main 分支红 ~30 min（团队其他人能看到）。

#### 问题 2：AI 实现枚举↔TINYINT 映射时默认用 ordinal

- **如何发现**：写 `AuthUser.verifyStatus` 时让 AI 出 entity，AI 第一版用 `@Enumerated(EnumType.ORDINAL)`。P3 决策记录 D3-01 已明确"`@Enumerated(ORDINAL)` 是禁区"（理由：enum 顺序变化静默错位）。
- **AI 的失误**：AI 没自动读 P3 决策记录，默认走"Java JPA 最常见写法"。
- **修复**：要求 AI 用 `@Convert(converter = VerifyStatusConverter.class)`，并新增显式 `code` 字段的 enum。
- **可迁移启示**：**AI 不读"决策记录"类文档**，它读得最多的是"代码 / 接口 / DTO"。决策记录中那些"为什么这么选"的反 default 决定必须每次都重新注入 prompt，不能假设 AI 记得。

#### 问题 3：AI 默认实现"账号枚举攻击友好"的错误码

- **如何发现**：AUTH-02 让 AI 写 `loginByPassword`，AI 第一版分了三种 401：用户不存在 / 密码错误 / 未设密码。这正好把"该手机号是否注册过"暴露给攻击者（攻击者可以枚举手机号 → 看哪些返回"用户不存在"）。
- **AI 的失误**：AI 给的错误消息是"为用户友好"的（"用户不存在" vs "密码错误"），但反而是安全风险。
- **修复（部分）**：合并"用户不存在"和"密码错误"为同一 `CREDENTIALS_INVALID` "手机号或密码错误"。但**保留** `PASSWORD_NOT_SET` 单独错误码（取舍：希望用户能看到"请用验证码登录补设密码"的引导），这是一个**有意识的安全 vs UX 权衡**，已写入审查指南 §5。
- **可迁移启示**：**AI 默认按 UX 优化错误消息**，安全方向需要人工额外干预。在 prompt 里加一条"避免账号枚举攻击：错误消息合并模糊化"作为默认。

#### 问题 4：AI 在 `@Transactional` 边界判断上不稳定

- **如何发现**：AUTH-02 `loginByPassword` 第一版没标 `@Transactional`，但因为内部要写"登录失败次数 +1"的逻辑（后续 AUTH-04 要加），不标事务会有问题。
- **AI 的失误**：AI 只看当前方法是不是"读还是写"，没考虑**未来扩展**会不会变成写。
- **修复**：所有 service 方法显式标注（readOnly=true 的明确标，写方法不带 readOnly）。
- **可迁移启示**：**AI 对"事务边界"的判断比对"代码结构"的判断弱**，因为这是个跨方法 / 跨时间维度的属性，AI 缺乏全局视角。这一类决策（事务边界、锁粒度、缓存失效）必须人工 review。

#### 问题 5：AI 处理"内存数据结构无上限"的风险盲区

- **如何发现**：DOC-06 审查指南阶段，让 AI 自审 `SmsRateLimiter`，AI 才发现"100 万用户 × 20 时间戳 × 24 字节 ≈ 480MB"的内存上限风险。
- **AI 的失误**：编码阶段 AI 实现 `ConcurrentHashMap<key, Deque<Long>>` 时**没考虑过 key 的增长无上限**。它默认数据集小。
- **修复**：当前阶段记入"已知技术债"（审查指南 §5），W14 之前评估 LRU 或 Redis 替换。
- **可迁移启示**：**AI 的代码生成模式默认"演示场景"**，缺乏"百万级用户压测视角"。所有用内存集合做缓存 / 限流 / 黑名单的代码都要在 review 时问一句"key 上限是多少？"。

### 3.2 系统性观察：P2 §3.2 / P3 §3.2 的"AI 四类偏弱"在 P4 编码阶段的延伸

| 类别 | P3 表现 | P4 编码阶段的具体形式 |
|---|---|---|
| **跨阶段一致性** | API 漏掉 P1 鉴权要求 | **lock 跨 npm 版本不一致**（本阶段最严重） |
| **不变量级约束** | 数据库默认建跨模块 FK | **`@Enumerated(ORDINAL)` 默认**（决策记录类强约束被忽略） |
| **批判性思考 / 反方论据** | 类图默认贴合需求做加法 | **错误消息默认 UX 优化**（账号枚举攻击友好） |
| **风险与边界** | API 漏限流 / 漏分页 | **内存数据结构无上限 / 事务边界不考虑未来扩展** |

**结论：四类偏弱完整保留，但表现形式从"设计层"下沉到"代码层"。**

### 4.2 P4 新增改进措施

#### 措施 1：版本敏感工具修复必须先读 CI 配置 🆕

**适用场景：** 修 `package-lock.json` / `pom.xml` / `requirements.txt` / `Cargo.lock` 等。

**Prompt 模板：**
```
当前任务：修复 [工具] 版本不一致问题。
**强制步骤**：
1. 先读 .github/workflows/*.yml，确定 CI 使用的 [工具] 版本
2. 检查本地版本（[工具] --version）
3. 如本地与 CI 不一致，必须用 docker 镜像 / nvm / pyenv 切换到 CI 版本后再操作
4. 操作完成后必须在 CI 同版本下复现 CI 命令验证
```

**已验证：** 本阶段第二次 CI 修复完全按此流程，一次成功。

#### 措施 2：每个 Entity 写 prompt 时强制喂"决策记录" 🆕

**适用场景：** JPA @Entity / DTO / @Column 注解。

**Prompt 模板：**
```
写 [实体名] 时，禁止：
- @Enumerated(EnumType.ORDINAL)         （决策 D3-01，必须用 @Convert）
- 任何跨前缀模块 @ManyToOne（INV-02）
- 在 entity 字段上加 BCrypt / 加密逻辑（应在 service）
- 明文 phone / realName / studentNo / idCard 字段名出现在任何 entity
必须：
- @Version 字段（所有可被并发更新的实体）
- @Column(nullable, length) 显式声明
- 注释里写明 "对应 schema.sql 表 xxx"
```

**计划：** 沉淀到 `docs/P4/AI-prompt/entity_template.md`，下次写 entity 时直接复用。

#### 措施 3：所有"内存 Map/List 缓存"代码必须包含上限注释 🆕

**适用场景：** ConcurrentHashMap 限流 / 黑名单 / 缓存 / pending 任务集合。

**Prompt 模板：**
```
写 [Map/List] 缓存时，注释必须写明：
- key 的潜在上限（用户数 / 任务数 / token 数）
- 单条 value 的字节估算
- 总占用上限（< 1MB / 1MB-100MB / > 100MB → 必须配置 LRU 或外部存储）
- 多实例部署的升级路径（Redis / 共享缓存）
```

**已验证：** USER-B 的 `DefaultSensitiveWordChecker` 一次过审；如果给 `SmsRateLimiter` 也这么搞，本阶段就不会留下技术债。

#### 措施 4：测试断言优先于实现代码 🆕

**适用场景：** 任何涉及隐私 / 业务不变量的 service。

**Prompt 模板：**
```
写 [功能] 之前，先列出 5 条测试断言：
1. 业务不变量断言（例：DB 不含明文 phone）
2. 边界断言（例：限流第 N 次触发）
3. 错误码断言（例：返回 401 / code=1002）
4. 状态机断言（例：A→B 合法、A→C 抛错）
5. 幂等/并发断言（例：重复消费同一 sms_code 拒绝）

写完断言后再写实现。实现不能让任何一条断言失败。
```

**已验证：** AUTH-01 + AUTH-02 + USER-01~04 都用此模式，零回炉。

## 5. 本阶段的核心工程判断

### 5.1 决策内容（4 项 A 模块代码层决策）

#### 决策 1：不引 spring-boot-starter-security，仅用 spring-security-crypto

- **背景：** SecurityConfig 是否要真启用 Spring Security？AI 默认引入 starter。
- **判断：** 不引入。理由：CSRF / formLogin / basicAuth 默认配置会和我们的纯 JWT 拦截器打架；只要 BCrypt，独立 `spring-security-crypto` 包就够。
- **代价：** SecurityConfig 退化为占位类（含详细注释说明启用条件）。
- **何时反悔：** 未来上 OAuth2 Resource Server 时再启用。

#### 决策 2：AUTH-02 一次做完 3 个 token 类接口，超出看板范围

- **背景：** P4 看板只列 `/api/auth/token`，但 OpenAPI 有 3 个 token 类接口。
- **判断：** 一次做完。理由：3 接口共用 `AuthService` / `AuthUser`，分次做实际工时 1.5x；FE-02 也需要 3 接口齐才能闭环。
- **代价：** 看板需要追加补充任务 ID 描述（待 W11 站会同步）。
- **决策权：** 由我（A）拍板，理由是"看板范围少于 OpenAPI 范围是 P4 看板的漏洞，不是设计漏洞"。

#### 决策 3：保留 `PASSWORD_NOT_SET` 单独错误码（违反"账号枚举攻击"模糊化原则）

- **背景：** 安全最佳实践：登录失败应统一返回"手机号或密码错误"，避免攻击者枚举手机号。
- **判断：** **故意违反**这条原则。理由：未设密用户极少，统一错误码会让真实用户陷入"我没设过密码但你跟我说密码错了"的死循环，UX 代价大于安全收益。
- **代价：** 攻击者可以通过 `PASSWORD_NOT_SET` 区分"已注册未设密用户"和"未注册用户"。
- **缓解：** 在审查指南 §5 标"安全讨论"项；如团队不接受，可在 P5 改回。

#### 决策 4：内存限流 / 黑名单不立即升级 Redis

- **背景：** `SmsRateLimiter` 在 100 万用户场景下内存可能爆。
- **判断：** P4 阶段不动。理由：本期是学校大作业，演示场景 < 100 用户；引入 Redis 增加部署复杂度反而拖累 W11~W14 主线。
- **代价：** 记入"已知技术债"（审查指南 §5）。
- **何时升级：** 真正部署生产 / 演示评审需要 100+ 用户压测 / 多实例时。

### 5.2 为什么 AI 无法做这些决策

| 决策 | AI 缺什么 |
|---|---|
| 1（不引 starter） | 缺**对历史 INF-03 决策的全局记忆** + 不知道"我们的拦截器是纯 JWT" |
| 2（超看板范围） | 缺**对项目分工 / 工时账本的判断**，AI 看到任务就按字面做 |
| 3（保留 PASSWORD_NOT_SET） | 缺**对本项目用户类型 / 真实使用频率的判断**（学校项目 vs 生产 SaaS 完全不同） |
| 4（不升 Redis） | 缺**对项目阶段 / 演示需求 / 部署复杂度成本的整体权衡** |

**共同特征：所有 4 个决策都涉及"超出当前任务上下文的整体权衡"。** AI 在单次 prompt 内能做最优局部决策，但跨任务 / 跨阶段 / 跨业务的权衡需要人工。

### 5.3 这一类决策的共同特征（跨 P1/P2/P3/P4 累计）

| 阶段 | 典型决策 | 共同特征 |
|---|---|---|
| P1 | scope 减项（树洞 / SSO 排除） | 业务取舍 |
| P2 | INV-01 跨模块直依赖禁令 | 架构约束 |
| P3 | D3-01 / D3-02 推翻既有规约 | 反 AI 默认的"维护既有"倾向 |
| **P4** | **决策 1-4（如本节）** | **代码级权衡 + 演示场景 vs 生产场景** |

**贯穿四阶段的核心特征：所有"AI 做不了"的决策都需要 "整个项目的非代码上下文"** —— 用户类型、部署目标、团队工时、未来路线、历史决策。AI 只能看到"当前 prompt 喂的内容"，所以**项目越成熟、决策越需要人工**。

### 5.4 团队启示（在 P3 启示基础上追加）

1. **review 不是可选的。** 即使 AI 出码 90% 可用，剩下 10% 中有 30% 是"看起来对但其实有隐性 bug"（账号枚举、ordinal 映射、无上限内存）。这 3% 的隐性 bug 必须靠人审。
2. **PR 描述里写 `[AI-assisted]` + Prompt 摘要不是形式主义。** 互审者看 PR 时能根据 prompt 倒推"AI 这次能做对吗"，缩短审查时间。
3. **测试断言是 AI 协作的最有效"约束注入"。** 比 prompt 里写"必须满足 X"更可靠 —— 因为代码必须真的通过测试才能 commit。
4. **决策记录类文档（ADR / 审查指南 / 反思日志）必须每次任务都重新提示 AI**。AI 不会自动 grep `docs/` 目录。
5. **工具版本一致性是 AI 协作的隐性陷阱**。从这阶段起，所有项目骨架都应包含 `.nvmrc` / `.java-version` / `requirements.lock`。

#### 6.3.2 D 阶段 AI 误导分析（4 条,与 §3.1 互补)

**问题 1：AI 看到"数量提示"会自动配凑素材**(最严重)
- **如何发现**：CRD-03 实现 ScoreRule 时,看板 §1.5 写"5 加分 + 4 扣分",但 SRS FR-CRED-01 实际只有 1 加分 + 4 扣分。AI 直接按看板字面输出,**凭空编出 4 个不存在的 reasonCode**(首次发布奖 / 七日活跃...)看起来全部合理但 SRS 没写。
- **根因**:AI 的"配凑数字"倾向 —— 给了目标数它会生造素材;同时 AI 不会自动建立"SRS > 看板"的文档优先级。
- **修复**:严格按 SRS 实现 5 条规则;enum Javadoc 显式标注"看板 5+4 不准,以 SRS 1+4 为权威"。
- **可迁移启示**:涉及"列出 N 条规则"的 prompt 必须写"如果文档实际只有 M < N 条,按 M 实现并显式 flag 数字差异,禁止编造补全"。已记入 `docs/P4/bug/陈泽昊_2026-05-23.md` Bug #2。

**问题 2：AI Explore subagent 会幻觉补充"该有的表/字段"**
- **如何发现**：第一个 Explore subagent 在汇报"credit 相关表清单"时,**报告 schema 含 `credit_score_log` 和 `credit_appeal`**。我亲手 grep schema.sql,只数到 10 张表,这两张都没有。
- **根因**:AI 看到"该有"就当成"有",且没附 grep 证据。这是与问题 1 同源的"训练数据偏置"。
- **修复**:① schema.sql 补 credit_score_log DDL(实际验收依据);② subagent prompt 加"只列实际 grep 命中的,禁止补全,必须附 grep 命令和输出"。
- **可迁移启示**:对 Explore subagent 必须强制要求"附执行命令证据",否则它会 hallucinate 出整张表。

**问题 3：AI 在"看起来权威的文档"和"真正权威的文档"之间无法自动建立优先级**
- **如何发现**：第一个 subagent 读了 A 的 `05_后端开发约定.md`(团队约定文档,看起来权威),抄了里面的 freezeId 句柄式伪代码,告诉我 CreditApi 应该走 freezeId 模型。但真正的契约源是 P3 §5 第 136 行 + schema.sql 的 `uk_credit_record_biz` —— 这两份说的是 bizKey 模型。
- **根因**:AI 读了第一个看起来权威的文档就停止比对;不会主动用 DB schema 做仲裁。
- **修复**:亲手回查 P3 §5 + schema unique key 证伪 freezeId 模型;同时与 A 同步确认(A 的 commit `192bd77` 已修)。
- **可迁移启示**:任何跨模块 API 契约出现两份不一致时,**立刻用 DB schema 做仲裁**(unique key 不会撒谎),而不是去找"哪份文档更权威"。这是比 §3.1 问题 2(@Enumerated ORDINAL)更深一层的"AI 不读决策记录"现象 —— AI 不仅不读决策记录,**连主动比对都不会做**,会停在第一个匹配的文档上。Bug 日志 Bug #1。

**问题 4：AI 写跨账户业务时倾向直译契约,忽略语义缺失**
- **如何发现**:settle 在 P3 §5 的签名是 `settle(userId, points, bizKey)` —— 只有一个 userId。AI 直接按字面实现"对 userId 加积分"。但 task 完成结算实际是**双账户转账**(发布者 frozen 释放 + 接单者 balance 入账),单 userId 表达不了"我是谁"。
- **根因**:AI 默认"契约签名是正确的",不会主动质疑"语义是否完整"。
- **修复**:折中实现 —— settle 单边语义("收款方入账"),付款方 frozen 释放在 CRD-04 listener 里分两次调 API(`unfreeze` + `settle`),Javadoc 写明。
- **可迁移启示**:遇到 AI 直译的契约,人工必须问一句"双方/多方语义都覆盖了吗?"。这条与 §3.1 问题 4(`@Transactional` 边界)同类 —— AI 缺乏"跨方法/跨业务流"的全局视角。Bug 日志 Bug #4。

#### 6.3.3 D 阶段 AI 协作意外亮点

1. **反向引导("从前端 types/credit.ts 反推 VO")极其高效**。F-CREDIT-01 / 08 接口实现时,我把前端 TypeScript 的 `CreditMeVO` interface 喂给 AI,让 AI 按字段反推 Java VO 字段名 + 类型。结果一次过审,**字段名、类型、可选性、命名风格完全对齐**前端,省去了"前后端接口字段对账"的反复修订。这条比"AI 看 OpenAPI 出 VO"还高效,因为 TS interface 比 OpenAPI 描述更紧凑、AI 推理负担更小。
2. **`@Autowired List<JpaRepository<?,?>>` 自动收集思路是 AI 反过来教我的**。我本来想在 BaseIT 里手写"已知的所有 Repository 类型"列表,AI 提议用 `List<JpaRepository<?,?>>` 让 Spring 自动收集 —— 这样**未来 B/C 加新 Repository 时 BaseIT 不用改**。这是 AI 在"框架使用范式"上比我熟练的一个具体案例。
3. **`@TransactionalEventListener(phase=BEFORE_COMMIT)` 的事务时机判断 AI 一次说对**。我担心 BEFORE_COMMIT vs AFTER_COMMIT 选错(选 AFTER_COMMIT 会导致 listener 抛错时主事务已 commit 无法回滚),AI 自动选了 BEFORE_COMMIT 并给出"事件失败应该让发布事件的事务一起回滚"的理由。事务边界这一类是 §3.1 问题 4 标记的 AI 弱项,但**在有显式选项的场景下 AI 反而表现稳定** —— 这说明 AI 弱在"主动识别需要 @Transactional",不弱在"已知 @Transactional 选哪个传播级别"。
