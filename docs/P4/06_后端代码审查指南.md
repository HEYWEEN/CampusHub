## 2. 🟠 P1 应读 —— 业务核心 service

> 这一层有真正的业务逻辑，AI 协作最容易在此犯隐性 bug。

### 2.1 `auth/service/AuthService.java` (~210 行)

**审查重点：**

#### 事务边界
- [ ] `loginOrRegisterByCode` `@Transactional`（写）：sms 消费 + user 建账 + profile 建立 在一个事务里
- [ ] `loginByPassword` `@Transactional(readOnly=true)`：只读，正确
- [ ] `refresh` `@Transactional(readOnly=true)`：但内部调 `blacklist.revoke()` —— 黑名单是内存 Map，**不属于数据库事务**，readOnly=true 不会拦
- [ ] `logout` 没标 `@Transactional`：纯内存操作 ✓

#### 账号枚举攻击防护
- [ ] `loginByPassword` 用户不存在 → 401 `CREDENTIALS_INVALID` "手机号或密码错误"
- [ ] 密码错误 → 同样 401 同样消息
- [ ] **但是** 未设密 → 401 `PASSWORD_NOT_SET` "请先用验证码登录后补设" —— ⚠️ **暴露了"该手机号已注册但未设密"** 的信息
      → 是否应该合并到 `CREDENTIALS_INVALID`？取舍：用户体验 vs 安全。当前选择体验。可作为审查讨论点。

#### refresh-rotation
- [ ] 旧 refresh 在发新 pair **之前** 入黑（line 109 vs 111）—— 顺序正确
- [ ] 但 issueTokens 失败时旧 refresh 已入黑 —— 实际不会失败（纯 JWT 生成），可接受

#### 验证码消费时机
- [ ] `loginOrRegisterByCode` 和 `register` 都先 `smsVerifier.verifyAndConsume`，立即标 consumed
      → 防止 token 接口和 register 接口共用同一验证码（一码一用）

### 2.2 `auth/service/SmsRateLimiter.java` (89 行)

**审查重点：**

- [ ] **`synchronized(deque)` 粒度**：不同 key 持有不同 Deque 实例 → 不会互相阻塞 ✓
- [ ] 滑动窗口：先 cutoff24h 清理过期再判断 24h 上限，再用 stream 滤 60s 段 —— 流式 size 计数 O(n) 但 n ≤ 200 上限，可接受
- [ ] **内存增长上限**：phoneTrack 按 hmac 存，每个 hmac 一个 deque，每 deque 最大 20 条
      → 极端情况 100 万用户 × 20 时间戳 × 24 字节 ≈ 480MB，**不可接受**
      → 需要后续优化：LRU 上限 或 Redis 替换
      → ⚠️ 已知技术债，应记入 bug 日志或新 issue
- [ ] check 顺序 phone 先于 IP —— 测试也覆盖了优先级

### 2.3 `auth/service/TokenBlacklist.java` (61 行)

**审查重点：**

- [ ] `revoke()` 入黑前查 `expireAt.isAfter(Instant.now())` —— 过期 token 不入黑（无意义）✓
- [ ] `isRevoked()` 在过期时 lazy 清理 + 返回 false —— 但 `purgeExpired()` 已经定时清，lazy 是双保险
- [ ] **`@Scheduled(fixedDelay = 10 * 60 * 1000)` 10 分钟一次**：够频繁吗？
      → 取决于 token TTL，access 120min / refresh 14 天，10 分钟周期内最多堆 ~1 万条，可接受
- [ ] 多实例部署：内存黑名单**不跨实例同步** —— 注释里明确指出了升级到 Redis 的路径

### 2.4 `auth/service/VerificationService.java` (~125 行)

**审查重点：**

- [ ] **PENDING 中重复提交 409**：`existsByUserIdAndStatus(userId, PENDING)` —— 是否有竞态？
      → 没有 SELECT...FOR UPDATE，并发两次提交都看到 false 然后双双插入 —— ⚠️ **理论有竞态**
      → 缓解：客户端节流 + 极端情况下管理端可手动 reject 后一条
      → 真正修复：加唯一约束 `(user_id, status=PENDING)` 部分索引 —— MySQL 不支持，需迁移到 PostgreSQL 或加 trigger
- [ ] AES 加密的字段：realName / studentNo / idCard（可空）—— 完整
- [ ] 测试已断言 DB 不含明文（line 119-121 of VerificationTest）✓
- [ ] auth_user.verify_status 同步推进到 PENDING —— 单事务里 ✓

### 2.5 `auth/entity/AuthUser.java` (~100 行)

**审查重点：**

- [ ] `@Version private Integer version` 用 Integer 不是 int —— 允许 null（首次插入 JPA 处理 null）✓
- [ ] `@Column(unique = true)` 在 `phone_hmac` 上 + `@Index(unique = true)` 重复了？
      → JPA 双声明可能在某些数据库下生成两条约束。可清理为一种
      → ⚠️ 小型优化项
- [ ] `VerifyStatusConverter` 不用 `autoApply` —— 显式 `@Convert` 反而更明确 ✓
- [ ] `hasPassword()` 用 `passwordHash != null && !isEmpty()` —— BCrypt 空字符串理论上能 hash 出有效值，但本类的语义只看是否 set 过，可接受
