## Bug #1：前端 CI 红 —— `package-lock.json` 与 `package.json` 不同步 + 二次修复时跨 npm 版本生成 lock 再次失败

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-22 16:23（CI 第 1 次失败）→ 16:33（修复后 CI 第 2 次仍失败）→ 16:48（真正修复并通过） |
| **发现人** | 何翌闻（在推送后端 INF-01~04 后被 GitHub Actions 暴露） |
| **所属模块** | CI/CD / 前端 |
| **关联任务 ID** | 间接阻塞 QA-04（CI/CD 绿灯） |
| **严重等级** | 🔴 阻塞（任何 push 都红，全员看到 main 是 broken 状态） |
| **是否 AI 协作触发** | 否（历史遗留 lock 不同步）+ 是（AI 在第一次修复时未考虑 npm 跨版本差异，导致二次失败） |

### 🐛 问题现象

#### 阶段 A：CI 首次失败
推送后端 INF-01~04 commit（`cb30d3a`）后，GitHub Actions `frontend-check` job 失败：

```
npm error code EUSAGE
npm error `npm ci` can only install packages when your package.json and package-lock.json
            or npm-shrinkwrap.json are in sync.
npm error Missing: @emnapi/core@1.10.0 from lock file
npm error Missing: @emnapi/runtime@1.10.0 from lock file
npm error Invalid: lock file's @emnapi/wasi-threads@1.2.0 does not satisfy @emnapi/wasi-threads@1.2.1
```

`@emnapi/*` 是 `vite 8 → @rolldown/binding-wasm32-wasi → @napi-rs/wasm-runtime` 链上的 transitive optional dep（wasm 运行时 fallback）。

#### 阶段 B：第一次修复后 CI 仍然失败
我在本地（node 25 / npm 11.6.2）跑 `npm install` 重生 lock，本地 `npm ci` + `npm run build` 都通过，提交（`8944208`）并推送。

CI 仍然报**完全相同的错**，但版本号变了：
- CI 期望 `@emnapi/core@1.10.0`，我 lock 里写的是 `1.9.1`

**预期行为：** `frontend-check` 的 `npm ci` 步骤成功（lock 与 package.json 同步）
**实际行为：** 同样的 EUSAGE 错误连出两次，第二次只是版本号从 `1.9.1` 变成 `1.10.0`

### 🔍 根因分析

**两层根因：**

#### 直接原因（阶段 A）
前端 `package-lock.json` 中 `@emnapi/wasi-threads` 仍是 1.2.0，且未声明嵌套在 `@rolldown/binding-wasm32-wasi` 下的 `@emnapi/core` / `runtime` —— 但 `package.json` 里 vite 8 的版本范围解析时已经需要新版。
应该是之前某次 `npm install` 改了 package.json 直接依赖后，**没把全量 lock 一起提交**，或在不同环境下 partial 提交。

#### 间接原因（阶段 B —— 真正的"AI 协作教训"）
我（AI）在阶段 A 的修复方案是"本地 `npm install` 重生 lock"，**忽略了一个事实**：

| | 本地 | CI |
|---|---|---|
| node | **25**.2.1 | 20 |
| npm | **11**.6.2 | 10.8.2 |

> ⚠️ **常见误解**：npm 大版本之间向后兼容，lock 文件格式跨版本通用 → 错。
>
> npm 10 和 npm 11 对 **optional / transitive deps**（特别是 wasm / napi 链上的）解析逻辑有差异：
> - npm 11 解析 `@emnapi/core` ≈ "尽量复用根级版本" → 1.9.1
> - npm 10 解析 `@emnapi/core` ≈ "每个 nested context 独立解析最新" → 1.10.0
>
> 因此**任何 lock 文件必须用 CI 同款 node/npm 版本生成才稳定**。

#### 是否之前已知
- ✗ 项目根 / frontend 都**没有 `.nvmrc`**，没人锁定过 node 版本
- ✗ 我作为 AI 在第一次修复时没有主动检查"我的 npm 版本 vs CI 的 npm 版本是否一致"

### 🔧 修复方案

#### 阶段 A 修复（最终被阶段 B 推翻）
```bash
cd frontend && npm install  # node 25 + npm 11 生成的 lock —— 在 CI 上仍不被接受
```
关联 commit：`8944208`（**事后看是错误修复**，仅作为反例保留）

#### 阶段 B 真正修复（用 docker 跑 node 20 镜像）
```bash
cd frontend
rm -rf node_modules package-lock.json
docker run --rm -v "$(pwd)":/work -w /work node:20 sh -c '
  npm install --no-audit --no-fund &&
  rm -rf node_modules &&
  npm ci --no-audit --no-fund &&  # 模拟 CI 验证
  npm run build                    # 模拟 CI build 步骤
'
```

并新增 `frontend/.nvmrc`：
```
20
```

关联 commit：`56139e7`

### ✅ 验证结果

- [x] 容器内 `npm ci` 成功（206 packages installed）
- [x] 容器内 `npm run build` 成功（dist 446 KB / gzip 138 KB）
- [x] CI 通过（GitHub Actions `frontend-check` ✓）
- [x] `@emnapi/core` 和 `runtime` 在 lock 中均为 1.10.0（CI 期望版本）
- [x] `.nvmrc` 提交，下次任何人 `nvm use` 会自动切到 node 20

### 🧠 经验教训

1. **跨 npm 版本生成 lock 是隐性陷阱**。npm 10 / 11 / 8 / 9 之间对 transitive optional dep 的解析不一致。任何 lock 修复必须在与 CI **完全一致的 node + npm 版本**下进行。
2. **修 CI 前先看 CI 的 node 版本**。`.github/workflows/main.yml` 里 `node-version: '20'` 是首要信息，比 error log 优先级更高。
3. **`.nvmrc` 应该是项目骨架的必备文件**，跟 `.gitignore` / `package.json` 同等优先级。本次给 frontend 补上。
4. **AI 协作教训**：第一次修复时 AI（我）没主动查 CI 配置，只看了 error log 就给方案，导致 fix → red → re-fix 的浪费。应该把"修 CI 时先 read `.github/workflows/`"作为强制流程。
5. **docker 是无 nvm 时跑特定 node 版本的兜底方案**：`docker run --rm -v $(pwd):/work -w /work node:20 sh -c '...'`，无副作用。

## Bug #2：filter-branch 报 "You need to run this command from the toplevel of the working tree"

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-22 16:18 |
| **发现人** | 何翌闻 |
| **所属模块** | git 工具链 / 本地仓库维护 |
| **关联任务 ID** | （非任务，是历史改写需求） |
| **严重等级** | 🟢 低（提示性，1 行 cwd 修正即可） |
| **是否 AI 协作触发** | 是（AI 在 `backend/` cwd 下直接跑了 filter-branch） |

### 🐛 问题现象

清理本地未推送 commit 中的 `Co-Authored-By` trailer 时，我执行：

```bash
git filter-branch -f --msg-filter 'python3 /tmp/strip_coauthor.py' 94a5744^..HEAD
```

git 立即返回错误：

```
WARNING: git-filter-branch has a glut of gotchas generating mangled history rewrites.
Proceeding with filter-branch...
You need to run this command from the toplevel of the working tree.
```

filter-branch 没有实际执行。

**复现步骤：**
1. 当前 cwd 在 `backend/`
2. 执行 `git filter-branch ...`
3. → 错误，filter-branch 拒绝在非 repo root 下运行

**预期行为：** filter-branch 重写指定范围的 commit message
**实际行为：** 拒绝执行，留下 "from the toplevel" 提示

### 🔍 根因分析

- 直接原因：`git filter-branch` 设计上**强制要求在 repo root 执行**（不像 `git log` / `git commit` 等命令能在 worktree 任何子目录跑）
- 间接原因：我此前一直在 `backend/` 目录下跑 mvn 测试，惯性地继续在那里跑 git 命令，没切回 repo root

### 🔧 修复方案

```bash
cd /Users/heyween/Desktop/软工二大作业/CampusHub && \
  git filter-branch -f --msg-filter 'python3 /tmp/strip_coauthor.py' 94a5744^..HEAD
```

关联 commit：（无 commit，仅本地历史改写）

### ✅ 验证结果

- [x] filter-branch 成功重写 6 个 commit
- [x] `git log` 显示 3 个目标 commit 的 trailer 已清除
- [x] 后续 `git push origin main` fast-forward 成功

### 🧠 经验教训

- `git filter-branch` / `git filter-repo` / `git submodule` 等"全仓级"操作必须在 repo root 跑。脚本化时显式 `cd "$(git rev-parse --show-toplevel)"` 是好习惯。
- 这个错误信息本身写得很清楚，被 filter-branch 警告 banner 淹没了，我应该认真读 stderr。
