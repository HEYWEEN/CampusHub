## Bug #1：后端启动崩溃 —— MySQL 9.x JDBC 握手 `Public Key Retrieval is not allowed`，前端发验证码返回 502

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-28 19:20（`./start.sh local` 启动后立刻 BUILD FAILURE）→ 用户在前端登录页点「发送验证码」收到 502 |
| **发现人** | 何翌闻（在本机首次启动后端、准备端到端联调时） |
| **所属模块** | 配置 / 数据库 |
| **关联任务 ID** | 间接阻塞所有依赖 DB 的接口联调（auth / task / trade / edu / credit / notify） |
| **严重等级** | 🔴 阻塞（后端起不来，前端只能走 mock fallback；任何团队成员升到 MySQL 8.4+/9.x 都会复现） |
| **是否 AI 协作触发** | 否（环境层根因），但 AI 协助定位（从日志 stacktrace → JDBC 握手插件 → 参数修复）|

### 🐛 问题现象

前端登录页点「发送验证码」按钮 → 浏览器 Network 面板看到 `POST /api/auth/sms-codes` 返回 **502 Bad Gateway**。

实际链路：

```
浏览器 → vite dev (5173) → vite proxy 转 /api/* → :8080 后端
                                                 ↑
                                              没人监听，proxy 返回 502
```

后端日志 (`.run-logs/backend.log`) 关键栈：

```
org.flywaydb.core.api.exception.FlywaySqlException:
  Unable to obtain connection from database:
  Public Key Retrieval is not allowed
Caused by: com.mysql.cj.exceptions.UnableToConnectException:
  Public Key Retrieval is not allowed
    at CachingSha2PasswordPlugin.nextAuthenticationStep(...)
...
[INFO] BUILD FAILURE
[INFO] Total time: 4.195 s
```

后端在 Flyway 拿连接阶段就崩了，Spring Boot 进程退出，8080 端口不监听 → 任何前端调用全部 502。

**复现步骤：**
1. 装 MySQL 9.3（Oracle DMG 安装），用 root + 本地密码
2. `./start.sh local` 启动
3. 后端 4 秒后 BUILD FAILURE 退出
4. 前端任意调用均 502

**预期行为：** 后端正常启动 (`Started CampushubApplication in X.XXs`)，8080 监听，`/api/health` 返回 200。
**实际行为：** Hikari → Flyway 拿连接时 MySQL 握手失败，启动中止。

### 🔍 根因分析

**直接原因：**
MySQL 8.0+ 默认认证插件改为 `caching_sha2_password`。客户端首次连接时需要**从服务器获取 RSA 公钥**来加密密码传输（`scrambled-password`）。
而 MySQL Connector/J 出于安全考虑，`allowPublicKeyRetrieval` 默认 = `false`（防止 MITM 截获明文公钥），导致握手在 `CachingSha2PasswordPlugin.nextAuthenticationStep` 阶段抛出 `UnableToConnectException`。

**间接原因：**

1. `application.properties` 中的 JDBC URL 是 MySQL 5.7 时代的"够用配置"，没考虑 8.0+ 的认证插件变化
2. 团队其他成员可能用 brew 装的旧版 MySQL（保留 `mysql_native_password`），或者本机已经 cache 过公钥，所以**没复现过**
3. 启动脚本 `start.sh` 没有 health-check 步骤——它只 launch mvnw，不验证 :8080 是否真起来；前端依然显示"已启动"，把问题暴露推迟到第一次 HTTP 调用（502）

**是否之前已知：** 否，团队的 P0~P3 文档与 README 均未提及 MySQL 8+ 的握手配置要求。

### 🔧 修复方案

`backend/src/main/resources/application.properties`：

```diff
- spring.datasource.url=jdbc:mysql://localhost:3306/campushub?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8&createDatabaseIfNotExist=true
+ spring.datasource.url=jdbc:mysql://localhost:3306/campushub?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8&createDatabaseIfNotExist=true&allowPublicKeyRetrieval=true
```

**为什么改主配置而不是 `application-local.properties`：**

- MySQL 8.4+ / 9.x 是趋势，每个新开发环境都会撞这个坑
- 加这个参数对已经能连的人**无任何副作用**（参数只在 sha2 握手路径生效）
- 改一处，团队所有人受益；如果改 local，下一个装 MySQL 8+ 的成员还会再踩一次

**关于安全：** `allowPublicKeyRetrieval=true` 在生产环境理论上有 MITM 风险（攻击者可冒充 server 发恶意公钥）。但本项目：
- dev：`useSSL=false` + localhost，根本无 MITM 面
- prod：应当走 TLS（`useSSL=true&requireSSL=true`），TLS 通道下公钥传输天然加密，本参数无副作用

- [x] 修改后 `./start.sh local` 重启 → 后端成功 `Started CampushubApplication`，监听 8080
- [x] `curl http://localhost:8080/api/health` → 200
- [x] 前端登录页「发送验证码」→ 不再 502（返回业务级响应）

### 🧠 经验教训

1. **MySQL 8.0+ JDBC 连接的标准配置应当包含 `allowPublicKeyRetrieval=true`**，应写入团队的 onboarding/README。
2. **502 = 上游服务不可达**，第一反应应该查后端进程是否在监听对应端口，而不是排查业务代码。
3. **`start.sh` 应增加 health-check 步骤**：launch 后 `curl -fsS http://localhost:8080/api/health` 重试 10 次，失败明确报"后端启动失败，请看 `.run-logs/backend.log`"，避免"看起来启动了但实际崩了"的体验。这条作为后续 INF 优化项。
4. **dev infra 类配置问题应改主配置而非 local 覆盖**，避免下个成员再次踩坑——团队节省的时间远大于一行 diff 进 git。

## Bug #2：Flyway V3 迁移使用 PostgreSQL 语法 `ALTER TABLE ADD COLUMN IF NOT EXISTS`，MySQL 不支持，后端启动崩溃

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-28 19:25（修复 Bug #1 后重启，Flyway 进入 V3 时崩溃） |
| **发现人** | 何翌闻 |
| **所属模块** | 数据库 / Flyway 迁移 |
| **关联任务 ID** | TRADE-02~04（V3 是 trade 模块迭代时引入的增量 DDL） |
| **严重等级** | 🔴 阻塞（任何新部署环境都启动失败；MySQL 全版本不支持该语法） |
| **是否 AI 协作触发** | 是（AI 直出 DDL 时混用了 PostgreSQL 语法，未对齐项目实际使用的 MySQL 方言） |

### 🐛 问题现象

修复 Bug #1（`allowPublicKeyRetrieval`）后重启，MySQL 握手成功、V1/V2 执行成功，Flyway 推进到 V3 时：

```
Caused by: FlywaySqlScriptException: Script V3__trade_edu.sql failed
SQL State  : 42000
Error Code : 1064
Message    : You have an error in your SQL syntax;
             check the manual that corresponds to your MySQL server version
             for the right syntax to use near
             'IF NOT EXISTS description VARCHAR(2000) NULL COMMENT '商品描述' AFTER title,'
             at line 7
Location   : db/migration/V3__trade_edu.sql
Line       : 6
```

V3 中 7 处 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` 语句首条即报错。

**复现步骤：**
1. 全新 MySQL 实例，campushub 库不存在
2. `./mvnw spring-boot:run`，等待 Flyway baseline → V1 → V2 → V3
3. V3 第 6 行 `ALTER TABLE trade_item ADD COLUMN IF NOT EXISTS ...` 触发 ERROR 1064，BUILD FAILURE

**预期行为：** Flyway 顺序执行 V1~V5，后端 `Started CampushubApplication`。
**实际行为：** V3 因不兼容 MySQL 语法报错，后端进程退出。

### 🔍 根因分析

**直接原因：**
`ALTER TABLE ADD COLUMN IF NOT EXISTS column_name ...` 是 **PostgreSQL 9.6+ 的语法**，MySQL 自 5.x 至 9.x **全版本均不支持**。MySQL 标准 ALTER 不允许在 ADD COLUMN 后接 IF NOT EXISTS 条件，会被解析为意料外的 token，触发 1064 语法错误。

```sql
-- ❌ PostgreSQL ok / MySQL 不支持
ALTER TABLE trade_item ADD COLUMN IF NOT EXISTS description VARCHAR(2000) NULL;

-- ✅ MySQL 实现幂等的常见做法（之一）：用 stored procedure + INFORMATION_SCHEMA
SET @s = (SELECT IF(
    EXISTS(SELECT 1 FROM INFORMATION_SCHEMA.COLUMNS
           WHERE TABLE_SCHEMA = DATABASE()
             AND TABLE_NAME = 'trade_item'
             AND COLUMN_NAME = 'description'),
    'SELECT 1', 'ALTER TABLE trade_item ADD COLUMN description VARCHAR(2000)'));
PREPARE st FROM @s; EXECUTE st; DEALLOCATE PREPARE st;
```

**间接原因：**

1. **AI 协作直出问题**：AI 在写 V3 时未先看 V1（不知道 V1 已经包含所有目标列），也未确认 MySQL 不支持 `ADD COLUMN IF NOT EXISTS`，直接套用了 PG 风格的"幂等模式"
2. **V3 设计上其实就是冗余的**：核查后发现，V1__init_schema.sql 已经包含了 V3 想 ALTER / CREATE 的**全部对象**：
   - `trade_item.{description, price_point, pickup_location_type, pickup_location_detail}`
   - `trade_order.{negotiated_price_point, buyer_confirmed, seller_confirmed}`
   - 表 `edu_tutor_task / edu_forbidden_word_hit / admin_forbidden_word`
   V3 本质上是一份"以为老环境需要补齐、实际新环境完全用不到"的迁移
3. **没有 CI 校验 Flyway**：项目 CI 只跑 `mvn test`（H2 内存库），从未在真实 MySQL 上跑过完整迁移链，所以 V3 这类 MySQL-only 语法错误一直未暴露

**是否之前已知：** 否。V3 是 2026-05-23 引入，作者本地环境可能已经把列建好了所以没复现，QA 阶段也没用过 fresh MySQL。

### 🔧 修复方案

**决策：把 V3 改成 no-op（`SELECT 1`）+ 详细注释保留版本占位。**

理由：
- V1 已包含 V3 全部内容，"补齐"已无意义
- 直接删 V3 文件会破坏 Flyway 版本链（老环境 `flyway_schema_history` 已有 V3 记录，校验时找不到文件报错）
- 用 stored procedure 做真正幂等技术上可行，但 7 条 ALTER 要写 ~200 行模板代码，得不偿失

```diff
- ALTER TABLE trade_item
-     ADD COLUMN IF NOT EXISTS description VARCHAR(2000) NULL COMMENT '商品描述' AFTER title,
-     ADD COLUMN IF NOT EXISTS price_point INT NOT NULL DEFAULT 0 ...
-     ... (7 处 ALTER + 5 处 CREATE TABLE IF NOT EXISTS) ...

+ -- Flyway V3 — no-op（保留版本占位）
+ -- V1__init_schema.sql 已经包含本脚本想 ALTER / CREATE 的全部对象
+ -- 详细说明见文件头注释
+ SELECT 1;
```

### 🧠 经验教训

1. **AI 协作生成 DDL 时必须先看 V1 全量 schema**，否则会出现"以为缺、实际有"或"幂等语法用错方言"的双重错误。下次 prompt 应在生成 V*.sql 前显式喂入 V1 + 当前 MySQL 版本。
2. **MySQL 永远不支持 `ALTER TABLE ADD COLUMN IF NOT EXISTS`**，要幂等只能用 stored procedure + INFORMATION_SCHEMA，或干脆依赖 Flyway 自身的「每个 version 只跑一次」机制不写幂等代码。
3. **CI 需要补一个 fresh-MySQL 迁移检验 job**（docker-compose 起 MySQL → mvnw flyway:migrate → 失败立刻挂红），避免下次 V6/V7 又出现 MySQL 方言问题。这条作为 QA 后续优化项。
4. **拉到此修复的队友请先执行 `./mvnw flyway:repair`**，再启动后端。原因：本地 schema_history 表里 V3 的 checksum 是旧值，启动校验会失败，repair 会自动更新为新 checksum。
