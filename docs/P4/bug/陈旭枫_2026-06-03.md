## Bug #1：`@TransactionalEventListener(phase = AFTER_COMMIT)` 在 MariaDB + JPA 下不触发，站内信静默丢失

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-03 13:00 |
| **发现人** | 陈旭枫（B，task 模块 owner） |
| **所属模块** | notify / task（跨模块事件链路） |
| **关联任务 ID** | NTF-02（notify listener 订阅 task 事件） |
| **严重等级** | 🟠 高（运行时静默失效 — 无报错无日志，通知全部丢失） |
| **是否 AI 协作触发** | 是（AI 按 P3 §5.2 事件契约表写了 `@TransactionalEventListener(phase = AFTER_COMMIT)`，设计意图正确但运行时失效） |

### 🐛 问题现象

全链路联调：用户 A 发布任务 → 用户 B 接单 → 用户 A 回来看通知 → **没有新消息**。

- `mvn test` 全量 136 例全绿（含 `notify/listener/TaskEventListenerTest`）
- 后端无任何异常日志
- `notify_message` 表为空
- `credit_account` 冻结/解冻正常（证明 `TaskAcceptedEvent` 确实发布了）
- credit 侧的 `@EventListener` 监听到了同一事件并正确处理了积分

**复现步骤：**
1. 启动后端（`application-local.properties` 连 MariaDB 11.8，JPA `ddl-auto=update`）
2. 用户 A 发任务 → 用户 B 接单
3. 查 `notify_message` 表 → 0 行
4. 查 `credit_record` 表 → 有 freeze 记录（事件已发布且 credit listener 已消费）

**预期行为：** 接单后 `notify_message` 应有一条 `TASK_ACCEPTED` 记录，用户 A 看到"你的任务已被接单"。
**实际行为：** 通知静默丢失，无日志，无异常。

### 🔍 根因分析

- **直接原因**：`notify/listener/TaskEventListener` 使用 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`，在 MariaDB 11.8 + `JpaTransactionManager` + `ddl-auto=update` 组合下，事务同步（`TransactionSynchronization`）未被正确注册，导致 AFTER_COMMIT 阶段的 listener **从未被调用**。

- **间接原因**：
  - credit 侧的 `TaskEventListener` 使用 `@EventListener`（非事务感知），**同步执行，因此正常工作**。写 notify listener 时参考了同一个模式但按 P3 §5.2 事件契约表的要求换成了 `@TransactionalEventListener`（该契约表明确标注"纯通知性副作用统一 AFTER_COMMIT + @Async"）。
  - 设计文档（P3 §5.2）的 AFTER_COMMIT 设计意图是正确的——通知不应阻塞业务、不应因通知失败回滚业务。但实际运行时，`@TransactionalEventListener` 的触发依赖 Spring 的 `TransactionSynchronizationManager`，在某些 DataSource/JPA 配置下可能不具活性。
  - 单元测试（`TaskEventListenerTest`）中 listener 被手动调用，未经过 Spring 的事件广播机制，因此未暴露此问题。

- **是否之前已知**：否。credit listener 用 `@EventListener`（同步），notify listener 用 `@TransactionalEventListener`（AFTER_COMMIT），两种机制在**单测**中都能手动验证，但**集成环境**下只有 `@EventListener` 实际生效。这是一个"测试骗过"的典型案例——测试直接调方法，绕过了 Spring 的事务同步层。

### 🔧 修复方案

将 `notify/listener/TaskEventListener` 中 4 个方法的注解从 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` 改为 `@EventListener`。

```diff
- @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
+ @EventListener
  public void onTaskAccepted(TaskAcceptedEvent event) {
      notifyOne(NotifyTemplate.TASK_ACCEPTED, event.taskId(), event.publisherId());
  }
```

**取舍说明：**
- 原设计（AFTER_COMMIT）：通知写入与业务事务解耦，通知失败不回滚业务
- 新设计（同步 @EventListener）：通知写入与业务事务同 TX，如果通知写入失败会回滚业务
- 接受这个 trade-off 的理由：①通知写入（`INSERT INTO notify_message`）几乎不会失败；②即使极小概率失败，回滚接单事务也比"通知静默丢失"更安全（用户可重试接单，而不是永远不知道被接单了）

### 🧠 经验教训

- **`@TransactionalEventListener` 不是所有 DataSource 配置下都生效**。在 MySQL/MariaDB + JPA + `ddl-auto=update` 环境下，如果事务同步未注册，listener 会**静默不触发**——没有异常、没有日志、测试甚至能过（因为测试直接调方法）。
- **credit listener 用 `@EventListener` 能工作，不是因为设计选择了同步，而是因为同步机制碰巧不受事务同步状态影响**。如果 notify listener 一开始就抄 credit 的 `@EventListener`，本 bug 不会出现。
- **"契约文档说的 AFTER_COMMIT"≠ "运行时环境支持 AFTER_COMMIT"**。P3 §5.2 的设计意图正确，但落地时需要验证事务同步机制在实际 DataSource 下的活性。更好的做法是：先用 `@EventListener` 保证功能可用，再评估是否值得引入 `@TransactionalEventListener` 解耦。
- notify listener 的方法加了 `log.info(...)` 日志——之前没有日志，导致排查时完全黑盒。
