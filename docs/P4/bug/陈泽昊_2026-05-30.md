## Bug #1：Spring `@Component` 默认 bean 名跨模块冲突，连带把 A 的测试也炸了

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-30 16:16 |
| **发现人** | 陈泽昊（D，credit 模块 owner） |
| **所属模块** | credit / notify / config（跨模块） |
| **关联任务 ID** | CRD-04（task 段 listener） |
| **严重等级** | 🟠 高（ApplicationContext 加载失败 → 整个测试套件 8 个用例全红，含 A 的） |
| **是否 AI 协作触发** | 是（AI 起手没显式命名 bean，沿用 `TradeEventListener` 同构写法） |

### 🐛 问题现象

刚写完 `com/campushub/credit/listener/TaskEventListener.java`，跑 `mvn test -Dtest='TaskEventListenerTest'`，
通配匹配同时跑到 D 新建的和 A 早就绿过的 `notify.listener.TaskEventListenerTest`，8 个用例**全部红**：

```
[ERROR] Tests run: 8, Failures: 0, Errors: 8, Skipped: 0
java.lang.IllegalStateException: ApplicationContext failure threshold (1) exceeded
```

**复现步骤：**
1. 在 `credit/listener/` 新建 `TaskEventListener` 类，标 `@Component`（无显式名字）
2. A 已有 `notify/listener/TaskEventListener`，也是 `@Component`（无显式名字）
3. 跑任何一个 `@SpringBootTest` 测试

**预期行为：** 两个不同包下的 listener 互不干扰，各跑各的测试。
**实际行为：** Spring 启动直接抛 `ConflictingBeanDefinitionException`，整个 context 起不来，连 A 的测试也连坐红。

### 🔍 根因分析

挖第一层 `Caused by` 才看到真实原因：

```
ConflictingBeanDefinitionException: Annotation-specified bean name 'taskEventListener'
  for bean class [com.campushub.notify.listener.TaskEventListener]
  conflicts with existing, non-compatible bean definition of same name and class
  [com.campushub.credit.listener.TaskEventListener]
```

- **直接原因**：`@Component` 默认按"类名首字母小写"生成 bean 名，**不看包路径**。A 和我都叫 `TaskEventListener`，bean 名都是 `taskEventListener`，Spring 装配时直接抛冲突。
- **间接原因**：
  - 跨模块协作时 AI 沿用同构命名（看 `TradeEventListener` 长啥样就照抄），不会主动 grep 项目里有没有同名类。
  - Spring 默认命名是**项目级扁平**，而包名隔离给人一种"互不打扰"的错觉，这是个隐性陷阱。
  - 没有 lint 规则 / ArchUnit 约束阻止跨模块同 simple name。
- **是否之前已知**：否。05_后端开发约定.md 没提，AI 协作时也没人想到。

### 🔧 修复方案

```diff
- @Component
- public class TaskEventListener {
+ @Component("creditTaskEventListener")
+ public class TaskEventListener {
```

A 的 `notify.listener.TaskEventListener` 一行不改（先到先占默认名）。

**关联 commit：** `0f01e6f`

### ✅ 验证结果

- [x] `mvn test -Dtest='TaskEventListenerTest'` 同时跑 credit + notify 两个，**Tests run: 8, BUILD SUCCESS**
- [x] `mvn test -Dtest='com.campushub.credit.listener.TradeEventListenerTest'` 邻接 listener 仍绿
- [x] 不需要回归 —— 改的是 bean 名，没有任何代码引用 `@Autowired @Qualifier("taskEventListener")`

### 🧠 经验教训

- **跨模块同名 `@Component` 在 Spring 项目里会静默炸 context**，错误信息还会污染到无辜模块的测试（A 的连坐红）。
- 今后写 listener / strategy / 其它"按角色命名"的组件时，`@Component` 必须用**模块前缀+角色名**显式命名（`creditXxx` / `notifyXxx` / `taskXxx`），无论当前有没有冲突。已建议 A 把这条写进 `05_后端开发约定.md`。
- 调试这类问题的快速路径：`grep "Caused by"`，第一层 `Caused by` 才是真错。

## Bug #2：AI 起手按看板"对称订阅"，未读 publisher 已内联的副作用 → 双扣风险

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-30 15:51（CRD-04 task 段 listener 写之前） |
| **发现人** | 陈泽昊（D） |
| **所属模块** | credit / task（跨模块契约） |
| **关联任务 ID** | CRD-04 |
| **严重等级** | 🔴 阻塞（如真发布，会让 cancel 路径双倍退款） |
| **是否 AI 协作触发** | 是（AI 按看板字面理解订阅范围） |

### 🐛 问题现象

看板 §1.5 CRD-04 一行写明 `credit/listener/TaskEventListener（订阅 TaskCompleted/Canceled）`。
AI 起手直接按"对称"写 listener，要订阅两个事件：

- `onTaskCompleted` → `unfreeze(publisher, reward) + settle(accepter, reward)`
- `onTaskCanceled`  → `unfreeze(publisher, reward) + unfreeze(accepter, deposit)`

看起来合理。但我手动 grep `creditApi\.` 在 `TaskServiceImpl.java`：

```
backend/.../task/service/TaskServiceImpl.java:219:
    creditApi.unfreeze(task.getPublisherId(), reward, "task:" + taskId + ":unfreeze_reward");
backend/.../task/service/TaskServiceImpl.java:222:
    creditApi.unfreeze(assigneeId, deposit, "task:" + taskId + ":unfreeze_deposit");
```

**取消路径的 unfreeze 已经被 B 内联在 service 里调过一次了**。如果 listener 再来一遍，bizKey 后缀不同（service 用 `:unfreeze_reward` / `:unfreeze_deposit`，listener 用别的）→ 幂等键挡不住 → 双倍退款。

**预期行为：** 同一笔业务的 unfreeze 应该只发生一次。
**实际行为（如不修）：** 取消任务后 publisher 余额会涨 2 × reward，accepter 余额会涨 2 × deposit；线上线性吃亏。

### 🔍 根因分析

- **直接原因**：AI 按看板"订阅 TaskCompleted/Canceled"字面输出，没读 publisher 的实现，假设了"事件 = 唯一副作用入口"。
- **间接原因**：
  - 看板的"订阅 X/Y"是给 D 看的工时口径，不是给代码看的契约口径。B 在写 service 时为了简化做了内联处理，看板没同步。
  - AI 不会主动 grep 事件发布者代码确认"副作用是否已经被发布者自己 commit 进事务"。这与 DOC-03 §6.3.2 问题 3（AI 不主动用代码事实仲裁两份文档）同源。
  - bizKey 后缀不同会绕过幂等键 —— 这是 CreditApi 模型的固有特性（同业务三段不同后缀），但反过来意味着同一段被两次不同后缀调用时是不安全的。
- **是否之前已知**：否，看板 CRD-04 行的"订阅"字眼具有误导性。

### 🔧 修复方案

`credit/listener/TaskEventListener` 只订阅 `TaskCompletedEvent`，**不订阅** `TaskCanceledEvent`，
并在 javadoc 把"为什么不订阅"作为一段强约束写进去：

```java
/**
 * ...
 * <p><b>为什么不订阅 TaskCanceledEvent</b>：
 * 取消路径 TaskServiceImpl.cancel（lines 219/222）已经 <i>内联</i>调用 unfreeze
 * 退还发布者悬赏 + 接单者押金（bizKey task:<id>:unfreeze_reward / task:<id>:unfreeze_deposit）。
 * 若 listener 再 unfreeze 一次会因 bizKey 后缀不同绕过幂等键，造成双倍退款。
 */
```

**关联 commit：** `0f01e6f`

### ✅ 验证结果

- [x] listener 单测 3 例（`TaskEventListenerTest`）只针对 Completed
- [x] `TaskHappyPathFlowTest` 集测 1 例覆盖正常路径
- [x] `TaskExceptionFlowTest` 已有的"用户取消任务"用例配合现行 service 行为，没有额外引入双扣

### 🧠 经验教训

- **写 listener 前必须 grep 事件发布者是否已经在自己事务里处理同类副作用**，bizKey 不同 ≠ 幂等保护到位。
- 看板的"订阅 X/Y"是工时口径，不是契约口径。AI 拿看板做契约源是危险的，应该明确告诉 AI **代码是唯一仲裁**。
- 把"为什么不订阅"写进 javadoc 比把它放在 commit message 强一个量级 —— 下次有人想加 `onTaskCanceled` 监听时能立刻看到 why-not。

## Bug #3：`TaskCompletedEvent` payload 缺 `depositPoint`，导致接单者押金在完成路径上无法返还

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-30 16:30（写 QA-02 task 段集测 assert 时） |
| **发现人** | 陈泽昊（D） |
| **所属模块** | task（event 字段）/ credit（listener 副作用） |
| **关联任务 ID** | CRD-04 + QA-02（task 段） |
| **严重等级** | 🟡 中（功能可用但守恒缺口；当前 deposit 永远不退 → 接单者吃亏） |
| **是否 AI 协作触发** | 否（事件字段是 B/A 在 NTF 落地时定的，本就缺一字段） |

### 🐛 问题现象

`task/event/TaskCompletedEvent.java`：

```java
public record TaskCompletedEvent(
        Long taskId, Long publisherId, Long accepterId,
        Integer rewardPoint, long version) {}
```

**没有 `depositPoint`**。但接单时确实 freeze 了 deposit（`TaskServiceImpl.accept` line 262）。
完成路径上 listener 拿不到 deposit 数量 → 退不回去 → 接单者押金永远在 `point_frozen` 字段里冻结到死。

**复现步骤：**
1. publisher 发 reward=40 的任务（publisher freeze 40）
2. accepter 接单（accepter freeze deposit=8）
3. accepter 提交凭证 + publisher 确认完成
4. 查 accepter 的 credit account → `pointFrozen = 8`，永远没释放

**预期行为：** 任务正常完成后 accepter 的 deposit 应该退回 balance。
**实际行为：** deposit 永远 frozen；accepter 余额 = 启动 100 - deposit 8 + reward 40 = 132，但 frozen 还有 8。

### 🔍 根因分析

- **直接原因**：`TaskCompletedEvent` payload 里没 `depositPoint`，listener 不知道要退多少。
- **间接原因**：
  - P3 类图原本只给了 `(taskId, version)` 两个字段（§02 §三.2 表）。A 提议扩到 `(taskId, publisherId, accepterId, rewardPoint, version)`，但**没加 depositPoint** —— 因为 A 当时关注的是 notify 侧（发站内信只要知道双方 id 和 reward），credit 侧的 deposit 释放需求没被 surfacing。
  - B 在 confirm 路径里也没自己内联 deposit unfreeze（不像 cancel 路径那样自己处理了）。
  - 三方（B 出事件 / A 出 notify / D 出 credit listener）没有人专门审计"deposit 在 happy path 上的归宿"。
- **是否之前已知**：否，DOC-03 §三.2 列了 4 个事件的字段缺口，但没标出 deposit。

### 🔧 修复方案

三个选项：

| 选项 | 做法 | 评价 |
|------|------|------|
| A | listener 自己算 `Math.max(reward/5, 5)` 复用 service 逻辑 | DRY 破坏，未来 deposit 公式改了两边不同步 |
| B | 让 B 扩 `TaskCompletedEvent` 加 `depositPoint` 字段 | 跨模块改 record + 改 A 的 notify listener + 改两边单测，工时大且影响面广 |
| **C（采用）** | **显式接受缺口**，javadoc 锁死"deposit 当前完成路径不退"，集测里写一条断言 `assertEquals(DEPOSIT, accFinal.getPointFrozen(), "已知缺口")` 固定当前行为 | javadoc 给人看，测试断言自动报警 —— 下次扩字段时断言立刻红，自然提示同步修 listener |

```java
// credit/listener/TaskEventListener.java javadoc：
//   接单者押金（task:<id>:deposit，accept 时冻结）在完成路径上不被本 listener 释放，
//   因为 TaskCompletedEvent payload 未携带 depositPoint（仅 cancel 事件携带）。
//   押金返还应由 task 模块在 confirm 内联处理，或等事件 payload 扩展后再补到 listener。

// TaskHappyPathFlowTest.java 集测：
assertEquals(DEPOSIT, accFinal.getPointFrozen(),
        "接单者押金当前在完成路径上不退（TaskCompletedEvent 不携带 depositPoint，"
      + "见 TaskEventListener javadoc 已知缺口）");
```

**关联 commit：** `0f01e6f`（javadoc） + `e01a280`（集测断言）

### ✅ 验证结果

- [x] `TaskHappyPathFlowTest#task_fromPublish_toConfirm_settlesCredit` 集测固定当前行为
- [x] javadoc 在两处（listener class doc + onTaskCompleted method）都留了说明
- [ ] 待 B 在某个 sprint 扩 event 字段或在 confirm 内联 deposit unfreeze —— 届时本测试断言会红 → 提示 listener 同步修

### 🧠 经验教训

- **遇到"想做但 payload/接口不允许"时**，第一反应不是"等扩展"也不是"绕实现"，而是 **"写死当前行为为测试断言 + javadoc 锁住 why"**。这比 TODO 注释强一个数量级：TODO 被动，断言主动。
- 跨模块事件契约的 review 必须问一句"**每一笔在前置步骤冻结的积分，在 happy path 上有归宿吗？**"。这次正好是 deposit 漏检的反例。
