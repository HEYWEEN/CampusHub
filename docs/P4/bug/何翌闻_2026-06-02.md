| **是否 AI 协作触发** | 是（IM 模块 AI 协作开发时引入，→ 进信任度实验素材） |

### 🐛 问题现象

登出当前账号 → 登录**另一个**账号 → 点进「消息」里的某个会话，出现两种错乱：
- 看到的是**上一个账号**的会话列表 / 消息内容；
- 或气泡左右（`mine`，我方右 / 对方左）按**旧用户视角**渲染（自己发的显示成对方发的，反之亦然）。

**复现步骤：**
1. A 账号登录，进入某会话 `/app/im/2`（缓存该会话消息）
2. 登出，登录 B 账号
3. 点进消息 → 显示的是 A 的会话 `/app/im/2`，且 `mine` 按 A 的视角算

**预期行为：** B 登录后只能看到 B 自己的会话；气泡方向按 B 视角。
**实际行为：** 命中 A 残留的前端缓存，显示 A 的数据 / A 的 `mine` 标记。

### 🔍 根因分析

- 直接原因：IM 的 React Query 查询 key（`['im','conversations']`、`['im','messages',cid]`）**不含 userId**，且登出/登录流程**从不清 React Query 缓存**。新用户进来直接命中旧用户缓存。
- 为什么 `mine` 会反：`mine` 是后端按**当前请求用户**计算后返回的（`ImMessageVO.from(m, viewerId)`）。A 取过的数据里 `mine` 是 A 的视角，缓存原样喂给 B。
- 间接原因：登出入口分散（`MePage` 登出按钮、`api/client.ts` 的 401 拦截、`LoginPage` 登录），没有任何一处统一清缓存。
- 是否之前已知：否。多用户共用同一前端缓存的典型隐患，开发时没意识到。

### 🔧 修复方案

集中式：在 `App.tsx` 顶层订阅 `auth.userId`，一旦变化（登录/登出/换号）即 `queryClient.clear()`，覆盖所有入口。

```diff
+ const userId = useAuthStore((s) => s.userId)
+ const qc = useQueryClient()
+ const prevUserId = useRef(userId)
+ useEffect(() => {
+   if (prevUserId.current !== userId) {
+     qc.clear()                 // 换号/登出清掉上一个用户的全部缓存
+     prevUserId.current = userId
+   }
+ }, [userId, qc])
  return <RouterProvider router={router} />
```

后端本就有会话参与者校验（非参与者访问返回 `8001 NOT_PARTICIPANT`），清缓存后 refetch 即拿到正确数据，双重兜底。

### 🧠 经验教训

1. **多用户 / 会话型应用，用户态切换必须清查询缓存**（或把 `userId` 纳入 query key）。隐私数据尤其要防"缓存串账号"。
2. 登出/登录入口往往分散，**在状态源（auth store）的单一变量上集中响应**比每个入口各清一遍更可靠、不易漏。
3. AI 直出的 per-user 接口缓存默认按 key 缓存，不会自动感知"当前用户变了" —— 审查 AI 生成的 react-query 代码时要专门检查这一点。
