## Bug #1：A 给的 `CreditApi` 句柄式契约与 P3 §5 不一致，险些把 freeze/settle 全实现错

### 📌 基本信息

| 字段 | 内容 |

| **是否 AI 协作触发** | **是**（第一个 Explore subagent 直接抄了 A 的旧伪代码并给出错误结论） |

### 🐛 问题现象

CreditApi 应该按 P3 §5 表用 **bizKey 幂等模型**：

```java
void freeze(long userId, int points, String bizKey);
void unfreeze(long userId, int points, String bizKey);
void settle(long userId, int points, String bizKey);
void deduct(long userId, int delta, String reasonCode, String bizKey);
```

但 A 在 `docs/P4/05_后端开发约定.md` 的伪代码示例里写的是 **freezeId 句柄模型**：

```java
String freezeId = creditApi.freeze(userId, points);
creditApi.settle(freezeId, payeeId);   // 用 freezeId 而不是 bizKey
```

两种模型互斥：
- bizKey 模型：DB 有 `credit_record.biz_id UNIQUE` 做幂等，调用方负责生成稳定 bizKey（`task:123:freeze`）
- freezeId 模型：需要额外 `credit_freeze` 句柄表跟踪冻结/解冻配对

**实际查 `docs/P3/数据库/schema.sql`：根本没有 freeze 句柄表，只有 `credit_record.biz_id UNIQUE`。**

**预期行为：** D 出的 `CreditApi` 与 P3 §5 表 + schema.sql 一致（bizKey 模型）
**实际（差点发生）：** 第一个 AI Explore subagent 抄了 A 文档里的 freezeId 伪代码，给我"freezeId 才是对的"结论 → 如果直接照做 → B/C 调用全部失败 + DB 没有的表凭空多出

- **直接原因**：A 在写 `05_后端开发约定.md` 时（早于 schema.sql 定稿）按个人习惯写了 freezeId 风格的伪代码示例，但 P3 §5 详细设计定稿和最终 schema 都已经走向 bizKey 模型；A 没回头校准约定文档
- **AI 协作的失误**：第一个 Explore subagent 读了 `05_后端开发约定.md` 找到看起来权威的"接口签名示例"，没继续校验 P3 §5 表 / schema.sql 是否一致，给出了**自信但错误**的结论
- **我的失误**：起初差点采信 subagent 第一轮结论，幸好疑心 schema 里"freeze 句柄表"的存在，回查 P3 §5 第 136 行 + schema unique key 才证伪
- **是否之前已知**：A 的 commit `192bd77` 已经把约定文档对齐到 bizKey 了（同一天稍早），但反思日志里没记这个分歧 → 我作为后写代码的人需要每次去 P3 §5 source-of-truth 拉权威值

### 🔧 修复方案

1. **代码侧** — `credit/api/CreditApi.java` 与 `service/CreditServiceImpl.java` 严格按 P3 §5 五方法签名实现，bizKey 走 `recordRepo.existsByBizId(bizKey)` 短路：

2. **协作侧** — 同步给 A：约定文档若还残留 freezeId 句柄伪代码应彻底删除（已由 `192bd77` 修；我抽查复核了一次，确认无残留）

### 🐛 问题现象

实现 `ScoreRule` enum 时面对两个互相矛盾的需求源：

| 来源 | 加分项数 | 扣分项数 |
|---|---:|---:|
| `docs/P4/01_Sprint看板.md` §1.5 CRD-03 行 | **5** | 4 |
| `docs/P1/.../SRS.md` FR-CRED-01 第 426~444 行（最终验收依据） | **1**（仅"任务完成双向好评 +1"） | 4 |

AI 第一版按看板字面输出，凭空编出 4 个不存在的加分项（"首次发布奖励 / 七日活跃 / ..."）。

**预期行为：** 实现严格对应 P1 SRS FR-CRED-01（学校验收时唯一权威）
**实际行为（修复前）：** 按看板字面 + AI 补全 → 5 个加分项里有 4 个是 AI 编的，SRS 里没写

### 🔍 根因分析

- **直接原因**：看板（A 主笔）把"加分项数量"写成了 5，但 SRS 只定义了 1 个；P3 详细设计沿用 SRS
- **间接原因**：P4 看板是后写的"任务清单"，作者归纳数字时手滑或心算错了；没人审查过这个数字 vs SRS 的一致性
- **AI 协作的失误**：AI 看到看板说"5 + 4"会**自动补齐**到 5 个加分项（生成 4 个貌似合理的 reasonCode），即使 SRS 没有这些；这是 AI 的"配凑数字"倾向 —— 给了目标数它会生造素材
- **是否之前已知**：否，本日才发现

### 🔧 修复方案

按 SRS 实现 5 条规则（1 加分 + 4 扣分），AI 编的 4 项加分**全部丢弃**：

```java
public enum ScoreRule implements ScoreStrategy {
    TASK_COMPLETE_BONUS("TASK_COMPLETE_BONUS", +1, "任务完成双向好评 +1（FR-CRED-01）"),
    TASK_NO_SHOW       ("TASK_NO_SHOW",        -5, "接单后无故取消 -5"),
    SEVERE_VIOLATION   ("SEVERE_VIOLATION",   -30, "严重违规一次 -30"),
    TREEHOLE_VIOLATION ("TREEHOLE_VIOLATION", -10, "树洞人身攻击/隐私 -10"),
    MALICIOUS_REVIEW   ("MALICIOUS_REVIEW",   -10, "议价报复经核实 -10");
    // 看板上写的"5 加分 + 4 扣分"不准；SRS FR-CRED-01 实际仅 1 加分 + 4 扣分
}
```

并在 enum Javadoc 里写明分歧来源与 SRS 行号引用,避免未来读者重蹈覆辙。

**关联 commit：** `eb750a3`（ScoreRule 一并落地）
**未改文档**：没去改看板"5+4"措辞（不是我的所有权文件）；已在站会脚本里 @A 提了一句"看板加分项数字与 SRS 不一致,看是否要回改"。

1. **AI 看到"数量"会自动配凑** —— 这是写 prompt 时最容易被坑的隐性陷阱。下次涉及"列出 N 条规则"的 prompt 必须写"如果文档实际只有 M < N 条，按 M 实现并显式 flag 数字差异，禁止编造补全"。

## Bug #4：P3 §5 `settle(userId, points, bizKey)` 单 userId 签名 → 转账双账户语义无处安放

### 📌 基本信息

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-05-23 11:10（CRD-01 写 settle 时） |
| **发现人** | 陈泽昊（D） |
| **所属模块** | credit / 跨模块契约 |
| **关联任务 ID** | CRD-01 + 待 B CRD-04 联调 |
| **严重等级** | 🟡 中（不影响本期单测，但联调 B 的 TaskCompletedEvent 时必须澄清；不澄清会出现"双方账户都加积分"的乌龙） |
| **是否 AI 协作触发** | 否（P3 §5 签名本身就有歧义；AI 实现时按字面直译） |

### 🐛 问题现象

P3 §5 给的契约：

```java
void settle(long userId, int points, String bizKey);
```

**只接受一个 userId**。但 task 完成结算的真实业务是 **双账户操作**：
- 付款方（发布者）：`pointFrozen -= points`
- 收款方（接单者）：`pointBalance += points`

签名里没有"付款方/收款方"的区分,**仅靠 userId 无法表达"我是谁"**。

**预期行为：** settle 同时处理付款方 frozen 释放 + 收款方 balance 入账
**实际行为（本次实现）：** 只能选一边 —— 按"收款方入账"单边语义实现；付款方 frozen 释放留 TODO 等 B 的 TaskCompletedEvent payload

### 🔍 根因分析

- **直接原因**：P3 §5 契约表设计时把 `freeze/unfreeze/settle` 当作"单账户三动作"看待，没考虑到 settle 本质是"转账"（双账户）
- **间接原因**：P3 详细设计阶段没写 settle 的伪代码,只有签名;签名 review 时没意识到语义缺失
- **是否之前已知**：否

### 🔧 修复方案（折中,需 B 协作确认）

本期按"收款方入账"单边实现 settle,付款方 frozen 释放等 CRD-04 listener 收到 B 的 `TaskCompletedEvent(taskId, publisherId, assigneeId, points)` 后,**分两次调 API**:

```java
@TransactionalEventListener
public void on(TaskCompletedEvent e) {
    creditApi.unfreeze(e.publisherId(), e.points(), "task:" + e.taskId() + ":unfreeze");
    creditApi.settle(e.assigneeId(),   e.points(), "task:" + e.taskId() + ":settle");
}
```

这样 settle 的单 userId 含义就是"收款方";付款方 frozen 释放走 unfreeze API。语义清晰、契约不破。

**已写入** `credit/service/CreditServiceImpl.java` 类 Javadoc:
> 注: settle 当前实现为「收款方入账」单边语义;付款方冻结的释放(task 完成时发布者 point_frozen 扣除)需与 B 的 task 完成事件 payload 一并敲定,见 CRD-04。

**协作项**: 跟 B 确认 `TaskCompletedEvent` 字段包含 `publisherId / assigneeId / points`,我才能落 listener。

**关联 commit：** `eb750a3`

### ✅ 验证结果

- [x] `CreditServiceTest#settleCreditsPayeeBalance` 验收单边语义符合预期
- [x] `CreditServiceTest#settleIsIdempotentByBizKey` 重复 settle 不双加
- [x] Javadoc 显式写明单边语义+未来联调路径
- [ ] CRD-04 listener 完整双边链路单测(BLOCKED on B 的 TaskCompletedEvent 类)

### 🧠 经验教训

1. **契约表里"看起来对称的方法签名"未必能承载真实业务语义**。freeze/unfreeze 是单账户操作所以 `(userId, points, bizKey)` 够用,但 settle 是双账户转账,同样签名就不够 —— 这种"对称带来的安全感"是设计层的隐性陷阱。
2. **遇到契约语义缺失时,折中方案优于改契约**。本来想推 A 改成 `settle(payerId, payeeId, points, bizKey)`,但已经签字的契约改一次代价高(B/C 都要联动);改成"unfreeze + settle 两次调用"既符合现有签名也清晰、还顺便用上了已有的 unfreeze 幂等。
3. **TODO 必须落 Javadoc,不能只落代码注释或心里默念**。Javadoc 在 IDE hover 时能看到,未来 B 联调时会自然读到这段说明。普通 `// TODO` 会被淹没在代码里。
