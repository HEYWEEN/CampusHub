## 二、做得好的地方（值得 B/C 借鉴）

### 2.1 `@TransactionalEventListener(phase = AFTER_COMMIT)` 的选择正确

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onTaskAccepted(TaskAcceptedEvent event) { ... }
```

`notify` 的 listener 用 `AFTER_COMMIT`，**与 D 的 `credit listener` 用默认（同步、与发布事务合并）形成清晰对照**：
- credit：合并事务，失败必须回滚业务（钱算错了 = 任务也不算完成）
- notify：分离事务，失败不应回滚业务（通知没发不能让用户的钱白冻）

这一点 javadoc 第 17 行写明了 "避免'通知失败导致业务回滚'的耦合"，是教科书级的事务边界判断。**建议把这段拿出来放到 `05_后端开发约定.md §七 listener 章节作为正反例对照**。

### 2.2 三层幂等防御

```java
public void appendLetter(...) {
    if (repo.existsByBizKey(bizKey)) return;     // 层 1：应用短路
    try {
        repo.save(new NotifyMessage(...));
    } catch (DataIntegrityViolationException dup) { // 层 2：并发兜底
        // 静默
    }
}
// + 层 3：DB uk_notify_biz_key
```

并发 race 下两个线程都查不到 → 都尝试 INSERT → DB UK 兜底 → 后到的吞掉异常。和 D 的 `credit_record.uk_credit_record_biz` 是同套路。**重要的是 catch 块的注释说明了"为什么 silent"**，避免 future reader 把它当成 bug 删掉。

### 2.3 拒绝跨模块查表，宁可文案不友好

```java
// NotifyTemplate.java javadoc 第 8-11 行：
// 早期版本想用任务标题渲染，但那要求 listener @Autowired TaskRepository，
// 破坏 P3 §3.4 模块边界（notify 不依赖 task 实现）。
// 用 taskId 是 pragmatic choice：文案略不友好但 listener 保持零依赖
```

这是**主动写下来的取舍**，比"无声做了取舍但没人知道"强一个量级。如果哪天 PM 要求文案带任务标题，会有人能立刻指着这段说"那必须改架构"。

### 2.4 复合索引设计与查询模式对齐

```sql
KEY idx_notify_user_unread (user_id, read_at, created_at)
```

对应 `findByUserIdOrderByReadAtAscCreatedAtDesc` —— "我的全部，未读优先，时间倒序"。
索引列顺序、查询 ORDER BY 顺序、ASC/DESC 方向都对得上。MySQL 8 能用这个索引做 index sort，无 filesort。

## 三、建议调整（不阻塞合并）

### 3.1 🟡 `@Component` 默认 bean 名 `taskEventListener` 已造成跨模块冲突

**现状**：A 的 `notify/listener/TaskEventListener` 用 `@Component`，bean 名默认为 `taskEventListener`。
D 在做 CRD-04 task 段时建了 `credit/listener/TaskEventListener`，**直接撞名**，Spring 装配失败、连带 A 的测试一起红。D 已经用 `@Component("creditTaskEventListener")` 让步避开（commit `0f01e6f`）。

**问题**：
- D 这次让步可以，但今后 B/C 写自己的 `TaskEventListener` 还会再撞；
- 当前的"先到先占默认名"不是个稳定约定。

**建议**：A 把自己的也改成 `@Component("notifyTaskEventListener")`，**统一规则**为
"所有 `XxxEventListener` 必须用 `<module>` 前缀显式命名"。这条加进 `05_后端开发约定.md`
（D 已经在 `bug/陈泽昊_2026-05-30.md` Bug #1 经验教训里建议过）。

**优先级**：低，但**最好这两天就改**，因为越晚改影响代码越多。

### 3.2 🟡 看板"24h 同类去重"语义 vs 实现的"bizKey 全局唯一"语义偏差

**看板原文**（§1.5 NTF-01 完成标准）："uk_notify_biz_key 兜底，24h 同类去重"
**实现**：bizKey = `TYPE:taskId:userId`，是**全局静态唯一**，不是"24h 滑动窗口"。

**差异**：
- 当前：用户 7001 任务 42 被接单 → 站内信 #1，bizKey=`TASK_ACCEPTED:42:7001`。如果同一任务后来被取消 → 重新接单（同一接单者），第二次 `TASK_ACCEPTED:42:7001` 会被 `existsByBizKey` 吞掉，**用户收不到通知**。
- 看板预期："24h 内同类去重"应该是滑动窗口，意思是同一事件 24h 内重投不重复发，**但 24h 外的同类事件应该重发**。

**两种修法**：

| 方案 | 改法 | 评价 |
|------|------|------|
| A | bizKey 里加日期片段：`TASK_ACCEPTED:42:7001:20260530` | 简单但牺牲了"同日重投幂等" |
| B | 改 service：`existsByBizKey` → `existsByBizKeyAndCreatedAtAfter(bizKey, now - 24h)`；不依赖 DB unique 单约束 | 真正实现 24h 窗口，但 DB unique 失效需要去掉 |
| **C** | **承认实现就是"全局唯一"，把看板描述修正为"同类同接收人静态幂等"** | 改文档 1 行；实现保留三层兜底；最务实 |

**D 倾向方案 C**：当前实现的"静态 bizKey 唯一"反而比"24h 窗口"语义更可靠（重启不丢、跨实例不丢）。
"同任务取消后再接单"的边角场景如果真要通知，应该用新事件（如 `TASK_REOPENED`）而不是复用 `TASK_ACCEPTED`。

**优先级**：低。但**A 需要在 W14 演示前要么改实现要么改文档**，否则评审一对比就会被问到。

### 3.3 🟢 nit：`NotifyMessage.createdAt` 在 Java 端默认 + DDL 也 `DEFAULT CURRENT_TIMESTAMP`，双源

```java
@Column(name = "created_at", nullable = false)
private Instant createdAt = Instant.now();   // Java 端默认
```

```sql
created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,   -- DB 端默认
```

JPA insert 时 Java 默认会赢（持有非 null 值），DB 默认从未被用上。两源并存不会出 bug，
但耦合度高，未来若改 Java 默认（例如改成构造参数注入时钟），可能误以为 DB 还会兜底。
**建议二选一**：要么删 Java 默认让 DB 填（推荐，方便 mock 时钟），要么删 DDL 默认让 Java 唯一负责。

**优先级**：很低，不在 W14 前改也无影响。

### 3.4 🟢 nit：`markAllRead` 拉全部到内存再 saveAll

```java
List<NotifyMessage> unread = repo.findByUserIdAndReadAtIsNullOrderByCreatedAtDesc(userId);
for (NotifyMessage m : unread) { m.markRead(); }
repo.saveAll(unread);
```

如果用户积压 1000 条未读，一次 SELECT 1000 行 + N 次 UPDATE。
**理想做法**：

```java
@Modifying
@Query("UPDATE NotifyMessage m SET m.readAt = :now " +
       "WHERE m.userId = :uid AND m.readAt IS NULL")
int markAllReadByUser(@Param("uid") long uid, @Param("now") Instant now);
```

一句 SQL。但当前演示场景用户数 < 100，不优化也跑得动。

**优先级**：很低，记入"已知技术债"即可。
