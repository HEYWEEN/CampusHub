## 二、做得好的地方（C 模块直接受益）

### 2.1 bizKey 模型与 C 侧调用完全对齐

C 在下单时冻结：

```java
creditApi.freeze(buyerId, dto.getNegotiatedPricePoint(), "trade:" + order.getId() + ":freeze");
```

`TradeEventListener` 完成时：

```java
creditApi.unfreeze(event.buyerId(),  event.pointAmount(), prefix + ":unfreeze");
creditApi.settle  (event.sellerId(), event.pointAmount(), prefix + ":settle");
```

freeze / unfreeze / settle **三个动作三个不同后缀**，符合 `02_后端代码分工.md §三.1` 约定。C 不需要懂 credit 内部结构，只构造语义化 bizKey 即可；重放同 key 时 `CreditServiceImpl.alreadyDone` 静默短路，trade 侧无需额外幂等逻辑。

### 2.2 `TradeOrderCompletedEvent` 四字段够用，listener 不越界

C 发布的事件 record 含 `(orderId, buyerId, sellerId, pointAmount)`，`TradeEventListener` 仅凭 event payload 完成结算，**未** `@Autowired TradeOrderRepository`。这与 P3 §3.4 模块边界一致，也是 C 在 TRADE-04 设计 event 时的明确目标（见 DOC-03 §6.2.4）。

### 2.3 `TradeHappyPathFlowTest` 是 C 模块最好的回归网

集测走 MockMvc 黑盒：注册 → JSON 发商品 → 下单 → 双方 confirm → 断言 buyer balance/frozen 与 seller balance 变化。比 C 自己的 service 单测更接近联调真实路径，且与 `TradeEventListener` 同 Spring context，能捕获 bean 冲突类问题（D 在 5-30 已踩过）。

### 2.4 主动 grep publisher 再写 listener，避免双 unfreeze

D 在 CRD-04 task 段发现 `TaskServiceImpl.cancel` 已内联 unfreeze，**刻意不订阅** `TaskCanceledEvent`，并在 javadoc 写明原因。这种「用代码事实仲裁看板字面」的做法，C 在 trade 侧若未来加 cancel+unfreeze 路径时应同样遵守——先 grep listener 是否已处理。

### 2.5 BaseIT + `List<JpaRepository<?,?>>` 自动收集

`BaseIT` 让 B/C 写同构集测时几乎复制粘贴即可成型。C 的 trade 段 happy path 受益于此；未来 edu 若补集测也可直接继承。

## 三、建议调整（不阻塞合并）

### 3.1 🟡 `settle` 单边语义 + `unfreeze` 组合导致全局非守恒（trade 段同样存在）

**现状**：`TradeEventListener` 先 `unfreeze(buyer)` 再 `settle(seller)`，效果是「买家拿回押金 + 卖家入账」，系统总积分增加。javadoc 已标注为已知缺口，推后等 `CreditApi.transfer`。

**对 C 的影响**：当前演示/集测可跑通，但答辩时可能被问「积分从哪来」。建议 D 在 `06_后端代码审查指南.md §5.3` 保持登记，答辩前与 B 统一口径（task/trade 同套路）。

**优先级**：低（P4 不修），文档已有。

### 3.2 🟡 `TaskCompletedEvent` 缺 `depositPoint`，task 完成路径 accepter 押金不退

**现状**：与 C 无直接代码耦合，但 C 作为邻居模块 owner 需知：task 完成时 accepter 的 deposit 仍 frozen，集测用断言固定了当前行为。

**建议**：若 B 扩展 event payload，D 同步改 listener；C 无需改 trade，但应在站会确认「task deposit 缺口不影响 trade 结算路径」。

**优先级**：中（task 模块 owner B 驱动）。

### 3.3 🟡 `TradeEventListener` 未显式命名 bean（低风险）

D 的 `TaskEventListener` 已用 `@Component("creditTaskEventListener")` 避让 A 的 notify listener；`TradeEventListener` 仍用默认 bean 名 `tradeEventListener`，目前无冲突。

**建议**：与 notify/credit 统一，改为 `@Component("creditTradeEventListener")`，预防未来 C 若写 `trade/listener/TradeEventListener` 再撞名。

**优先级**：低。

## 四、对 C 模块的联动影响核对

| C 侧动作 | D 侧响应 | 一致性 |
|----------|----------|--------|
| `createOrder` → `freeze(buyer, price, trade:<id>:freeze)` | 无 listener（下单非完成） | ✅ |
| 双方 `confirmOrder` → `TradeOrderCompletedEvent` | `unfreeze(buyer)` + `settle(seller)` | ✅ bizKey 后缀不冲突 |
| 订单未完成前取消（若未来实现） | 需 C 内联 `unfreeze` 或新 event；**不应**假设 D listener 会处理 | ⚠️ 参考 task cancel 模式 |
| `TradeHappyPathFlowTest` 断言 | 与 listener 副作用一致 | ✅ |

**结论**：C 模块对 D 的硬依赖（CRD-01 freeze + CRD-04 trade listener + QA-02 trade 段）已闭合，可标记 TRADE-03/04 对 credit 的依赖为已验收。
