## 二、做得好的地方（A 受益最直接的点）

### 2.1 事件字段补全 —— 直接解锁我的 notify listener

§三.2 当时挂着「事件字段偏少，listener 不能反查 TaskRepository」这个未决项，我提了一版扩展建议。B 实现的 record 和建议几乎一致：

```java
// task/event/TaskCompletedEvent.java
public record TaskCompletedEvent(
        Long taskId, Long publisherId, Long accepterId,
        Integer rewardPoint, long version) {}
```

这让我的 `TaskEventListener.notifyBoth()` 能直接拿 `publisherId / accepterId` 给双方发信：

```java
// notify/listener/TaskEventListener.java line 75-78
private void notifyBoth(NotifyTemplate tpl, long taskId, Long publisherId, Long accepterId) {
    notifyOne(tpl, taskId, publisherId);
    notifyOne(tpl, taskId, accepterId);   // accepter 为 null（PENDING 取消）时内部跳过
}
```

**关键收益**：notify 完全不依赖 `TaskApi`/`TaskRepository`，INV-01 零越界。`TaskCanceledEvent` 还贴心地在 `accepter == null` 时传 null（`TaskServiceImpl.cancel` line 237-238），我这边 `notifyOne` 一个 null 判断就兜住了「待接单直接取消只通知发布者」。

### 2.2 状态机实体层兜底 —— scheduler 都越不过白名单

```java
// task/entity/Task.java line 114-115
public void setStatus(TaskStatus status) {
    if (!this.status.canTransitionTo(status)) { /* 抛异常 */ }
```

State 模式（`TaskStateContext` + 7 个 State 类）负责业务流校验，但 B 又在 `setStatus()` 里嵌了一层 `canTransitionTo()`。结果是 `TaskTimeoutScanner.scan()` 即便绕过 `TaskStateContext` 直接 `task.setStatus(EXPIRED)`（scanner line 38），也不可能造出非法转换。这种「业务层 + 实体层」双保险比 C 的 trade（校验散落在各 service 方法）更稳。

### 2.3 bizKey 后缀分离严格遵守 §三.1

同一 task 的三笔 credit 动作用了三个不同后缀，且取消时奖励/押金再拆两笔：

```java
// 发布: task:<id>:freeze     接单: task:<id>:deposit
// 取消: task:<id>:unfreeze_reward + task:<id>:unfreeze_deposit
// 完成: task:<id>:unfreeze_deposit
```

`uk_credit_record_biz` 不会撞键。`cancel()` 里**先快照** `assigneeId/reward/deposit`（line 223-225）再走 `ctx.cancel()`，避免状态流转后字段被清空——这个顺序很细心。

### 2.4 认证 + 信用双门槛，全走 Api interface

`create`（line 95-103）和 `accept`（line 246-249）都先 `userApi.getVerifyStatus()` 验认证、再 `creditApi.getScoreOf()` 验信用分，全程走我暴露的 `UserApi` / D 的 `CreditApi`，没有 `@Autowired` 任何 ServiceImpl。

## 三、建议调整

### 3.1 🔴 dailyAcceptLimit 绕过 UserApi 直接读写 `UserProfileRepository`（需要我配合）

**现状**：task 模块直接注入了我的 `UserProfileRepository`、引用了 `UserProfile` 实体：

```java
// TaskServiceImpl.java line 51 / 262-264（读）
int limit = profileRepo.findByUserId(userId)
        .map(UserProfile::getDailyAcceptLimit).orElse(2);
// line 383-385（写）
UserProfile profile = profileRepo.findByUserId(userId).orElseThrow(...);
profile.setDailyAcceptLimit(limit);
```

但 `UserApi` 目前只暴露 `getPublicUser` / `getVerifyStatus`，且接口注释白纸黑字写着「**禁止直接 @Autowired UserServiceImpl**」。这里更进一步——直接吃了我的 Repository + entity，正好踩中 §一 铁律和 §四 review 清单「跨模块调用是否走 `*Api` interface」。一旦我改 `user_profile` 表结构或给 `dailyAcceptLimit` 加业务规则（如 VIP 上限），task 会被静默带崩。

**建议**：我来在 `UserApi` 补两个方法，task 侧改调接口、删掉 `UserProfileRepository`/`UserProfile` 依赖：

```java
int  getDailyAcceptLimit(long userId);          // 缺省 2
void setDailyAcceptLimit(long userId, int n);   // 校验区间放我这边
```

**优先级**：🔴 中高。功能现在能跑，但属于明确的边界违约，建议本轮合入前一起改。我可以今天就把 `UserApi` 加好，你 wire 过去即可。

### 3.2 🟡 accept 乐观锁是「读-校验-save」，并发碰撞落到 500 而非 409

**现状**：

```java
// TaskServiceImpl.accept line 257-258
if (task.getVersion() != expectedVersion) {
    throw new BizException(TaskErrorCode.VERSION_CONFLICT, "任务已被其他人抢先接单");
}
```

这步只挡住「客户端拿着旧 version 来接」。真正的并发——两个请求同读到 `version=v`、都通过 `!= expectedVersion`、都走 `ctx.accept + freeze + save`——靠的是 JPA `@Version` 在 flush 时抛 `ObjectOptimisticLockingFailureException`。问题在我的 `GlobalExceptionHandler` **没有这个异常的 handler**，会落到 `@ExceptionHandler(Throwable.class)`（line 80）→ **500**。§完成标准要求「并发 50 次只能 1 次成功」，结果是 1 次 200 + 49 次 500（而非友好的 409）。

**两个修法（择一）**：
- **(B 侧，推荐)** 仿 C 在 trade 的原子 CAS——这正是你在 `B评C §二.1` 点赞过的写法：
  ```java
  int updated = taskRepo.acceptIfMatch(taskId, userId, expectedVersion); // UPDATE ... WHERE id=? AND status=0 AND version=?
  if (updated == 0) throw new BizException(VERSION_CONFLICT, ...);  // 直接 409，无异常栈
  ```
- **(A 侧兜底)** 我在 `common/GlobalExceptionHandler` 加一个 `ObjectOptimisticLockingFailureException → 409` 的 handler，全队的乐观锁碰撞统一翻译。

**建议**：两者其实可以都做——你上原子 CAS 治本，我加 handler 兜住其他模块。需要我加的话说一声。

**优先级**：🟡 中。

### 3.3 🟡 超时扫描单大事务 + 同步 notify，一条失败回滚整批

**现状**：`TaskTimeoutScanner.scan()` 是一个 `@Transactional` 方法，循环里逐个 `setStatus(EXPIRED) + save + publishEvent`（scanner line 32-45）。我的 `TaskEventListener` 现在是 `@EventListener` **同步、同事务**（当初因为 MariaDB+JPA 下 `AFTER_COMMIT` 不触发改的）。两者叠加 → 批里**任意一条** task 的 notify 写失败，整个 scan 事务回滚，**这一批所有 EXPIRED 都不落库**，下个周期重扫重发。

**建议**：扫描循环改成**每条独立事务**（把单条处理抽成 `@Transactional(REQUIRES_NEW)` 的方法，或在 scanner 里逐条提交），把一条的失败隔离掉。这块根因有一半在我的同步 listener 上，算我俩的共同账，我可以配合把 listener 对「单条 notify 失败」做 try-catch 降级（记日志不抛）。

**优先级**：🟡 中低。demo 数据量下不会触发，但属于健壮性隐患。

### 3.4 🟢 search 排序字段直接取自请求参数

```java
// TaskServiceImpl.search line 157
String sortField = query.getSort().split(",")[0];
Pageable pageable = PageRequest.of(..., Sort.by(dir, sortField));
```

`sortField` 未做白名单，传个不存在的属性名会触发 `PropertyReferenceException` → 又落到 Throwable → 500。建议用一个允许集合（`createdAt/deadlineAt/rewardPoint`）兜一下，非法值回退默认排序。

**优先级**：🟢 低，refactor 时顺手。

## 四、对 A 模块（auth / user / notify / common）的联动核对

| A 侧依赖点 | B 侧实现 | 一致性 |
|----------|----------|--------|
| `UserApi.getVerifyStatus` | create/accept 调用 | ✅ 走接口 |
| `UserApi.getPublicUser` | getDetail 渲染发布者/接单者 | ✅ 走接口 |
| `UserProfileRepository`（我的内部件） | dailyAcceptLimit 直接注入 | ❌ 越界，见 §三.1 |
| 4 类 task 事件字段 | record 带齐 publisher/accepter/reward/deposit | ✅ notify listener 零反查 |
