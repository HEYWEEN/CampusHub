## 1. 项目与 P0 范围

CampusHub 是面向单一高校的「**校园需求互助平台**」：以**虚拟积分**为唯一价值媒介，覆盖**跑腿/万能互助/二手交易/课程评价与资料/比赛组队/树洞**等模块，由**学生证人工认证 + 信用分**双闸门控制风险，**严禁外部支付与外部身份系统**（详见 ADR-003/004）。

本期 P3 详细设计的**P0（Must）范围**（来自 [02 功能映射主表](./02_功能映射主表.md) 中 ✓ 行，共 38 个）覆盖以下 9 个模块的核心闭环：

| 模块 | P0 关键能力 |
| :--- | :--- |
| `auth` | 短信验证码 + 密码登录、JWT、学生证认证（人工审核）|
| `user` | 资料、隐私三开关、PublicUserVO |
| `task` | 发布—接单—完成凭证—确认—取消—超时（State 机 + 乐观锁）|
| `trade` | 二手商品上下架 + 议价后下单 + 双方确认 |
| `edu` | 辅导任务发布（违禁词同步拦截） |
| `im` | 任务关联会话、消息持久化、未读计数、申诉证据导出 |
| `notify` | 事件 → 站内信、超时温柔提醒 |
| `credit` | 信用分查询、积分冻结/解冻/结算、扣减（Strategy）、差评申诉 |
| `report` + `admin` | 仲裁工作台、强制结算/退款、认证审核、操作审计 |
| `search` | 任务大厅多维筛选 |

**降级项：** `team` 模块（招募）整体为 ★（P1，本期类图不展开）；`wall`（树洞）模块归属待团队会议决定；`F-RANK-01`（热门榜单）整体 Won't。

## 2. 设计基线与硬性约束

### 2.1 来自 P1 SRS 的硬性约束（PR 必查）

1. **资金**：禁真实支付/二清；仅校园虚拟积分（INT，禁 DECIMAL）。
2. **身份**：禁 SSO/OAuth/CAS；身份依赖手机号 + 学生证人工认证 + 密码（详见 [决策记录 D3-02](./决策记录.md#d3-02鉴权方案引入密码回归-p1-srs-原意)）。
3. **隐私**：手机号/真实姓名/学号/证件号严禁明文落库；前台 API 禁出黑名单字段。
4. **信用规则实时性**：`< 80 限单 1 / < 60 禁发禁接`，必须**同事务内**完成判定，不能依赖异步窗口。
5. **响应时间硬约束**：常规接口 P95 ≤ 1.5s；任务/订单完成动作积分流转 ≤ 10s。

### 2.2 来自 P2 架构的不变量（INV-01 ~ INV-06）

| 编号 | 不变量 | 在 P3 的检查点 |
| :--- | :--- | :--- |
| INV-01 | 跨模块只走 `XxxApi` 或 `ApplicationEvent` | 见 [04 §4](./04_核心类图.md#4-跨模块依赖总览合法边) 合法边图 |
| INV-02 | 业务表归属唯一，无跨模块 FK | 见 [数据库/schema.sql](./数据库/schema.sql)：跨前缀**均**为逻辑外键 |
| INV-03 | Controller 出参禁 Entity | [openapi.yaml](./API/openapi.yaml) 所有响应均为 VO；见 [API/AI 辅助审查](./API/AI辅助审查_API.md) §5 |
| INV-04 | 扣分/积分类 Listener 必 `BEFORE_COMMIT` | 见 §5.2 事件契约表 |
| INV-05 | `/api/admin/**` 必 `@PreAuthorize` | OpenAPI 中管理端路径独立 tag；P4 在 SecurityConfig 落地 |
| INV-06 | 日志输出用脱敏 DTO | 见 [01 统一规约 §2.5.2](./01_统一规约.md) + [P2 ADR-004](../P2/ADR.md) |

### 2.3 P3 阶段全员强约束（来自 [01 统一规约](./01_统一规约.md)）

- **命名**：见 §1。后缀（Controller/Service/Impl/Repository/DTO/VO/Api/Event/Exception/Config）强制。
- **API 契约**：见 §2。统一响应包装 `{code,message,data,traceId}`；分页 `page` 从 1 起；错误码 4 位整数分段；时间 ISO 8601。
- **数据建模**：见 §3。`BIGINT` 主键 + 全表审计字段；跨模块禁 FK；枚举统一 `TINYINT` + Converter（[决策 D3-01](./决策记录.md#d3-01状态枚举存储采用-tinyint不用-varchar)）。
- **设计模式**：团队级两个固定模式——State（`task`）+ Strategy（`credit.deduct`）；模块内可自选第 3 个。

## 5. 跨模块通信契约

### 5.1 `XxxApi` 接口清单（同步调用，全部在 `<module>/api/` 子包，[03 骨架 §4.1](./03_包结构骨架.md) 强制）

| 接口 | 提供方 | 调用方典型场景 | 关键方法 |
| :--- | :--- | :--- | :--- |
| `CreditApi` | `credit` | task / trade 冻结-解冻-结算-扣减；search 信用分阈值；admin 仲裁强制结算 | `getScoreOf(userId)`、`freeze/unfreeze/settle(userId, points, bizKey)`、`deduct(userId, delta, reasonCode, bizKey)` |
| `UserApi` | `user` | task/im/trade 取 PublicUserVO；admin 取后台字段 | `getPublicUser(userId)`、`getMyProfile()` |
| `TaskApi` | `task` | search 大厅检索；report 取任务全流程；edu 复用底层任务 | `getTaskStatus(taskId)`、`getPublisherId(taskId)` |
| `TradeApi` | `trade` | report 取订单全流程 | `getOrderForAdmin(orderId)` |
| `ImApi` | `im` | report 一键引用聊天证据；admin 仲裁取双方私信 | `listMessagesForArbitration(caseId)`、`exportEvidenceSnippet(...)` |

> **强约束（INV-01）：** 跨模块依赖的目标**只能**是上述 `*Api` 或下述事件；**禁止**跨模块直接 `@Autowired` 他模块 `Repository`、`Service实现` 或 `Entity`。

### 5.2 应用事件清单（异步/同事务订阅，phase 严格区分）

> **核心约束（INV-04）：** 涉及**积分/信用**的副作用必须 `phase = BEFORE_COMMIT`，避免"先提交业务、再算账"留下漏洞窗口；纯通知性副作用统一 `AFTER_COMMIT + @Async`。

| 事件 | 发布方 | 订阅方 | phase | 副作用 |
| :--- | :--- | :--- | :--- | :--- |
| `TaskAcceptedEvent` | `task` | `credit.CreditTaskListener` | **BEFORE_COMMIT** | 冻结接单方押金（同事务回滚） |
|  |  | `im.TaskAcceptedImListener` | AFTER_COMMIT + @Async | 创建任务会话 + 推系统消息 |
|  |  | `notify.TaskEventListener` | AFTER_COMMIT + @Async | 写入站内信"已接单" |
| `TaskCompletedEvent` | `task` | `credit.CreditTaskListener` | **BEFORE_COMMIT** | 结算：解冻悬赏 + 转移给接单方 |
|  |  | `notify.TaskEventListener` | AFTER_COMMIT + @Async | 双方通知 |
| `TaskCanceledEvent` | `task` | `credit.CreditTaskListener` | **BEFORE_COMMIT** | 解冻悬赏 + 押金 |
| `TaskExpiredEvent` | `task` (scheduler) | `report.ReportServiceImpl` | AFTER_COMMIT | 进入仲裁队列 |
|  |  | `notify` | AFTER_COMMIT + @Async | 通知双方 + 接单者超时前 10 min 温柔提醒（独立 scheduler） |
| `UserVerifiedEvent` | `auth` (admin 审核通过后发) | `user.UserVerifiedEventListener` | AFTER_COMMIT + @Async | 刷新 `verify_status` 缓存、设置"校园已认证"标签 |
|  |  | `notify` | AFTER_COMMIT + @Async | 推送通知 |
| `ReportSubmittedEvent` | `report` | `notify.ReportEventListener` | AFTER_COMMIT + @Async | 通知管理员仲裁队列有新案件 |
| `BadReviewSettledEvent` | `report`（仲裁结果） | `credit.BadReviewEventListener` | **BEFORE_COMMIT** | 申诉成功 → 回滚扣分；申诉失败 → 维持 |

**实现规约：**
- 所有 BEFORE_COMMIT Listener 必须**显式注解** `@TransactionalEventListener(phase = BEFORE_COMMIT)`，**不能**省略 phase 参数（Spring 默认是 AFTER_COMMIT —— 见 [P2 AI 反思日志 §3.2 问题 2](../P2/AI协作反思日志_P2.md)）。
- 所有 BEFORE_COMMIT Listener 抛业务异常 → 当前事务整体回滚。
- AFTER_COMMIT 监听必须 `@Async` 跑独立线程池，避免阻塞主事务提交。

## 6. 设计模式应用

> **总览：** 团队级两个 GoF 模式（State + Strategy）+ Spring `ApplicationEvent` 作为 Observer 语义补充，符合 [01 统一规约 §5](./01_统一规约.md) 与 P3-详细设计 §1.3 "至少 2 种"的硬性要求。详尽论述见 [05 SOLID 与设计模式 §5](./05_SOLID检查清单与设计模式.md#5-设计模式应用至少-2-种)。

### 6.1 State 模式 — `task` 模块状态机

- **状态类**：`TaskState`（接口）+ 6 个具体状态（PendingAccept/InProgress/WaitConfirm/Completed/Canceled/Expired），`TaskStateContext` 持有当前状态并委托转移。
- **类图**：见 [04 §3.2](./04_核心类图.md#32-task含-state-模式与事件)。
- **为什么用**：任务状态 6 种 + 复杂跳转（US-19 超时 / US-01.5 待接单可编辑 / US-19.5 延长截止时间），若用 `switch(status)` 长链会污染 `TaskServiceImpl` 主干，违反 OCP；并且乐观锁 + 同事务积分联动场景下，状态方法集中抛业务异常更易于触发回滚。
- **不用会怎样**：每加一个状态（如未来"协商中"）就要修改 `TaskServiceImpl` 中所有动作方法的 if/else，review 难以覆盖全部组合，状态遗漏校验是高概率事故。

### 6.2 Strategy 模式 — `credit.deduct(reasonCode)`

- **策略接口**：`DeductStrategy`（`supports(reasonCode)` + `apply(account, delta, ctx)`），具体实现 `SevereViolationDeductStrategy` / `TaskNoShowDeductStrategy` / `AppealFailedDeductStrategy` / `BadReviewDeductStrategy`（按 P1 FR-CRED-01 的扣分清单实现）。
- **注册器**：`DeductStrategyRegistry`（容器注入 `List<DeductStrategy>` 或 EnumMap 工厂）。
- **类图**：见 [04 §3.5](./04_核心类图.md#35-credit含-strategy-与监听)。
- **为什么用**：信用规则是 P2 § 1.1 的核心硬约束，且**可能频繁调整**（新增"违禁词触发扣分"等），Strategy 让规则隔离、新增原因码只需加实现 + 注册即可。
- **不用会怎样**：`CreditServiceImpl.deduct()` 内无限 `if-else`，一次新增原因可能误改其他分支的幂等键或流水类型，测试组合爆炸。

### 6.3 Observer（Spring `ApplicationEvent`）—— 跨模块解耦

详见 §5.2 事件契约表。属于"基础设施级"模式，未计入"团队级两个 GoF 模式"的指标，但承担了**模块化单体下跨模块异步解耦**的全部职责（替代外部 MQ，详见 [P2 ADR-002](../P2/ADR.md)）。

## 8. 关键设计决策回顾

> 仅摘要本期产生的两个**规约级 / 实现选型**决策，详见 [决策记录.md](./决策记录.md) 的四段论（初稿 → 反方 → 推翻 → 教训）。

### 8.1 D3-01：状态枚举存储用 `TINYINT`，不用 `VARCHAR`

- 初稿规约一度禁用 `TINYINT`，组长 review 后拆穿三条理由全部站不住脚 → 改为强制 `TINYINT + @Convert`，严禁 `@Enumerated(EnumType.ORDINAL)`。
- **教训：「强约束」的每一条论据都必须经得起 challenge，否则破窗效应会拖垮整本规约。**

### 8.2 D3-02：密码 + 验证码组合，回归 P1 SRS 原意

- P2 ADR-003 把"禁外部身份系统（SSO/OAuth/CAS）"**过度泛化**为"完全不要密码"，P3 §3.6 继承了该错误。
- P3 review 时回查 P1 SRS 发现 FR-AUTH-01 原文要求"手机号 + 短信验证码 + 登录密码（首次注册时设置）"。
- 修订方案：**密码为主，验证码辅助**（登录用密码，注册/改密用验证码）；显式排除新设备识别、异地登录、管理端双因子（理由见决策记录）。
- **教训：AI 在执行「严禁 X」类强约束时极易把 X 外延悄悄扩大；写规约时每条"严禁"必须显式列出**覆盖边界 + 反例**。**

## 9. 隐私与安全

### 9.1 数据存储（与 §2.1 第 3 条对齐）

| 字段 | 落库方式 | 算法 / 备注 |
| :--- | :--- | :--- |
| `phone` | `phone_hmac` (CHAR(64)) + `phone_cipher` (VARBINARY) | HMAC-SHA256 用于登录等值；AES-256-GCM 仅用于审计回放；**不存明文列** |
| `password` | `auth_user.password_hash` | BCrypt cost=10；永不打日志、永不出 API |
| `real_name / student_no / id_card` | `auth_verification` 密文字段 | AES-256-GCM；业务表禁冗余 |
| 证件图片 | MinIO（对象存储） | DB 只存 SHA-256 + URL；30 日后自动删原图 |

### 9.2 API 输出（强约束）

- **PublicUserVO**（[01 §2.6](./01_统一规约.md)）：所有用户信息出口必须使用，仅含 `userId / nickname / avatarUrl / verifiedTag`。
- **隐私黑名单**（[01 §2.7](./01_统一规约.md)）：`realName / studentNo / idCardNo` 前台 API 永禁；`phone` 必须脱敏 `138****1234`。
- INV-03：Controller 出参禁 Entity，全部用 VO；JPA `@JsonIgnore` 双保险。

### 9.3 登录安全

- JWT：Access 30 min / Refresh 7 d；ISO 8601 时间。
- 防爆破（[01 §2.5.3](./01_统一规约.md)）：单账号 5 次错 → 锁 15 min；单 IP 1 h 内 20 次失败 → 锁 1 h；锁定期内即使密码正确也返回 `403 ACCOUNT_LOCKED`。
- 计数存 Redis（未启用降级 DB）。

### 9.4 日志脱敏（INV-06，[P2 ADR-004](../P2/ADR.md)）

业务日志统一用**脱敏 DTO** 打印；禁用 `entity.toString()` 直接进 `@Slf4j`；异常堆栈对密码字段单独过滤。这部分将在 P4 由 AOP + Logback Pattern 落地。
