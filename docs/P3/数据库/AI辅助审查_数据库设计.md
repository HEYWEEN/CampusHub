# AI 辅助审查：数据库设计（对应《P3-详细设计》任务 3.3）

> 审查对象：`docs/P3/数据库/schema.sql`、`索引说明.md`  
> 对照：`01_统一规约.md` §3  

## 1. 第三范式（3NF）

| 结论 | 说明 |
| :--- | :--- |
| **整体满足 3NF** | 各表主键为单一代理键 `id`；非主属性对主键无传递依赖。用户展示字段集中在 `user_profile`，认证敏感字段集中在 `auth_verification`，任务事实集中在 `task`，符合 **单事实来源**。 |
| **可接受的结构化冗余** | `trade_order` 同时存 `buyer_id` 与 `seller_id`：避免每次列表 JOIN `trade_item` 才能判断对手方，属典型 **刻意反规范化**，当前数据量下可接受；若订单状态机复杂化，可再评估是否拆 `trade_order_participant` 以消除角色冗余。 |
| **不宜再拆的边界** | `task_review` 与 `task` 分离而非嵌入 `task` 宽表：评价有独立生命周期与唯一约束 `(task_id, reviewer_id)`，拆表更清晰，符合 3NF。 |

## 2. 索引设计合理性

| 维度 | 评估 |
| :--- | :--- |
| 逻辑外键 | `publisher_id`、`assignee_id`、`user_id`、`task_id` 等均已建索引，满足 §3.5 自查清单。 |
| 联合索引列序 | `task(status, deadline_at)` 将高选择性状态放前、时间范围扫描在后，适配「大厅筛选 + 超时扫描」两类查询；若线上以 `created_at` 倒序为主且 `status` 过滤极宽，可用 `EXPLAIN` 验证是否需 `(created_at)` 覆盖索引调优。 |
| 低选择性列 | 单独 `credit_score` 索引在超大规模用户下收益有限；已备注「以搜索宽表/缓存为主」，避免过度索引写放大。 |
| 唯一索引 | `phone_hmac`、`credit_record.biz_id`、`task_review(task_id, reviewer_id)` 支撑幂等与防重复评价，设计合理。 |

## 3. 潜在性能瓶颈与缓解

| 风险 | 说明 | 缓解建议 |
| :--- | :--- | :--- |
| 任务大厅复杂筛选 | 多条件 + 排序 + 分页对 `task` 单表压力大 | 按 P2 由 **search 模块** 维护宽表或 ES；MySQL 索引作为过渡；热点读可加缓存 TTL 30–60s（注意与接单写一致性）。 |
| `nickname` 索引 | 非唯一文本 btree，并发写入与模糊搜索成本高 | 产品若强依赖昵称搜，建议迁 **全文/搜索引擎**；MySQL 仅保留精确/前缀场景。 |
| 加密手机号登录 | 等值查询依赖 `phone_hmac`，需保证 **规范化规则** 与 **HMAC 密钥** 轮换策略一致 | 密钥放 KMS/环境变量；轮换时双写或重算哈希窗口。 |
| 乐观锁高频冲突 | 抢单热点任务 `version` 冲突导致重试风暴 | 应用层指数退避 + 限流；极端热点可引入队列串行化（实现期再论证）。 |
| 软删除 | 大量 `deleted_at IS NULL` 条件若未进索引可能导致扫描 | 列表 SQL 统一带 `deleted_at` 条件并将该列纳入联合索引末尾（见 `索引说明.md` §1）。 |

## 4. 隐私与合规（与 3.2 交叉核对）

- 密码仅存 BCrypt；手机号不以明文列落库。  
- 证件与真实姓名仅存 `auth_verification` 密文，符合「业务表禁冗余」。  

## 5. 审查结论

当前 DDL 在 **范式、索引主路径、跨模块 FK 禁令** 上与团队规约一致；主要性能风险集中在 **搜索与热点抢单**，应在实现阶段配合 **search 模块与缓存策略** 验证，而非仅靠加索引解决。
