## D3-01：状态枚举存储采用 TINYINT，不用 VARCHAR

### 状态
**已接受**（2026-05-12，组长 heyween 决议）

### 初稿（被推翻）
《01_统一规约.md》§3.4 第一版规定：
- 枚举存储用 `VARCHAR(32)` + Java enum 字符串映射
- 明文**禁止** `TINYINT`，给出的理由是「可读性差，跨模块对齐成本高」

### 复议触发
组长在 review 规约时质疑该禁令的论据强度。逐条拆解后发现三个理由全部站不住脚：

| 初稿理由 | 拆穿 |
| :--- | :--- |
| "SQL log 直读语义" | 日常开发看的是 ORM 翻译后的 Java enum；DBA 直读 raw SQL 是低频场景；DataGrip / 字典视图都能解决 |
| "跨模块对齐成本" | **逻辑错误**。跨模块对齐靠**类型系统**（`TaskStatus` vs `TradeStatus` 是不同 Java 类型），不靠 DB 列类型。`task.status='COMPLETED'` 和 `trade.status='COMPLETED'` 同样是不同语义，VARCHAR 不提供任何额外保护 |
| "评审效率" | PR 评审看类图 / API / Java 代码，不看 DDL 截图。属于凑出来的理由 |

### 最终决策

1. **列类型**：状态/类型枚举字段统一 `TINYINT NOT NULL`
2. **JPA 映射**：强制 `@Convert(converter = XxxStatusConverter.class)`，**严禁** `@Enumerated(EnumType.ORDINAL)`
3. **统一基类**：`common/enums/BaseEnum` 提供 `getCode() / getDesc()` 接口和通用 converter 工厂
4. **代码约束**：业务代码内禁止状态裸数字字面量（`status == 1` 必须改成 `status == TaskStatus.IN_PROGRESS`）

### 选择 TINYINT 的真实理由（强论据）

1. **与《阿里巴巴 Java 开发手册》MySQL 规约一致** —— 工业标准，不需要每次都解释
2. **改名零成本** —— `PENDING_ACCEPT` 改成 `WAIT_ACCEPT`，只动 Java，DB 一行不用迁
3. **索引更紧凑** —— 状态字段必建索引，1B vs 平均 10B 在大表上是真实差异
4. **杜绝字符串脏数据** —— 避免 `'completed'` / `'COMPLETED'` / `'Completed'` 三种写法并存
5. **与《03_包结构骨架.md》中已存在的 `BaseEnum.java` 一致** —— 消除文档内部矛盾（BaseEnum 是 TINYINT 方案的标志性产物，STRING 直存根本不需要基类）

### VARCHAR 仅有的硬理由（已用其他方式覆盖）

VARCHAR 方案真正能 defend 的只有一条：**规避 `@Enumerated(EnumType.ORDINAL)` 的历史事故**（枚举声明顺序变动导致历史数据错位）。

本决策通过「强制 `@Convert` + ArchUnit 静态检查禁止 `@Enumerated(ORDINAL)`」覆盖该风险，不需要拿列类型来兜底。

### 反向风险与缓解

| 风险 | 缓解措施 |
| :--- | :--- |
| 团队成员误用 `@Enumerated(EnumType.ORDINAL)` → 新增枚举值时历史数据错位 | ArchUnit 规则：`@Entity` 字段禁止出现 `@Enumerated`，只允许 `@Convert`；CI 阶段直接打回 |
| DBA 直读 SQL log 时数字含义不直观 | 三道防线：① enum 内 `getDesc()` 提供中文描述；② DataGrip 列注释；③ 必要时 P4 提供 `v_xxx_with_status_desc` 视图 |
| 跨模块 review 时数字"难认" | 严格 review 时不允许出现裸数字字面量；ArchUnit 规则禁止 `status == <int_literal>` 模式 |
| 新成员上手时不熟悉 converter 写法 | `common/enums/BaseEnum` 提供模板；规约 §1.1 已规定 `enums` 包位置；P4 阶段每个状态枚举有一份参考实现 |

### 同步修改

- ✅ `01_统一规约.md` §3.4 表格 + 禁令段（已改）
- ✅ `03_包结构骨架.md` `common/enums/BaseEnum.java` —— 命名已符合新方案，无需调整
- ⏳ P4 编码阶段：在 `archunit` 测试包中加入对应规则
- ⏳ `AI协作反思日志_P3.md`：记录"AI 初稿偏向 DDD 惯例 → 人工 challenge 后回到 MySQL 工业实践"的案例

### 教训（讲故事 / 答辩用）

**核心教训：「强约束」的每一条论据都必须经得住 challenge，否则会产生破窗效应。**

原规约把「**惰性最优**」（VARCHAR + JPA 默认 `EnumType.STRING` 省事）包装成「**技术铁律**」（禁止 TINYINT）。表面上规约更"严"，实际上：

- 论据弱 → reviewer 一旦认真问就崩
- 一条强约束被发现是凑出来的 → 全员会默默怀疑其他强约束的可信度
- 整本规约的权威性下滑

**写规约时必须区分三档语气：**

| 语气 | 含义 | 示例 |
| :--- | :--- | :--- |
| **强制** | 违反则技术上必爆 / 安全合规违规 | 跨模块禁止 FK；隐私字段禁出前台 |
| **推荐** | 团队约定，论据可讨论 | 优先组合优先继承 |
| **示例做法** | 仅供参考，无强制力 | 文件目录命名建议 |

**初稿把"推荐"伪装成"强制"是这次问题的根因。**

## D3-02：鉴权方案引入密码，回归 P1 SRS 原意

### 状态
**已接受**（2026-05-12，组长 heyween 决议；同步修订 P2 ADR-003）

### 初稿（被推翻）

**两层错误叠加：**

| 阶段 | 文档 | 错误内容 |
| :--- | :--- | :--- |
| P2 | `P2/ADR.md` ADR-003 | 鉴权"仅用短信验证码"，**不存密码** |
| P3 | `P3/01_统一规约.md` §3.6 | `password_hash`「不存（无密码登录）」，理由「我们用短信验证码」 |

### 复议触发：发现 P1 → P2 偏离

2026-05-12 与 Claude 讨论 §3.6 隐私字段时，用户提出"我们还是需要密码"。回查 P1 SRS 后发现：

| 文档 | 行号 | 原文 |
| :--- | :--- | :--- |
| `P1/软件需求规格说明书.md` FR-AUTH-01 | 行 89 | **"输入：手机号码、短信验证码、登录密码（首次注册时设置）"** |
| `P1/需求分析.md` NFR-SEC-02 | 行 626 | **"密码、支付凭证、身份令牌等敏感信息不得明文存储"** |

**结论：P2 ADR-003 偏离了 P1 SRS**，且 P3 §3.6 继承了该错误。这不是 P3 阶段拍脑袋加密码，而是 P3 做规约 review 时**回归到 P1 的原意**。

### 偏离的根因（教训关键点）

P2 阶段 ADR-003 锁死了「**严禁 SSO / OAuth / CAS**」这条强约束。AI 在生成 ADR 时把这条约束**过度泛化**：
- 强约束本意："不引入**外部**身份系统"
- 被 AI 泛化为："**完全不要密码**"

团队 P2 阶段 review 时未察觉该泛化——因为"只用验证码"听起来也很合理（确实有 App 这么做），且与"严禁外部登录"在表面上一致。

**这是典型的 AI 强约束泛化误差。**

### 子决策 1：密码 vs 验证码的关系

**最终方案：密码为主，验证码辅助**（接近 P1 原意，也是淘宝、知乎等主流 App 的做法）

| 场景 | 凭据 |
| :--- | :--- |
| 学生端日常登录 | 手机号 + 密码 |
| 首次注册 | 手机号 + 短信验证码 → 设置初始密码 |
| 忘记密码重置 | 手机号 + 短信验证码 → 重置密码 |
| 改密码 / 改手机号（敏感操作） | 旧密码 + 短信验证码 |
| 管理端 `/api/admin/**` 日常登录 | 管理员账号 + 密码（与学生端对称） |
| 管理端账号创建 / 密码重置 | 由组长 DB 直接操作（不开放注册流程） |

**讨论过的其他方案：**
- 验证码为主 + 密码备用：体验略好，但与 P1 SRS"首次注册设置密码"的措辞不贴合
- 全员双因子：管理端体验差、学生端更差
- 学生端单因子 + 管理端双因子：曾被定为初版方案（见下方「二次收敛」），但当天进一步评估后取消

#### ※ 二次收敛 2026-05-12（管理端取消双因子）

初版子决策 1 给管理端定的是"密码 + 验证码双因子强制"。同日二次评估后**取消该双因子要求**，理由：

| 论据 | 内容 |
| :--- | :--- |
| 账号数极少 | `admin_user` 仅 5-10 个，由组长 DB 直接托管创建，不开放注册流程 |
| 验证码渠道不自然 | 管理员不一定愿意绑定个人手机号到 `admin_user` 表，且会增加一条隐私字段 |
| 不对称带来认知负担 | 学生端单因子、管理端双因子 → API 文档、前端登录组件、错误码都要分两套 |
| 失窃风险已分层 | 即使管理员密码被盗，`@PreAuthorize` + 操作审计日志（INV-05 + admin 模块日志）仍是有效防线 |
| 「严禁过度设计」是 P2 的元规约 | 双因子是为高安全场景设计的；校园助手平台的管理端不在此列 |

**收敛后管理端等效于"内部后台系统"模型**：账号由组织托管、不开放注册、依赖密码 + 权限模型 + 审计。与学生端登录方式对称，运维和代码都简化。

**这次二次收敛本身也是一个 D3-02 内部的小教训：** 第一轮决策容易在"安全性"维度过度加码，需要立即问一句"这个维度的加码是否会被其他防线（权限模型、审计日志）覆盖"。如果是，就该砍掉。

### 子决策 2：是否做新设备识别 / 异地登录

**最终方案：都不做。**

| 能力 | 技术可行性 | 工时 | 决策 | 理由 |
| :--- | :--- | :--- | :--- | :--- |
| 新设备识别（device_id cookie / LocalStorage UUID） | ✅ 可行 | 0.5 天 | ❌ **不做** | CampusHub 规模（2000 并发 / 校园场景）不足以让此投入产生明显安全收益 |
| 异地识别（IP + GeoIP，如 ip2region 离线库） | ✅ 可行 | 0.5 天 | ❌ **不做** | 校园场景误报率高：学生在宿舍 WiFi / 4G / 5G / 校园网间频繁切换 + 校园 NAT 出口在异地机房 → 用户会被反复弹验证码 |
| 行为风控 / ML 异常检测（淘宝/百度做法） | ❌ 不可行 | — | ❌ **不做** | 能力不足 |

**做半残的 GeoIP 比不做还差** —— 用户会把它视为 bug 而不是安全特性。

### 子决策 3：密码存储与防爆破

| 维度 | 决策 | 备注 |
| :--- | :--- | :--- |
| 算法 | BCrypt cost=10 | Spring Security 默认；cost 因子未来可调 |
| 强度 | 8–32 字符，含字母 + 数字 | 不强制特殊符号（学生场景平衡可用性） |
| 永不打日志 | `toString` 排除、`@Slf4j` debug 禁、异常堆栈脱敏 | 三道防线 |
| 永不出 API | DTO/VO 转换强制（INV-03） + `@JsonIgnore` 双保险 | 与 ADR-004 一致 |
| 账号锁定 | 5 次密码错误 → 锁 15 分钟 | 计数存 Redis（未启用降级 DB） |
| IP 锁定 | 1 小时 20 次失败 → 锁 1 小时 | 同上 |

### 教训（讲故事 / 答辩用）

**核心教训：AI 在执行「严禁 X」这类强约束时，极易把 X 的外延悄悄扩大。**

| 强约束本意 | AI 泛化后的实际行为 |
| :--- | :--- |
| 不引入**外部**身份系统（SSO/OAuth/CAS） | **完全不要密码** |
| （类似的潜在风险）"不引入消息队列" | 可能被泛化为"不做任何异步" |
| "不做企业级 SLA" | 可能被泛化为"不做基本可用性保障" |

**这与 D3-01 是同一类问题的两种表现：**

| 决策 | AI 错误模式 | 人工介入点 |
| :--- | :--- | :--- |
| D3-01 | AI 顺着用户文档维护错误论据 | 用户 challenge"理由薄弱" |
| D3-02 | AI 把强约束过度泛化，团队 review 没察觉 | 跨阶段 review 时回查 P1 |

**共同启示：** 写规约时，每条「严禁」必须**显式列出覆盖边界 + 显式列出不在边界内的反例**。例如本次修订后的 ADR-003 末尾就明确写了：
- 严禁的：SSO / OAuth / CAS
- **不在严禁范围内的**：本平台自有的"密码 + 验证码"组合

**这种「显式反例」是阻止 AI 强约束泛化的最有效手段。**
