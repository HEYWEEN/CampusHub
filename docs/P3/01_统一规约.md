# P3 详细设计统一规约（Convention）

> **目的：** 4 人横向分工（类图 / API / ER+SQL / 整合）下，三视角必须咬合。本规约是**全员强约束**，PR 阶段任何违反必须被打回。
> **生效范围：** P3 详细设计阶段所有交付物（类图、API 文档、ER 图、建表 SQL、整合文档）。
> **来源：** P1 SRS / 用户故事 + P2 架构设计文档 + ADR-001~005。

---

## 0. 工具栈与文档格式（先定，避免 4 个人用 4 种工具）

| 交付物 | 推荐工具 | 文件格式 | 理由 |

## 1. Java 命名与编码规约

### 1.1 类名后缀（强制）

| 角色 | 后缀 | 示例 | 所在包 |
| :--- | :--- | :--- | :--- |
| Controller（HTTP 入口） | `Controller` | `TaskController` | `controller` |
| Service 接口 | `Service` | `TaskService` | `service` |
| Service 实现 | `ServiceImpl` | `TaskServiceImpl` | `service.impl`（或 `service` 同包） |
| Repository（JPA） | `Repository` | `TaskRepository` | `repository` |
| 实体 / DO | 无后缀（直接是名词） | `Task`, `User` | `entity` |
| 入参 DTO | `DTO` 或 `Req` | `TaskCreateDTO` | `dto` |
| 出参 VO | `VO` | `TaskDetailVO` | `vo` |
| 跨模块 API 接口 | `Api` | `CreditApi` | `api` |
| 应用事件 | `Event` | `TaskAcceptedEvent` | `event` |
| 业务异常 | `Exception` | `CreditNotEnoughException` | `exception` |
| 枚举 | 名词或 `Enum`（不强制） | `TaskStatus` | `entity` 或 `enums` |
| 配置类 | `Config` | `JwtConfig` | `config` |

**禁止：**
- `Manager` / `Helper` / `Util` 后缀（除非真的是工具类放在 `common.util`）
- 一个类承担多角色（如 `TaskUtil` 里又有业务逻辑又有静态方法）

### 1.2 包路径规约

```
com.campushub.<module>.{api, controller, service, repository, entity, dto, vo, event, exception}
com.campushub.common.{response, exception, util, enums}
com.campushub.config
```

每个业务模块（11 个）必须有完全相同的子包结构（具体见 `03_包结构骨架.md`）。

### 1.3 字段与方法

- Java 字段：`camelCase`（`createdAt`, `taskId`）
- 数据库字段：`snake_case`（`created_at`, `task_id`），通过 JPA `@Column(name="...")` 或 MyBatis 配置自动映射
- 常量：`UPPER_SNAKE_CASE`
- 方法名：动词开头（`createTask`, `findByPhone`, `getScoreOf`）

## 2. API 全局公共契约（最容易撞车，必须钉死）

### 2.1 路径与方法

| 维度 | 规约 |
| :--- | :--- |
| 学生端前缀 | `/api/<module>/...`，例：`/api/tasks`、`/api/credits/me` |
| 管理端前缀 | `/api/admin/<module>/...`，例：`/api/admin/auth/verifications` |
| HTTP 方法 | `POST` 创建/动作；`GET` 查询；`PATCH` 局部更新；`PUT` 全量替换（少用）；`DELETE` 软删除 |
| 资源命名 | 复数（`/tasks`、`/users`），id 用路径参数（`/tasks/{taskId}`） |
| 动作型路径 | 资源后挂动词（`/tasks/{id}/accept`、`/tasks/{id}/complete-proof`），仅用于"非 CRUD"业务动作 |

### 2.2 统一响应包装（强制，全部 API 适用）

```json
{
  "code": 0,
  "message": "ok",
  "data": { /* 实际业务数据；无数据时为 null 或 {} */ },
  "traceId": "9f3c2a..."
}
```

- `code = 0` 表示成功；非 0 为业务错误码
- HTTP 状态码与 `code` **不互斥**：HTTP 4xx/5xx 同时存在，便于前端做粗筛
- `traceId` 由网关或 Spring 拦截器统一注入，便于日志关联

### 2.3 分页格式（强制）

**入参：**
```
GET /api/tasks?page=1&size=20&sort=createdAt,desc
```

**出参：**
```json
{
  "code": 0,
  "data": {
    "items": [ /* 元素列表 */ ],
    "total": 156,
    "page": 1,
    "size": 20
  }
}
```

- `page` 从 1 开始（非 0）
- `size` 默认 20，最大 100
- 排序参数 `sort=field,asc|desc`，多字段用逗号分隔

### 2.4 错误码格式

- 业务码：`UPPER_SNAKE_CASE`，前缀按模块（如 `TASK_ALREADY_ACCEPTED`、`CREDIT_NOT_ENOUGH`）
- 数值码：4 位整数，分段：`1xxx` 通用 / `2xxx` auth / `3xxx` user / `4xxx` task / `5xxx` trade / `6xxx` edu / `7xxx` team / `8xxx` im / `9xxx` notify / `10xxx` credit / `11xxx` report / `12xxx` admin / `13xxx` search

| HTTP | 业务语义 | 典型场景 |
| :--- | :--- | :--- |
| 400 | 参数错误 | 字段缺失、格式错误 |
| 401 | 未登录 | JWT 无效或过期 |
| 403 | 无权限 | 信用分不足、未认证、非管理员 |
| 404 | 资源不存在 | 任务/用户找不到 |
| 409 | 状态冲突 | 乐观锁失败、重复操作、状态机非法跳转 |
| 422 | 业务规则不满足 | 申诉超过 7 日 / 3 次 |
| 429 | 限流 | 短信验证码频次 |
| 500 | 服务端异常 | 兜底，禁止用于已知业务错误 |

### 2.5 鉴权与时间

- 鉴权头：`Authorization: Bearer <jwt>`
- JWT 有效期 7200 秒（2h），刷新策略见 ADR-003
- 时间字段统一 ISO 8601：`2026-05-17T23:59:59+08:00`
- 后端用 `LocalDateTime` 存储；JSON 序列化用 Jackson `@JsonFormat`

### 2.6 公开用户对象（PublicUserVO，强制）

```json
{
  "userId": 123456,
  "nickname": "校园路人甲",
  "avatarUrl": "https://oss.example.com/avatars/...",
  "verifiedTag": true
}
```

**强制：** 所有返回"用户信息"的接口必须使用此 VO，不得返回 Entity 或扩展字段。

### 2.7 隐私字段黑名单（强制，前台 API 永禁出现）

| 字段 | 处理 |
| :--- | :--- |
| `realName` | 前台禁出；仅 `/api/admin/**` 允许 |
| `studentNo` | 同上 |
| `idCardNo` | 同上 |
| `phone` | 必须脱敏：`138****1234` |

## 3. 数据建模公约

### 3.1 通用审计字段（每张表强制带）

```sql
id           BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
-- 可选（按需）
version      INT          NOT NULL DEFAULT 0,        -- 乐观锁，存在并发改的表必加
deleted_at   DATETIME     NULL,                       -- 软删除，存在删除场景的表必加
creator_id   BIGINT       NULL,                       -- 业务创建者 user_id
updater_id   BIGINT       NULL                        -- 最近更新者 user_id
```

### 3.2 主键策略

- **统一使用 `BIGINT AUTO_INCREMENT`**（不引入雪花算法）
- Java 类型 `Long`
- 理由：单库单实例，无需分布式 ID；雪花算法引入运维复杂度违反 ADR-001

### 3.3 跨模块外键禁令（强约束）

> **来自 P2 § 2 不变量第 2 条：业务表归属唯一。**

- **禁止**在表级别使用 `FOREIGN KEY` 约束跨越模块前缀（如 `task_*` 表禁止 FK 指向 `user_*`）
- 跨模块关联只能用**逻辑外键**（`user_id BIGINT`），不加 DB 约束
- 模块内表（同前缀）允许 FK
- 跨模块查询走 `XxxApi` 接口

### 3.4 命名

| 对象 | 规约 | 示例 |
| :--- | :--- | :--- |
| 表名 | `<module>_<entity>`，全小写下划线 | `task_order`, `credit_account` |
| 字段名 | snake_case | `created_at`, `reward_point` |
| 普通索引 | `idx_<table>_<col1>_<col2>` | `idx_task_order_status_deadline` |
| 唯一索引 | `uk_<table>_<col>` | `uk_auth_user_phone` |
| 枚举存储 | **`VARCHAR(32)`** + Java enum 字符串映射 | `status VARCHAR(32) NOT NULL` |
| 字符集 | 全库 `utf8mb4` + `utf8mb4_0900_ai_ci` | — |

**禁止：** 用 `TINYINT` 存状态枚举（可读性差，跨模块对齐成本高）。

### 3.5 必建索引清单（每张表自查）

- 所有逻辑外键字段（`user_id`, `task_id` 等）
- 所有作为查询条件的字段（`status`, `category`）
- 排序字段（通常是 `created_at`）
- 唯一性字段（`phone`, `student_no` 在 auth 表）
- 软删除查询：`deleted_at` 列上建索引或在所有索引最右侧加 `deleted_at`（视查询模式）

### 3.6 隐私字段处理

| 字段 | 存储方式 | 加密算法 | 说明 |
| :--- | :--- | :--- | :--- |
| `phone` | 明文存储 + 列加密 | AES-256-GCM | 登录需精确匹配，加密时使用确定性加密或 hash 索引 |
| `real_name` | 仅 `auth_verification` 表 | AES-256-GCM | 业务表禁冗余 |
| `student_no` | 同上 | AES-256-GCM | 同上 |
| `password_hash` | 不存（无密码登录） | — | 我们用短信验证码 |
| 证件图片 | MinIO 存储；DB 只存 SHA-256 + URL | — | 30 日后自动删除原图（ADR-003） |

### 3.7 积分与信用分

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `point_balance` | `INT NOT NULL DEFAULT 0` | 可用积分 |
| `point_frozen` | `INT NOT NULL DEFAULT 0` | 冻结积分 |
| `credit_score` | `INT NOT NULL DEFAULT 100` | 信用分（0~120） |

**禁止：** 用 `DECIMAL` 存积分（虚拟积分无小数语义）。

## 4. 类图颗粒度规约

### 4.1 必须出现的类

| 类型 | 是否必出 | 说明 |
| :--- | :---: | :--- |
| Entity | ✓ | 核心业务实体 |
| Service 接口 | ✓ | 对内 |
| ServiceImpl | △ | 仅当方法签名不同于接口时画 |
| Controller | ✓ | HTTP 入口 |
| Repository 接口 | ✓ | 仅画方法名，不画 JPA 派生方法的具体实现 |
| `XxxApi` 接口 | ✓ | 跨模块通信契约 |
| 关键 DTO / VO | ✓ | 仅画"承载契约语义"的那些（如 `TaskCreateDTO`），简单透传的可省略 |
| Event 类 | ✓ | 跨模块事件 |
| 业务异常 | △ | 自定义异常画即可，标准异常省略 |

### 4.2 必须省略的内容

- getter / setter（用 Lombok 注解 `@Data` 表达即可）
- Spring 注解（`@Autowired`、`@Service` 等）
- 私有 helper 方法
- 标准库继承关系（如 `extends Object`）

### 4.3 关系符号判断标准（最易出错）

| 关系 | UML 符号 | 判断标准 | 示例 |
| :--- | :--- | :--- | :--- |
| 关联（Association） | 实线箭头 | A 用到 B 的方法或属性 | `TaskService → CreditApi` |
| 聚合（Aggregation） | 空心菱形 | "A has B"，B 独立存在 | `Team ◇ User` |
| 组合（Composition） | 实心菱形 | "A 没了 B 也没了" | `Task ◆ TaskAttachment` |
| 继承（Inheritance） | 空心三角 | 真正的 IS-A 关系 | `AdminUser ▷ User` |
| 实现（Implementation） | 虚线三角 | 实现接口 | `TaskServiceImpl ▷-- TaskService` |
| 依赖（Dependency） | 虚线箭头 | A 临时使用 B（参数/局部变量） | `TaskController ⇢ TaskCreateDTO` |

**默认偏好：** 组合优先继承；除非真正 IS-A，否则不要画继承。

### 4.4 类图覆盖范围

P3 阶段类图至少覆盖以下 5 类核心场景：
1. **鉴权与认证流程**（auth + user）
2. **任务发布—接单—完成—结算**（task + credit + im + notify）
3. **二手交易**（trade + credit + im）
4. **课程评价 + 学习资料 + 辅导任务**（edu + task）
5. **差评申诉—管理员仲裁**（report + credit + admin + notify）

每个场景一张图，不要全部画在一张总图（不可读）。

## 5. 设计模式预选（团队级，不可改）

> ⚠️ **常见误解：** 让 4 个人各自找地方塞模式 → 撞车 / 重复 / 不一致。
> 团队**预先选定 2 个全局模式**，模块内可再自由选。

### 5.1 模式 1：State 模式 — 任务状态机

**用在：** `task` 模块的状态流转

**状态：** `PENDING_ACCEPT`（待接单）→ `IN_PROGRESS`（进行中）→ `WAIT_CONFIRM`（待确认）→ `COMPLETED`（已完成）/ `CANCELED`（已取消）/ `EXPIRED`（异常中止）

**为什么用：**
- P2 已明确 6 种状态 + 复杂跳转规则（US-19 超时流转、US-01.5 待接单可编辑）
- 不用 State 模式 → 必然出现巨型 `switch` 或 `if-else`，违反 OCP
- 新增状态（如未来"协商中"）只需加一个 State 类，不改老代码

**类骨架：**
```java
interface TaskState {
    void onAccept(TaskContext ctx);
    void onComplete(TaskContext ctx);
    void onCancel(TaskContext ctx);
    void onTimeout(TaskContext ctx);
}
class PendingAcceptState implements TaskState { ... }
class InProgressState implements TaskState { ... }
// ...
```

### 5.2 模式 2：Strategy 模式 — 信用分扣减规则

**用在：** `credit` 模块的扣分策略

**策略：** 按 `reasonCode` 分发不同扣分逻辑（任务违约 -5 / 差评 -5 / 仲裁严重违规 -30 / 申诉成功回滚 +5 ……）

**为什么用：**
- 信用规则是 P2 § 1.1 的核心硬约束（`< 80 限单 1 / < 60 禁发禁接`，实时生效）
- 规则可能频繁调整（如新增"违禁词触发"扣分）
- 不用 Strategy → `CreditService.deduct()` 内部硬编码 `if (reasonCode == ...)` 链路，改一次回归一次

**类骨架：**
```java
interface CreditDeductStrategy {
    int calculateDelta(DeductContext ctx);
    String reasonCode();
}
class TaskBreachStrategy implements CreditDeductStrategy { ... }    // -5
class BadReviewStrategy implements CreditDeductStrategy { ... }      // -5
class ArbitrationSevereStrategy implements CreditDeductStrategy { ... } // -30
// 用 Map<String, Strategy> 注入
```

### 5.3 第 3 个模式（可选，模块内自选）

如果 SOLID 检查中发现合适场景，团队成员可在自己模块内引入第 3 个模式（如观察者已被 `ApplicationEvent` 覆盖，可考虑工厂、模板方法、责任链等），并在文档中说明"为什么这里用"和"不用会怎样"。

## 6. 架构不变量（来自 P2 § 2，PR 必查）

| 编号 | 不变量 | 在 P3 的检查点 |
| :--- | :--- | :--- |
| INV-01 | 跨模块只走 `XxxApi` 或 `ApplicationEvent` | 类图中跨包关联必经接口；API 文档不应跨模块直引 Entity |
| INV-02 | 业务表归属唯一，无跨模块外键 | ER 图检查：FK 不跨前缀 |
| INV-03 | Controller 出参禁用 Entity | API 文档响应字段对照 VO 类 |
| INV-04 | 扣分/积分类 Listener 必须 `BEFORE_COMMIT` | 事件契约表中 phase 必填 |
| INV-05 | `/api/admin/**` 必须 `@PreAuthorize` | API 文档管理端接口标注 |
| INV-06 | 日志输出用脱敏 DTO | 类图中 `toString()` 重写要标注 |

## 7. AI 协作规约（统一 Prompt 风格）

### 7.1 三视角 AI Prompt 模板

**类图 Prompt：**
```
基于以下信息生成 PlantUML 类图：
- 业务模块：<module>
- 涉及功能：<F-XXX-NN 列表>
- 必须遵守：详见《P3 统一规约》§1（命名）、§4（类图颗粒度）、§5（设计模式）
请输出可直接渲染的 .puml 代码块。
```

**API Prompt：**
```
基于以下信息生成 OpenAPI 3.1 YAML：
- 业务模块：<module>
- 涉及功能：<F-XXX-NN 列表>
- 必须遵守：详见《P3 统一规约》§2（响应包装、分页、错误码、PublicUserVO、隐私黑名单）
请输出可直接导入 Swagger Editor 的 yaml。
```

**ER + SQL Prompt：**
```
基于以下信息生成 DBML 和 MySQL 8 DDL：
- 业务模块：<module>
- 涉及功能：<F-XXX-NN 列表>
- 必须遵守：详见《P3 统一规约》§3（审计字段、主键、跨模块外键禁令、命名、索引、隐私）
请同时输出 .dbml 和 .sql。
```

### 7.2 SOLID 注入实验流程

1. 第 10 周中：每个视角负责人**先用 AI 生成原始版**，原样保存为 `XX_ai_raw.md`（不改）
2. 团队会议：对照 P3-详细设计 § 1.2 检查表逐条审查
3. 修订后保存为 `XX_revised.md`，并在 SOLID 清单中记录每条违反 + 修正方案
4. **AI 反思日志统计：** 违反数、最严重问题、人工修改幅度

## 8. 工作流（推荐）

```
第 10 周
  D1   组长发布本规约 + 功能映射主表 + 包结构骨架（30 min 全员对齐会）
  D2-3 ER 图 + 建表 SQL（C 主导；A/B 同步看草稿）
  D4   交叉互审 1 轮：A/B 把 C 的字段映射回各自的类/API，发现冲突当天解决
  D5-6 类图（A 主导）+ API 文档（B 主导），并行
  D7   第 2 轮交叉互审：完整三视角对齐
第 11 周
  D8-9 SOLID 实验 + 设计模式应用文档化
  D10  整合（D 主导）
  D11  AI 反思日志 #3 + 提交
```

**关键检查点：** 每轮互审产出"冲突清单"，组长拍板。冲突点不解决 → 不允许进入下一阶段。
