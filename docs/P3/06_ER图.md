## 1. 核心 ER 图 (Entity-Relationship Diagram)

根据项目“跨模块无物理外键 (Foreign Key) 约束”的架构原则，数据库实际的物理外键仅存在于模块内部从表与主表之间（例如 `task` 与 `task_attachment`）。跨模块的关联（如 `task` 关联 `auth_user`）以逻辑外键处理。图中虚线表示逻辑外键，实线表示物理外键（或强所属关系）。

```mermaid
erDiagram
    %% ==========================================
    %% Auth 模块
    %% ==========================================
    AUTH_USER {
        BIGINT id PK
        CHAR(64) phone_hmac "HMAC加密手机号(登录索引)"
        VARBINARY(512) phone_cipher "AES加密手机号明文"
        VARCHAR(255) password_hash
        TINYINT verify_status "验证状态"
        TINYINT banned "是否封禁"
    }

    AUTH_VERIFICATION {
        BIGINT id PK
        BIGINT user_id FK "关联 auth_user"
        TINYINT status "审核状态"
        VARBINARY(512) real_name_cipher
        VARBINARY(512) student_no_cipher
        VARBINARY(512) id_card_cipher
    }

    AUTH_USER ||--o{ AUTH_VERIFICATION : "has (物理外键)"

    %% ==========================================
    %% User 模块
    %% ==========================================
    USER_PROFILE {
        BIGINT id PK
        BIGINT user_id "逻辑外键 -> auth_user.id"
        VARCHAR(64) nickname
        VARCHAR(512) avatar_url
        TINYINT hide_publish_hist
        TINYINT hide_accept_hist
    }

    AUTH_USER ||..|| USER_PROFILE : "1:1 (逻辑关联)"

    %% ==========================================
    %% Task 模块
    %% ==========================================
    TASK {
        BIGINT id PK
        BIGINT publisher_id "逻辑关联 user_profile"
        BIGINT assignee_id "逻辑关联 user_profile"
        VARCHAR(120) title
        TINYINT task_type "跑腿/互助/辅导"
        TINYINT status "状态机枚举"
        INT reward_point "悬赏积分"
        DATETIME deadline_at
    }

    TASK_ATTACHMENT {
        BIGINT id PK
        BIGINT task_id FK "关联 task"
        VARCHAR(512) url
        TINYINT kind "附件类型"
    }

    TASK_REVIEW {
        BIGINT id PK
        BIGINT task_id FK "关联 task"
        BIGINT reviewer_id
        BIGINT reviewee_id
        TINYINT rating "1-5星"
        VARCHAR(500) comment
    }

    USER_PROFILE ||..o{ TASK : "publishes (逻辑关联)"
    USER_PROFILE ||..o{ TASK : "accepts (逻辑关联)"
    TASK ||--o{ TASK_ATTACHMENT : "contains (物理外键)"
    TASK ||--o| TASK_REVIEW : "receives (物理外键)"

    %% ==========================================
    %% Credit 模块
    %% ==========================================
    CREDIT_ACCOUNT {
        BIGINT id PK
        BIGINT user_id "逻辑关联 user_profile"
        INT point_balance "积分余额"
        INT point_frozen "冻结积分"
    }

    CREDIT_FLOW {
        BIGINT id PK
        BIGINT account_id FK
        INT amount_change
        TINYINT flow_type "加分/扣分类型"
    }

    USER_PROFILE ||..|| CREDIT_ACCOUNT : "has (逻辑关联)"
    CREDIT_ACCOUNT ||--o{ CREDIT_FLOW : "records (物理外键)"
```

## 2. 设计规范说明

1. **隐私与加密原则（P1 硬性约束）：** 
   - 数据库严禁存储明文手机号、真实姓名和学号。
   - `auth_user` 表中的 `phone_hmac` 用于等值查询索引（登录匹配）。
   - 实名认证涉及数据在 `auth_verification` 表中以 `VARBINARY` 形式进行 AES-256 加密存储。
2. **逻辑外键（跨模块解耦）：** 
   - `user_profile.user_id` 和 `task.publisher_id` 为逻辑外键，数据库层面不建立强 FK 约束，保证服务隔离与可扩展性。
3. **资金安全化限制：** 
   - `credit_account` 和 `credit_flow` 仅使用整型（积分）字段，严禁出现代表真实法币金额的属性（如 BigDecimal/Money 类型）。
4. **主键与通用字段（统一规约）：**
   - 全部表统一使用 `BIGINT id AUTO_INCREMENT` 为主键。
   - 全部表隐藏了公共审计字段（`version`, `created_at`, `updated_at`, `deleted_at` 等，详见 `schema.sql`），保证绘图核心清晰。
