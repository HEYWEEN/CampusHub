## 2. AI 助力分析（Q1）

### 2.1 本阶段 AI 最大的贡献

1. **类图 / SQL / OpenAPI 骨架的一次成稿，节省最大宗工时。**
   - 类图 v0 虽然 80% 重画，但**这本身就是"AI 设计缺陷注入"实验的实验材料**——v0 提供了一份"看起来完整但违反纪律"的基线，让团队的 SOLID 检查表第一次有了真实靶子。如果没有 AI 出 v0，团队需要自己先画一份"故意有缺陷"的版本，工时反而更高。
   - OpenAPI YAML 与 schema.sql 的 60–70% 由 AI 一次成稿，剩下的是人工对齐统一规约（包装格式、错误码分段、审计字段、跨模块 FK 禁令）。

2. **作为"严苛 reviewer"的低成本红队。**
   - API 审查 / 数据库审查 / SOLID 检查三处都是把 Claude 切换到"reviewer 角色"做的，**比团队成员自己 review 更敢挑硬伤**。例如数据库 AI 审查里"乐观锁高频冲突 → 重试风暴"和"加密手机号登录的 HMAC 密钥轮换"这两个风险，是团队自己 review 不一定能想到的。

3. **强迫团队把"模糊判断"翻译成"具体规则"。**
   - 例如 D3-01 决策里，AI 第二轮主动列出"VARCHAR 真正能 defend 的只有 `@Enumerated(EnumType.ORDINAL)` 的历史事故"——把模糊的"觉得 VARCHAR 更稳"翻译成了具体的技术原因。这种"逼具体"的能力让决策记录的"反方论据"段落质量显著提升。

4. **生成统一规约配套表格的标准模板。**
   - 命名规约表、错误码分段表、必建索引清单、设计模式应用对照表——这些表格的字段抽取与对齐由 AI 处理，团队只需校对内容，省去重复劳动。

### 2.2 不同 Prompt 策略下 AI 回答质量的差异（延续 P2 框架，新增 P3 观察）

| 策略 | 对应使用场景 | 模型 | 输出质量观察 |
| :--- | :--- | :--- | :--- |
| **A：零上下文直接要求出图** | 类图 v0（实验材料） | Claude Opus 4.7 | **故意**用零上下文 → 得到一份违反 SOLID 的"教科书反例"，非常适合做实验 baseline |
| **B：详细约束注入** | 类图 v1、OpenAPI、schema.sql | Claude/ChatGPT/DeepSeek | 投喂统一规约后输出质量显著上升；但**仍会偷偷违反约束**（例如 schema.sql 默认建跨模块 FK，违反 INV-02） |
| **C：reviewer 角色 + 检查表** | API 审查、DB 审查、SOLID 检查 | Claude Opus 4.7 | **本阶段性价比最高的策略**：用 P2 反思 §4.2 的"角色 + 极简 Prompt"激活 AI 自我审查；产出比 B 更具批判性 |

## 3. AI 误导分析（Q2）

**SOLID 检查中发现的 AI 设计问题数量：6**

**最严重的设计问题是：跨模块直接依赖他模块 Repository（`TaskServiceImpl` 直接 `@Autowired CreditAccountRepository` 等），破坏信用域不变量与事务边界，同时违反 P2 INV-01。**

详细 6 条违规清单见 [05 §3](./05_SOLID检查清单与设计模式.md#3-solid-逐条检查清单对照-v0) 与 [§4](./05_SOLID检查清单与设计模式.md#4-违规统计与计数规则)。

### 3.1 P3 阶段新增的 AI 误导问题（不仅限于类图 SOLID）

#### 问题 1：AI 在"既有文档维护"与"真诚分析"之间默认偏向前者（D3-01）

- **如何发现**：组长 review 统一规约时，对"禁止 TINYINT，强制 VARCHAR"的三条理由提出"理由很薄弱"。
- **第一轮 AI 行为**：Claude 顺着既有规约维护 VARCHAR 方案，给出"看起来合理实则薄弱"的辩护理由（SQL log 直读语义、跨模块对齐成本、评审效率）。
- **第二轮 AI 行为（关键）**：用户挑战后，Claude 拆穿了自己第一轮的论据，转而支持 TINYINT，并列出 5 条强论据 + 1 条 VARCHAR 真正能 defend 的硬理由。
- **可迁移启示**：**AI 默认会保护用户的既有文档不被推翻**，这是一种"对齐税"——只要用户没有显式 challenge，AI 就会维持现状。这意味着团队 review 自己的文档时**必须主动设置"挑刺"语境**（例如 "请假设这条规约是错的，找出反对它的最强论据"），否则 AI 给不出真正的批判。

#### 问题 2：AI 在执行"严禁 X"类强约束时极易把 X 外延悄悄扩大（D3-02）

- **如何发现**：P3 review §3.6 隐私字段时，组长问"我们还是需要密码吧？"。回查 P1 SRS 后发现 FR-AUTH-01 明文要求"手机号 + 短信验证码 + 登录密码（首次注册时设置）"，但 P2 ADR-003 写了"仅用短信验证码，不存密码"。
- **AI 在 P2 阶段的偏差**：把"严禁 SSO/OAuth/CAS"过度泛化为"完全不要密码"——AI 没区分"外部身份系统"与"本平台自有的密码方案"。
- **如何修正**：D3-02 决策回归 P1 原意（密码为主 + 验证码辅助）；同步修订 ADR-003 + 统一规约 §2.5 + schema.sql `password_hash` 列。
- **可迁移启示**：**每条"严禁"必须显式列出"覆盖边界 + 反例"**。例如修订后的 ADR-003 末尾明确写：「严禁的：SSO / OAuth / CAS；**不在严禁范围内的**：本平台自有的"密码 + 验证码"组合。」这种"显式反例"是阻止 AI 强约束泛化的最有效手段。

#### 问题 3：AI 在 DDL 生成时默认建跨模块 FK（违反 INV-02）

- **如何发现**：DeepSeek-V4 第一版 schema.sql 在 `user_profile.user_id`、`task_order.publisher_id`、`credit_account.user_id` 上都加了 `FOREIGN KEY ... REFERENCES auth_user(id)`。
- **修正**：人工删掉所有跨前缀 FK，仅保留同模块内 FK（`task_attachment → task_order` 等）。
- **可迁移启示**：AI 在 SQL 输出时遵循"教科书最佳实践"（FK 越多越规范），而**模块化单体的核心反直觉之一就是"逻辑外键 + 应用层校验"**。这类"反直觉规约"必须在 Prompt 中**正面提及**（不要只说"遵守 §3.3"，要直接写"严禁跨表前缀 FOREIGN KEY"）。

#### 问题 4：AI 在 OpenAPI 生成时默认遗漏鉴权 + 限流（API/AI 辅助审查文档已记录）

- **如何发现**：ChatGPT-5.3 第一版 OpenAPI 在 `POST /api/tasks`、`POST /api/tasks/{taskId}/accept` 等敏感路径上未声明 `security: bearerAuth`；短信验证码接口缺 429 限流。
- **修正**：人工补 `security: bearerAuth`、429 响应、`AccountLocked`、`CreditOrPermission` 等响应模板。
- **可迁移启示**：AI 默认按 RESTful "happy path" 出接口，**安全维度需要在 Prompt 里显式列出检查项**（Bearer 鉴权、限流、错误码示例、隐私字段黑名单）。

#### 问题 5：AI 在 ER 图生成时默认与 SQL 不完全一致

- **如何发现**：D 整合阶段对账时发现 ER 图实体 `CREDIT_FLOW` 与 schema.sql 表 `credit_record` 不一致，缺 `trade_*` 实体，字段名也对不上。
- **修正**：D 在整合阶段重画 ER 图与 schema.sql 完全对齐；显式区分物理 FK / 逻辑外键连线样式。
- **可迁移启示**：AI 在"反向生成"时（从 SQL 出 ER）易丢失细节；**最稳的做法是把 SQL 与 ER 用同一份 Prompt 一次生成**，不要分两次。

### 3.2 系统性观察：P2 §3.2 的"AI 四类偏弱"在 P3 的延伸

| P2 已识别偏弱 | P3 新表现 |
| :--- | :--- |
| **隐性权重** | 类图 v0 默认把"完整性"权重打得很高（生成上帝服务覆盖一切），而"模块边界"权重打得很低 |
| **默认值方向** | `@TransactionalEventListener` phase 默认值仍是 AFTER_COMMIT，P3 类图描述中 AI 多次省略 phase 标注 → 仍需人工补 |
| **出口路径** | OpenAPI 默认不写日志脱敏侧的考量；schema.sql 默认不写"软删除如何参与索引" |
| **触发条件 / 工程纪律** | AI 在生成 ADR 后续条款时仍倾向"由开发自觉遵守"，不会主动写"ArchUnit 自动校验"——D3-01 决策里的 ArchUnit 规则是人工补充 |

**新增第五类偏弱：跨阶段一致性。** AI 在生成 P3 文档时不会主动回查 P1 SRS 是否被 P2 偏离——这是 D3-02 暴露出来的新维度。

### 4.2 P3 新增改进措施

针对 §3 暴露的 P3 阶段新问题，新增以下措施：

7. **"挑刺语境"作为文档 review Prompt 的固定开头**：
   - **依据**：见 §3.1 问题 1。
   - **下阶段执行**：在每次让 AI review 团队既有文档时，强制以下开头：
     ```
     请假设这份文档是错的，列出反对它的最强论据 3 条。
     不要急于维护现有结论；如果发现论据薄弱，请直接拆穿它。
     ```

8. **"严禁 X" 必须配套"反例清单"**：
   - **依据**：见 §3.1 问题 2。
   - **下阶段执行**：每条"严禁 X"的 ADR / 规约条款 Prompt 必须追加：
     ```
     除了写"严禁 X"，还请显式列出：
     1. 严禁的边界（哪些情形算 X）；
     2. 不在严禁范围内的反例（哪些类似但不算 X）。
     ```

9. **"反直觉规约"必须在 Prompt 中正面提及**：
   - **依据**：见 §3.1 问题 3。
   - **下阶段执行**：在生成 DDL / 类图 / 架构图前，强制列出"本项目反直觉规约清单"（如"跨模块禁 FK"、"BEFORE_COMMIT 必须显式"），不要假设 AI 会自己从规约文档推断。

10. **"SQL ↔ ER ↔ Java 实体"一次生成 + 一次审查**：
    - **依据**：见 §3.1 问题 5。
    - **下阶段执行**：在 P4 编码阶段，当某张表需要新建/修改时，**同一份 Prompt** 必须要求 AI 同时输出 DDL + Mermaid ER 片段 + JPA Entity Java 文件，并要求 AI 自己 review "三者字段名是否完全一致"。

11. **"跨阶段一致性 review"制度化**（来自 D3-02 教训）：
    - **依据**：见 §3.1 问题 2 + §3.2 第五类偏弱。
    - **下阶段执行**：P4 开工前必须召开**一次** 30 min 的"P1 SRS 原文对照"会议，由组长（或 D）逐条对照 P1 FR/NFR 检查 P2/P3 决策是否偏离。这条不是 Prompt 改进，是**流程改进**——AI 触达不了，必须人工兜底。

## 5. 本阶段的核心工程判断

### 5.1 决策内容

**回归 P1 SRS 原意，把鉴权方案修订为"密码为主 + 验证码辅助"，并显式排除新设备识别 / 异地登录 / 管理端双因子（D3-02）。**

这是本期与 AI 出入最大的一处决策：

| 阶段 | AI 默认输出 | 团队最终决定 |
| :--- | :--- | :--- |
| P2 ADR-003 | "禁外部身份系统 ⇒ **完全不要密码**" | 暂未察觉，沿用 |
| P3 §3.6 隐私字段 | 继承 ADR-003，写"`password_hash` 不存（无密码登录）" | P3 review 发现偏离 |
| P3 修订后 | —— | 密码为主 + 验证码辅助 + 不做新设备/异地 |

### 5.2 为什么 AI 无法做这个决策

AI 不能拍板这条决策，本质原因是它缺少以下三类信息：

1. **跨阶段对齐不是 AI 的默认行为。**
   AI 在生成 P3 文档时只接得到当前 Prompt 的上下文，**不会主动回查 P1 SRS 是否被 P2 偏离**。这意味着"AI 顺着 P2 文档继续工作"对 AI 来说是最理性的行为，但对项目来说是把偏离一路传递下去。**这是 AI 训练机制的固有局限**——它在每一次生成时倾向"当前文档自洽"，而不是"跨文档一致"。

2. **"严禁 X"的语义边界由人类约定，AI 不会自己划。**
   "严禁 SSO/OAuth/CAS" → "不要密码" 的扩展看似合理（都是"不要外部 / 非主流认证"），但本项目对"外部"和"自有"的区分是**有商业意义**的（高校场景下学校 SSO 有法律责任、自有密码方案没有）。这条边界 AI 没有训练数据来推导，必须由团队（特别是组长）在 review 时主动划定。

3. **校园场景下"安全收益 vs 用户体验"的本地权衡，AI 倾向过度加码。**
   决策子项 2（不做新设备识别 / 异地登录）和子项 1 的二次收敛（不做管理端双因子）都是这类——AI 默认推荐"加上更安全"，但**本平台规模（2000 并发、admin_user 5–10 个）下，多一道防线带来的安全收益 ≈ 0，体验损失 ≠ 0**。这种"在本场景下应该砍掉"的判断，AI 缺少校园场景的现场感。

### 5.3 这一类决策的共同特征（跨 P1/P2/P3 累计）

| 阶段 | AI 无法独立做出的决策 |
| :--- | :--- |
| P1 | 移除 SSO 改人工审核 |
| P2 | 拒绝外部消息队列 |
| P3 | 回归密码方案 / 砍管理端双因子 |

三次共同特征：
- 取决于**团队承诺**（4 人能否承担额外的工程/运维/合规成本）；
- 取决于**资源边界**（工时盒子、运维带宽、法务责任）；
- 取决于**可逆性**（先加 vs. 先不加的反悔成本不对称）；
- 取决于**跨阶段对齐**（本期新增）——AI 不会主动回查上游文档是否被偏离。

这四类信息共同构成"工程判断"作为人类核心能力的**不可替代区**。

### 5.4 团队启示（在 P2 启示基础上追加）

P2 已记录的三问（运维带宽 / 反悔成本 / 假设偏差）继续有效；P3 新增第四问：

**4. 这条 AI 推荐 / AI 文档的结论，是否在跨阶段（P1 → P2 → P3）保持一致？如果偏离，是有意修订还是被 AI 悄悄泛化？**

这一问应**制度化**为 P4 开工前的"P1 SRS 原文对照"会议（详见 §4.2 改进措施 11）。
