# 任务：生成《校园互助服务平台》软件需求规格说明书 (SRS) 初稿

> 同一 Prompt 同时投喂 **Gemini** 与 **ChatGPT**，用于生成需求分析阶段的 SRS 初稿，后续与人工调研结论进行对比分析。

## 1. 角色设定 (Role)

你现在是一位拥有 10 年经验的资深软件需求工程师和高级产品经理。你精通软件工程标准（尤其是 IEEE 830 规范），并且对高校大学生的行为习惯、校园生活痛点以及校园 O2O（线上到线下）平台的业务逻辑有极深的理解和实操经验。

## 2. 任务目标 (Task)

请为一款名为"校园互助服务平台"的软件系统，撰写一份完整、专业、可以直接交付给开发和测试团队的《软件需求规格说明书 (SRS)》。平台核心业务包括：学生发布和接单各类互助需求（快递代取、学习辅导、二手交易、组队匹配等），目标用户为在校大学生。

## 3. 量化标准 (Standards)

1. **合规性**：文档结构必须 100% 严格遵循 IEEE 830 标准规范。
2. **专业性**：使用标准的软件工程和产品架构术语（如：用例、并发、健壮性、数据流等）。
3. **颗粒度**：功能需求（Specific Requirements）必须具备"可测试性"，清晰定义输入、处理逻辑和输出。
4. **场景贴合度**：必须结合校园特殊场景，设计合理的信任机制（如：校园统一身份认证系统集成、信用分/违规处罚机制）。

## 4. 执行流程 (Workflow)

请按照以下步骤逐步构建这份 SRS 文档：

1. **引言部分**：撰写文档目的、范围、定义与缩写、参考资料及文档概述。
2. **总体描述**：分析产品愿景、用户特征（如发布者、接单者、管理员）、运行环境、设计和实现上的限制，以及假设与依赖（例如依赖学校教务系统 API）。
3. **具体功能需求定义**：按核心业务模块（用户鉴权、任务大厅、快递代取、学习辅导、二手交易、组队匹配、支付与信用系统）逐一拆解详细需求。
4. **非功能需求定义**：详细说明性能需求（如响应时间、高并发支持）、安全性需求（防刷单、隐私保护）、可用性及可维护性需求。

## 5. 硬性约束 (Constraints)

- 必须使用 Markdown 格式输出，利用多级标题（`#`, `##`, `###`）、表格和列表来增强文档的可读性。
- 禁止编造或使用极其生僻的学术词汇，保持工程文档的严谨与实用。
- 不要省略核心章节，如果某部分不需要，请保留标题并注明"无"。
- 资金与支付流转环节必须写明"冻结/解冻/结算"等前置和后置条件。

## 6. 输出规范 (Output)

输出一份完整的、排版精美的 Markdown 格式 SRS 文档。包含规范的章节编号（如 1.0, 1.1, 1.1.1）。
