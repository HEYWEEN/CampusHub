# CampusHub 候选架构对比表


| 对比维度 | 方案 A：单体分层架构 | 方案 B：微服务架构 | 方案 C：事件驱动架构 |
| :--- | :--- | :--- | :--- |
| **开发复杂度** | **低**。内部逻辑在一个程序内互通，不需要处理诸网络请求中断、跨数据库等难题 | **极高**。需要额外搭建网关和服务注册中心，处理服务间的调用超时和数据同步问题 | **高**。需要引入和维护消息队列组件，并且需要防止消息丢失或被重复处理 |
| **可维护性** | **高**。排查 Bug 时只需查看一个后台程序的运行日志，问题定位路径短。对小团队友好 | **低**。报错可能需要去多后台程序的日志里去排查。如果没有专业的全链路监控工具，维护成本极高 | **中**。业务的流转逻辑被分散截断，如果后续部分发生异常，排查连续性会受阻 |
| **可扩展性** | **中**。增加新功能时需要重新打包和部署整个后台程序，性能扩展受限于单台 MySQL 数据库的处理速度 | **极高**。可以随时独立增加新业务领域，原有服务解耦彻底，可以单独对一个功能修改配置 | **高**。可以在不改动主体代码的情况下，轻易地挂载新的附属业务去监听处理消息 |
| **性能** | **高**。后台靠内存方法的本地调用，无中间流转消耗，响应时间在毫秒级别。 | **低**。部分逻辑需要在各服务器之间进行多段网络请求，增加请求延迟，且占用服务器内存资源 | **中**。请求进入团队队列后能很快获得成功反馈，但在后台把数据写进数据库的环节，可能有延迟 |
| **团队学习成本**| **低**。团队成员大部分已具备Java 和 Spring Boot 基础，门槛低 | **极高**。需要全员花大量精力学习微服务组件和容器化部署，跑通架构的耗时可能会超过 预期 | **高**。需要额外学习消息队列环境部署和异步编程思维，运行环境复杂 |
| **10周内可行性**| **可行**  | **不可行** 。仅梳理微服务环境部署就会吃掉前几周的全部工时，会导致期末项目无法按时跑通 | **存在风险** 。很可能会导致在基础功能还没写完时，被卡在解决消息队列组件报错的问题上 |
