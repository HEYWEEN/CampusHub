# CampusHub 架构候选方案对比表

## 1. 评估目标与硬约束

| 约束类别 | 具体内容 | 对架构选型的影响 |
| :--- | :--- | :--- |
| **团队规模** | 4 人学生团队，人均 ≤ 12 小时/周，总周期 ≤ 10 周 | 任何吃掉 ≥ 30% 工时在"基础设施搭建"上的方案直接出局 |
| **技术栈基线** | 后端 Spring Boot + Java 17 + MySQL 8 已锁定 | 不考虑跨语言、跨数据库范式的方案 |
| **业务复杂度** | 8 个核心业务模块（任务、二手、辅导、组队、失物、社区、私信、信用），但模块间共享同一用户账号体系 | 强调"业务边界清晰但数据强耦合"，影响拆分粒度 |
| **强一致性需求** | 信用分 < 80 限单 1、< 60 禁发禁接，必须实时生效 | 异步最终一致方案在核心链路上不可接受 |
| **隐私红线** | 后台强实名 / 前台弱展示，禁止真实姓名、学号外泄 | 必须存在 DTO 转换层，纯 MVC（Controller 直接 return Entity）架构出局 |
| **运维能力** | 1 台云服务器（2C4G ~ 4C8G），无 K8s/服务网格运维经验 | 任何依赖容器编排的方案需要折算运维学习成本 |
| **性能目标** | 并发 2000 / 月可用 99% / 核心查询 P95 ≤ 2s | 不需要追求"互联网级"指标，单实例即可达标 |

## 2. 候选方案集合

依据课堂讲授的主流后端架构风格，结合 CampusHub 的业务形态，确定四个候选方案进入对比：

- **方案 A：纯 MVC（Controller 直连数据库）**
- **方案 B：模块化单体 + 分层架构（推荐）**
- **方案 C：微服务架构（Spring Cloud Alibaba）**
- **方案 D：事件驱动架构（外部消息队列驱动）**

### 2.1 方案 A：纯 MVC（Controller 直连数据库）

- **核心思想**：保留 Model-View-Controller 三段式，Controller 内部直接调用 JdbcTemplate / MyBatis 完成 SQL 操作，不抽离 Service 层。
- **CampusHub 形态**：8 个业务模块各自一个 `XxxController`，发单、扣信用分、改积分都写在同一个 Controller 方法里。User Entity 直接序列化为 JSON 返回。
- **可见落点**：典型实现就是 4 周内"快速堆功能"的脚手架；调研访谈里 cxf 最初提的方案就是这一种。

### 2.2 方案 B：模块化单体 + 分层架构（推荐）

- **核心思想**：单一 Spring Boot 进程，按业务域（user / task / trade / credit 等）切分顶层包，每个包内严格保留 Controller-Service-Repository 三层；跨包通信只走 **应用服务接口** 和 **Spring ApplicationEvent**，禁止跨包直接读写 DAO。
- **CampusHub 形态**：
  - 部署仍是一个 fat-jar；
  - 代码工程在 IDE 里看起来像 8 个微服务（同名的 `user/`、`task/`、`credit/` 包）；
  - 信用扣分通过 `@TransactionalEventListener` 与发单写在同一个本地事务中，避免最终一致漏洞。
- **可见落点**：是辩论会最终拍板的方案，也是当前业内对"中小团队 + 多业务域"项目最常见的推荐起手式。

### 2.3 方案 C：微服务架构（Spring Cloud Alibaba）

- **核心思想**：按业务域物理拆分为独立服务（user-service、task-service、credit-service…），各自独立部署、独立数据库；引入 Nacos 作注册中心，Spring Cloud Gateway 做网关，Feign/OpenFeign 做服务间通信，Seata 处理分布式事务。
- **CampusHub 形态**：至少 6 个独立服务 + 网关 + 注册中心 + 配置中心 + Seata Server，至少需要 8 个进程在线，单台 4C8G 机器跑起来已较紧张。
- **可见落点**：辩论会上 czh 最初的诉求；其驱动力主要来自"简历加分 / 简介好看"，而不是真实的可扩展性需求。

### 2.4 方案 D：事件驱动架构（外部消息队列驱动）

- **核心思想**：核心写流程（发单、违约、评价）作为事件发布到 RabbitMQ / Kafka，下游模块（信用、积分、通知）以独立消费者异步处理；服务自身保持单体或微服务形态。
- **CampusHub 形态**：跑腿订单违约 → 发布 `OrderCanceled` 事件 → 信用模块异步扣分 → 积分模块异步退积分 → 通知模块异步发站内信。
- **可见落点**：辩论会上 lcy 最初的诉求；理论上解耦最彻底，但与"信用规则实时生效"的硬约束直接冲突。

## 3. 六维度详细对比

### 3.1 开发复杂度

| 方案 | 评分 | 关键复杂点 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐⭐⭐⭐ | 几乎无脚手架开销 | 第 1 周即可跑通"发单-接单"链路；但每加一处扣分逻辑都要复制 SQL |
| **B 模块化单体** | **⭐⭐⭐⭐⭐** | 仅需约定包结构、`@TransactionalEventListener` 用法 | 第 1 周搭骨架，第 2 周即可并行开发 8 个业务包，无服务通信成本 |
| C 微服务 | ⭐ | 服务拆分、网关、注册发现、Feign 契约、Seata 配置、Docker 编排 | 仅"环境联调能跑通"就要吃掉 2~3 周；4 人轮流踩坑 |
| D 事件驱动（外部 MQ） | ⭐⭐ | 需要部署/学习 RabbitMQ 或 Kafka、设计幂等消费、死信队列 | MQ 单独部署 + 消费失败处理一周起步；事件契约还需团队对齐 |

### 3.2 可维护性

| 方案 | 评分 | 维护风险点 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐ | 业务规则散落、复制粘贴泛滥、DTO 缺位导致隐私泄漏 | 信用扣分逻辑会同时出现在跑腿、二手、社区三个 Controller，修一处漏两处 |
| **B 模块化单体** | **⭐⭐⭐⭐⭐** | 仅需治理"跨包直读表"这一个反模式 | 信用扣分集中在 `credit/` 包，对外只暴露 `CreditService.deduct()` 和 `CreditDeductedEvent` |
| C 微服务 | ⭐⭐⭐ | 看起来"边界清晰"，但分布式调试链路非常长 | 一次"违约扣分"可能要跨 3 个服务的日志 + Seata 的事务日志，4 人团队没有全链路追踪基础设施 |
| D 事件驱动（外部 MQ） | ⭐⭐ | 事件链路天然难追踪 | 一条订单违约可能触发 5 条异步事件，出错时分不清是生产问题还是消费问题 |

### 3.3 可扩展性

| 方案 | 评分 | 横向 / 纵向扩展能力 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐⭐ | 只能整体扩缩容；无法独立扩展某模块 | 二手大促时只能整体加机器，浪费明显 |
| **B 模块化单体** | **⭐⭐⭐⭐**（项目所需够用） | 可以整机水平扩展；将来某模块成瓶颈，沿包边界剥离即可 | 2000 并发场景下 1 台机器即可吃下；将来 IM 模块若成瓶颈，可独立剥离 |
| C 微服务 | ⭐⭐⭐⭐⭐ | 真正按服务粒度独立扩缩容 | 但本项目根本用不到这种粒度，扩展能力是"过剩"，不会兑现成收益 |
| D 事件驱动（外部 MQ） | ⭐⭐⭐⭐⭐ | 异步天然削峰；下游消费者可独立扩展 | 同上，CampusHub 没有"突发大批量异步任务"场景，能力闲置 |

### 3.4 性能

| 方案 | 评分 | 延迟 / 吞吐特征 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐⭐⭐⭐ | 进程内调用，零网络开销 | P95 可低于 200ms，但缺缓存、缺连接池调优意识 |
| **B 模块化单体** | **⭐⭐⭐⭐⭐** | 进程内调用 + 受控的 HikariCP + 可选 Redis | 单实例即可达 2000 并发 / P95 ≤ 2s 目标 |
| C 微服务 | ⭐⭐ | 每次跨服务调用增加 ~5~30ms 网络开销 | 一次"发单+扣信用+扣积分"可能涉及 3 跳网络调用，延迟显著上升 |
| D 事件驱动（外部 MQ） | ⭐⭐⭐ | 吞吐量高，但端到端延迟高（消息排队） | 信用扣分异步意味着"违约 → 扣分"之间存在数秒空窗，**会被恶意脚本利用刷单** |

### 3.5 团队学习成本

| 方案 | 评分 | 必须掌握的新知识 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐⭐⭐⭐⭐ | 仅 Spring MVC 注解 | 课程涉及，团队全员零启动成本 |
| **B 模块化单体** | **⭐⭐⭐⭐⭐** | Spring 分层 + DTO + ApplicationEvent | 课程基本覆盖；ApplicationEvent 半小时上手 |
| C 微服务 | ⭐ | Spring Cloud Alibaba 全家桶 + Docker + Nacos + Gateway + Feign + Seata | 团队成员需要 1~2 周自学，挤占核心业务工时 |
| D 事件驱动（外部 MQ） | ⭐⭐ | RabbitMQ/Kafka 部署、消息模型、幂等消费、最终一致 | 学习曲线集中在"消息丢失/重复消费"等坑点上 |

### 3.6 10 周内落地可行性（一票否决项）

| 方案 | 评分 | 主要风险 | CampusHub 落地推演 |
| :--- | :--- | :--- | :--- |
| A 纯 MVC | ⭐⭐⭐ | 上得去，但中后期易翻车 | 第 4~5 周隐私泄漏 / 规则不一致 Bug 集中爆雷，可能需要返工重构 |
| **B 模块化单体** | **⭐⭐⭐⭐⭐** | 风险点已经被工程实践充分覆盖 | 时间预估稳健：W1 骨架、W2~W6 业务、W7 联调、W8 压测、W9~W10 验收 |
| C 微服务 | ⭐ | 仅基础设施搭建就吃掉 2~3 周；联调阶段会再吃 1~2 周 | 大概率"环境跑不稳 + 业务做不完"双输 |

## 5. 选择结论

### 5.1 入选方案：方案 B（模块化单体 + 分层架构）

> 在团队规模 4 人 / 周期 10 周 / 业务规则强一致 / 隐私后强前弱的复合约束下，方案 B 是 **唯一同时落在"可交付 ∧ 可维护 ∧ 合规"** 三圈交集内的选择。具体落地见 `架构设计文档.md`。

入选要点：
1. **可交付**：技术栈与团队既有储备完全一致，10 周时间表可控，无外部基础设施依赖；
2. **强一致性原生满足**：信用扣分 + 积分流转可在同一本地事务中完成，无最终一致漏洞；
3. **保留演进退路**：包结构按 DDD 边界设计，将来某模块真成瓶颈，可剥离为独立服务，沉没成本低；
4. **隐私边界清晰**：分层架构强制 DTO 转换，从架构层面阻断 Entity 直出。

### 5.2 退选方案与理由

| 退选方案 | 关键退选理由 | 是否预留演进可能 |
| :--- | :--- | :--- |
| **A 纯 MVC** | 没有 Service / DTO 隔离层，会从架构层面**违反 P1 的隐私硬约束**（前台弱展示原则在编码现场极易被绕过）；同时业务规则散落在 Controller 里造成长期可维护性塌陷。 | 否（取消层级容易，加回去难） |
| **C 微服务** | 在团队人数 < 服务数 × 2（康威定律）时必然崩坏；分布式事务 + 服务治理的工时黑洞会吞掉项目周期 70%；扩展性收益对于 2000 并发场景**完全不会兑现**；单纯出于"简历加分"的技术选型是典型的过度设计。 | 是（B → C 可平滑演进，反向不可） |
| **D 事件驱动（外部 MQ）** | 信用分 < 80 限单 1 / < 60 禁发禁接是**强一致硬规则**，异步处理产生的秒级窗口可被脚本批量刷单。即使把"非关键路径"（通知、统计）切换到 MQ，外部 MQ 部署成本也远高于 Spring ApplicationEvent。 | 是（仅在通知 / 数据归档等非关键路径上保留事件思路即可） |

### 5.3 演进路径建议

为了避免被"模块化单体 = 永远不能演进"绑架，需要在工程规范里写死以下三条，把"未来拆分成本"控制到最低：

1. **包间通信只允许走 `XxxApi` 接口或 Spring `ApplicationEvent`**，禁止跨包 `@Autowired` 别人的 `Repository`；
2. **每个业务包独立持有自己 `xxx_*` 前缀的表**，禁止跨表外键；
3. **DTO/VO 严格定义在 Controller 边界**，Service 间传递的对象禁止直接序列化对外。

这三条规范配合 ArchUnit / 包扫描脚本可在 CI 中自动校验，是"未来真要拆微服务"时的最小成本前置投资。
