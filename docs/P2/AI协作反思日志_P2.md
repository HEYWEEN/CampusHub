## 2. AI 助力分析（Q1）

### 2.1 本阶段 AI 最大的贡献

1. **加速"候选方案"的扫描 → 收敛过程**：四种 Prompt 策略下的 AI 回答交叉比对后，团队在 30 分钟内就完成了"候选方案集合 + 各自利弊清单"的初稿。同样的工作量人工分别整理至少需要 4~6 小时。
2. **提供"业内默认陷阱清单"**：尤其是 Claude Opus 4.7 在"资深架构师"角色下输出的隐藏风险（学校 SSO 法律责任、二清红线、信用分滥用），这些是 AI 训练语料里高频出现但学生团队往往不会主动查的风险点。AI 在这里起到了"低成本的红队"作用。
3. **充当"工程术语翻译器"**：把团队成员口语化的"如果违约扣分太慢会被刷"翻译成 ADR 里的"信用规则在异步窗口期失效，存在被脚本批量利用的业务漏洞"——这种术语替换能让外部审查者更快进入语境。
4. **生成 ADR / 文档的"标准骨架"**：背景 / 决策 / 理由 / 后果 / AI 辅助记录的五段式骨架，AI 一次性生成、格式齐整，免去团队对模板的重复劳动。

### 2.2 不同 Prompt 策略下 AI 回答质量的差异

| 策略 | 对应成员 | 模型 | 输出质量观察 |
| :--- | :--- | :--- | :--- |
| **A：零上下文直接询问** | A | Gemini 3.1 Pro | 只能给"百科式"答案，把四种架构平铺直叙；不带任何项目约束的判断；最后还反问"你更偏哪种"——典型的"AI 把决策推回用户"。**作为 baseline，质量明显最低。** |
| **B：投喂 P1 全部硬性约束** | B | DeepSeek-V4 | 答案精确度显著上升，能逐条对齐"约束 1 / 约束 2 / 约束 5"，输出可直接做模块划分初稿。**约束越具体，答案越可用。** |
| **C：要求多方案对比** | C | ChatGPT-5.3 | 输出结构非常工整，带定性评分和"星级矩阵"；但容易陷入"扩展性高 = 好"这种与项目无关的默认价值观，需要人工显式重写权重。**结构最强，价值观偏弱。** |
| **D：资深架构师角色** | D | Claude Opus 4.7 | 在不喂任何约束的情况下，AI **主动**输出了"假设清单"（4-12 人团队、DAU 1k~10k）、"反 AI 默认建议清单"、"二清红线 / SSO 法律责任"等高价值内容。**性价比最高的策略——零约束 + 角色头衔即可激活 AI 的"自我审查"。** |

> **关键观察**：Prompt 策略的质量梯度大致呈 **A < C ≈ B < D**。"角色法（D）"的边际成本极低（只多一段 Prompt），但产出收益接近"详细约束法（B）"，**这是 P2 阶段最重要的 Prompt 工程发现**，已纳入下阶段改进措施（详见 §4）。

### 2.3 估计节省时间

≈ 12 人时（人均 3 人时），主要集中在：候选方案扫描（节省 4 人时）、ADR 骨架（节省 3 人时）、辩论会记录扩写（节省 5 人时）。

## 3. AI 误导分析（Q2）

### 3.1 问题清单

#### 问题 1：AI 默认对"扩展性 = 越高越好"的隐性价值观偏好

- **如何发现**：ChatGPT-5.3 做 6 维度对比的结果里"事件驱动架构 ⭐⭐⭐⭐⭐ 可扩展性"被标为最高评分，对应的"⭐ 10 周可行性"却被一笔带过。AI 在 6 维平均分计算上隐含了"扩展性 = 重要"的权重。但本项目的核心约束是 10 周可交付 + 规则强一致，扩展性的权重应当被显著调低。
- **如何修正**：在 `架构候选方案对比表.md` §1 显式写出"评估目标与硬约束"，把"扩展性按本项目权重"作为独立列；在 §3.3 的关键洞察明确写"校园场景的可扩展性收益接近 0"。
- **可迁移启示**：AI 在多维度对比时容易给出"看起来公平的平均分"，但它的隐性权重并不一定是项目权重，**必须由人工显式声明权重**。

#### 问题 2：AI 在"工程默认值方向"上的系统性盲区

- **如何发现**：ADR-002 撰写时，AI 推荐使用 Spring `@TransactionalEventListener` 替代外部 MQ，但完全没提该注解的默认 phase 是 `AFTER_COMMIT`——也就是说"提交事务后才扣分"，与"必须同事务内完成"的语义直接冲突。新手照抄文档会写出"先提交订单再扣信用分"的严重 Bug。
- **如何修正**：在 ADR-002 决策正文显式写"扣分类 Listener 必须显式声明 `phase = BEFORE_COMMIT`"，并在 PR 模板中加入校验项。
- **可迁移启示**：AI 在"概念层"几乎不会出错，但在"具体 API 的默认值方向"上会沉默——它不会主动告诉你"默认值与你的需求方向相反"。**这一类 Bug 必须用 PR 模板 + 静态规则兜底，不能依赖 AI 评审。**

#### 问题 3：AI 容易遗漏"出口的隐蔽路径"——例如日志泄漏

- **如何发现**：ADR-004（隐私 DTO 强制转换）由 AI 起草时，覆盖了 API 返回值的脱敏，但完全没提**应用日志 / 错误堆栈 / 第三方监控平台**也是隐私出口。现实中 80% 的隐私泄漏发生在日志里，而不是 API 返回里。
- **如何修正**：在 ADR-004 新增"日志输出脱敏"作为独立子项，要求业务日志统一用脱敏 DTO 打印。
- **可迁移启示**：AI 默认 Top-Down 思维——它从"用户请求 → API 响应"路径思考，会忽略横向出口（日志、监控、第三方上报、错误堆栈、备份导出）。**做安全 / 合规 ADR 时必须人工补"非主路径出口清单"。**

#### 问题 4：AI 把"看情况而定"当作可接受的决策

- **如何发现**：ADR-005（Redis 是否启用）的 AI 初稿写了"非强制，视压测结果决定"——这在 ADR 语境里等同于"没决策"。三个月后回看会变成"是不是该加 Redis"的反复讨论。
- **如何修正**：人工补充三条具体的"启用触发条件"（P95 > 2s / 连接池 Wait > 100ms / 出现热点），并要求满足任一条件需发新 ADR。
- **可迁移启示**：AI 倾向于"安全的模糊"，但 ADR 的核心价值是消灭未来的反复讨论。**所有"视情况而定"必须翻译成"满足 X 条件即触发 Y 动作"。**

#### 问题 5：AI 在"团队管理 / 工程纪律"维度上几乎无输出

- **如何发现**：所有 AI 初稿都只关注技术决策，没有任何"如何防止业务方私自加缓存""如何在 PR 模板里强制校验"这类工程纪律层面的内容。但这些恰是模块化单体能不能撑住的命脉。
- **如何修正**：在 ADR-001 / ADR-002 / ADR-005 中分别新增"工程纪律 / CI 校验 / PR 模板"小节。
- **可迁移启示**：ADR 不仅是技术决策记录，也是团队约定的法律文本。AI 只会写技术，不会写约定，**约定部分必须由人工补全**。

### 3.2 总结性观察

AI 在本阶段的系统性偏弱区域可以归为四类：
1. **隐性权重**（多维对比中默认价值观偏好）；
2. **默认值方向**（API 默认值与需求方向相反）；
3. **出口路径**（日志、监控等非主路径）；
4. **触发条件 / 工程纪律**（"看情况而定" + 团队约定缺位）。

> **后续 Prompt 工程的重点目标**：让 AI 在以上四类上"主动声明 / 主动列举"，而不是"被动等人工补"。具体改进措施见 §4。

## 4. Prompt 改进计划（Q3）

### 4.1 P1 阶段提出的改进措施验证

| P1 改进措施 | 本阶段落地情况 | 验证结果 |
| :--- | :--- | :--- |
| **分层 Prompt**：先分析、再细化，每层带上游文档作上下文 | 部分落地。lcy投喂了完整的 P1 硬性约束，hyw在角色 Prompt 后又分了 4 个细分问题（架构判断 / 决策点 / 模块划分 / 隐藏风险） | ✅ 有效。B 与 D 的输出质量明显高于零上下文 Prompt（A） |
| **显式负面约束 + 领域事实注入** | 落地。lcy的 Prompt 把 P1 的 5 条"硬性禁止"原文复制粘贴 | ✅ 有效。AI 输出里完全没出现 SSO / 真实支付 / 99.9% SLA 等"幻觉"；首轮就达到可用质量 |
| **AI 红队反转视角** | 部分落地。"资深架构师角色"在某种程度上扮演了红队（主动列出隐藏风险），但没有正式让 AI 反过来"挑自己的刺" | ⚠️ 半有效。下阶段需要正式纳入"自我审查 Prompt" |
| **Few-Shot 限定验收标准形式** | 未落地。本阶段未涉及验收标准产出 | ⏸️ N/A，待下阶段（实现 / 测试）再验证 |

### 4.2 本阶段新增的 Prompt 改进措施

针对 §3 暴露的四类系统性偏弱，新增以下改进措施：

1. **"角色 + 极简 Prompt"作为低成本启动器**：
   - **依据**：本阶段证明"资深架构师角色 + 不喂详细约束"（策略 D）能以最低成本激活 AI 的自我审查能力，性价比明显高于"详细约束注入"（策略 B）。
   - **下阶段执行**：在每个新模块的设计起步阶段，先用"角色法"做 Brain Dump，再用"约束法"收敛，形成"先发散后收敛"的两阶段 Prompt 工作流。

2. **"权重声明前置"防止 AI 隐性价值观偏好**：
   - **依据**：见 §3 问题 1。
   - **下阶段执行**：在多维对比型 Prompt 中，**强制要求 AI 在做对比之前先列出"它打算用的权重"**，并由人工显式调整后再产出对比结论。具体 Prompt 模板：
     ```
     在做以下对比之前，请先列出你打算给每个维度的权重（满分 10）。
     等待我确认或调整权重后，再进行对比与综合评分。
     ```

3. **"非主路径出口清单"作为安全 / 合规 Prompt 的固定结尾**：
   - **依据**：见 §3 问题 3。
   - **下阶段执行**：每条安全 / 合规相关的 Prompt 后必须追加一句：
     ```
     除了 API 响应路径，还有哪些非主路径（日志 / 监控 / 错误堆栈 / 备份导出 / 第三方上报）
     可能成为该数据的隐蔽出口？请一一列举。
     ```

4. **"触发条件强制具体化"防止"看情况而定"**：
   - **依据**：见 §3 问题 4。
   - **下阶段执行**：在所有"是否引入 X"类决策 Prompt 中追加：
     ```
     如果你给出"视情况而定"的结论，请把"情况"翻译成可观测的具体触发条件
     （例如 P95 > 2s / CPU > 70% / 错误率 > 1% 等）。
     ```

5. **"工程纪律段落"强制纳入 ADR Prompt**：
   - **依据**：见 §3 问题 5。
   - **下阶段执行**：在 ADR 生成 Prompt 中明确要求：
     ```
     除了技术决策，还请输出一段"工程纪律"——
     说明：哪些行为应被禁止 / 哪些应在 CI 中自动校验 / 哪些应写入 PR 模板。
     ```

6. **"AI 自我审查"作为正式独立环节**：
   - **依据**：P1 提出但未完全落地（见 §4.1）。
   - **下阶段执行**：每条 ADR 起草完成后，必须再发一轮 Prompt：
     ```
     请以严苛的安全审计员 + 代码审查员视角，挑出该 ADR 中：
     1. 遗漏的质量属性权衡；
     2. 过于乐观的隐含假设；
     3. 实施层面的潜在 Bug。
     ```
   - 把这一步做成强制环节而非可选环节。

## 5. 本阶段的核心工程判断

### 5.1 决策内容

**拒绝外部消息队列（RabbitMQ / Kafka），改用 Spring `ApplicationEvent` + `@TransactionalEventListener(BEFORE_COMMIT)` 在单进程内做模块解耦。** 详见 ADR-002。

这是本阶段团队与 AI 出入最大的一处。事实上 AI 在 Prompt 策略 C / D 下都不同程度地"建议保留 MQ 作为退路"，而团队最终钉死的结论是"在 P2 阶段彻底不引入"。

### 5.2 为什么 AI 无法做这个决策

AI 不能拍板这条决策，本质原因是它缺少以下三类信息：

1. **业务规则的"实时性硬约束"在 AI 视角下只是普通约束**：  
   AI 知道"信用分 < 80 限单 1"是规则，但它不会自动联想到"这条规则一旦在异步窗口期失效，就会成为可被脚本批量利用的业务漏洞"。这条因果链条需要团队成员（lcy）在辩论中现场推导，再由队长（hyw）做出"哪怕牺牲解耦也要保一致性"的取舍。**AI 没有"在中国大学生群体里有人会写脚本刷单"这种现场感。**

2. **运维带宽是离散资源，AI 视角下是连续可扩张的**：  
   AI 默认认为"团队需要时可以学新东西"，但实际上 4 人 × 12 小时/周的运维带宽是**几乎不可压缩的离散资源**——"再学一个 RabbitMQ 部署"在 AI 看来是 1 个 Story Point，在真实工时表上可能直接挤掉 2~3 个核心业务模块的开发。**这是工时盒子约束，AI 看不到工时盒子。**

3. **可逆性 / 不可逆性的非对称风险，AI 不会主动量化**：  
   "先不引入 MQ，需要时再加" vs. "先引入 MQ，不需要时再撤"——前者是 24h 内可反悔的可逆决策，后者是涉及代码 + 数据 + 部署的不可逆决策。**AI 倾向于把两个选项当作同等地位的选项，但工程师必须主动量化二者的反悔成本不对称。**

### 5.3 这一类决策的共同特征

回看 P1 的"移除 SSO 改人工审核"和 P2 的"拒绝外部 MQ"，两次 AI 无法独立做出的决策都具备同样的三个特征：

- 取决于 **团队承诺**（4 人能否在 10 周内承担额外的运维 / 学习成本）；
- 取决于 **资源边界**（工时、运维带宽、法务责任）；
- 取决于 **可逆性**（先加 vs. 先不加的反悔成本不对称）。

这三类信息都不在 AI 的训练语料里——AI 只能看到"技术上可行"，看不到"团队能否承担、出问题谁来背、半年后想撤还能不能撤"。**这是"工程判断"作为人类核心能力的不可替代区**。

### 5.4 团队启示

未来在每一个"AI 给了多个候选方案 + 推荐了其中一个"的场景，团队必须主动追问以下三问：

1. **AI 推荐的这个方案，运维带宽预算是多少？我们承担得起吗？**
2. **如果今天选 A，三个月后想换 B，反悔成本是多少？反过来呢？**
3. **AI 在做这个推荐时，假设的团队规模 / 用户量级 / 工时预算是多少？与我们真实情况偏差有多大？**
