## ADR-001：后端整体采用模块化单体（Modular Monolith）架构

### 状态
**已接受**（2026-04-28，团队全员通过；见 `架构选择辩论会记录.md` §第二部分）

### 背景
- 团队规模 4 人，人均 ≤ 12 小时/周，项目周期 10 周；
- 后端栈固定为 Spring Boot + MySQL 8；
- 业务模块多（任务/二手/辅导/组队/失物/社区/私信/信用），但底层用户与积分账号体系强耦合；
- 性能目标为 2000 并发 / 月可用 99%，无"互联网级 SLA"压力；
- 候选方案：纯 MVC、模块化单体、微服务、事件驱动（详见 `架构候选方案对比表.md` §3）。

### 决策
后端采用 **模块化单体**：单 Spring Boot 进程部署 + 单 MySQL 数据库；代码工程内部按业务域顶层包切分（`user/` `task/` `trade/` `community/` `credit/` `im/` `notify/` `admin/`），每包内严格保留 Controller-Service-Repository 三层；**跨包只允许通过应用服务接口或 Spring `ApplicationEvent` 通信，禁止跨包直接 `@Autowired` 他人 Repository 或直接读写他人表**。

### 理由
1. **可交付性**：在 4 人 × 10 周的工时盒子里，纯 MVC 没有 Service/DTO 防线、隐私容易翻车；微服务的基础设施搭建会吃掉 ≥ 30% 工时；外部 MQ 与"信用分实时生效"硬规则冲突。模块化单体是唯一能稳交付的选择。
2. **强一致性原生满足**：信用扣分 + 积分流水可在同一本地事务中提交，无需 Seata 等分布式事务框架。
3. **可演进性**：包结构按 DDD 边界设计，将来某模块成瓶颈可剥离为独立服务，沉没成本低；与"先单体后微服务"的业内经验路径一致。
4. **遵循康威定律**：业内经验法则"团队人数 ≥ 服务数 × 2"在 4 人团队下意味着最多 2 个微服务，与本项目 8 个业务域不匹配。

### 后果
- **正面影响**：
  - 工时投入可集中在业务规则、隐私边界、信用算法等"真正的难点"上；
  - 部署与故障排查链路最短，单一日志源；
  - 单库本地事务保证强一致，避免最终一致漏洞。
- **负面影响**：
  - 整机水平扩展粒度较粗，但 2000 并发场景下不会触发该瓶颈；
  - 代码工程随业务增长会增大，依赖团队对包间约定的纪律性。
- **需要关注的风险**：
  - **跨包直接读写表**会让模块化单体退化为"大泥球"；缓解措施：在 CI 中加 ArchUnit 静态规则，违规直接打回；
  - **共享 Spring 配置**容易出现"一处改全局炸"；缓解措施：业务包内的配置类用 `@ConditionalOnProperty` 隔离启停。

- **AI 初稿内容摘要**（来自 `架构辩论赛-成员记录/架构辩论赛_成员D.md`，Claude Opus 4.7 输出）：

- **`[人工修订]` 修订点 2：把"业务模块多 vs 用户量级不大"的判断显式拆为两条独立约束**  
  - AI 把这两点混在一起说，但其实"业务多"和"用户少"对架构选型的牵引方向相反——业务多倾向拆服务、用户少倾向不拆。把两者解耦后才能讲清"模块化单体"是怎么把这对矛盾化解掉的（业务多用包结构解决，用户少用单进程部署解决）。
  - 修订理由：AI 善于"输出结论"，但不擅长"拆解相反的牵引力"，这是工程判断的必修动作。

- **`[人工修订]` 修订点 3：补充"强一致性原生满足"作为独立理由**  
  - AI 初稿讲了"数据强耦合，拆完会被分布式事务反噬"（即避免坏处），但没正面讲"单体下信用扣分天然在本地事务里跑"（即享受好处）。
  - 修订理由：质量属性的权衡需要双向论证（避免什么 + 收益什么），单向"避免坏处"会让外部审查者怀疑是不是只是"懒得拆"。

## ADR-002：跨模块通信采用 Spring `ApplicationEvent` + 同步事务，不引入外部消息队列

### 状态
**已接受**（2026-04-28，团队辩论后由队长拍板；见 `架构选择辩论会记录.md`）

### 背景
- 业务中存在大量跨模块联动场景：
  - 跑腿订单违约 → 扣信用分 + 退积分 + 发通知；
  - 二手交易完成 → 加信用分 + 结算积分；
  - 树洞违规 → 扣信用分 + 隐藏帖子 + 通知用户。
- 若各模块直接互调 Service，会产生强耦合（`ErrandService` 强依赖 `CreditService` + `PointsService` + `NotifyService`），违反模块化单体的"包间最小耦合"目标；
- 若引入外部 MQ（RabbitMQ / Kafka），异步执行扣分会导致"信用分 < 80 限单"规则在秒级窗口内失效，**可被脚本利用刷单**（见 `架构选择辩论会记录.md` §lcy 与 hyw 的关键交锋）。

### 决策
- 采用 **Spring `ApplicationEvent` + `@TransactionalEventListener`**：
  - 事件发布点（如 `OrderCanceledEvent`、`BadReviewSettledEvent`）由 **业务的源头模块**（如 `task/`）发布；
  - 下游模块（如 `credit/`、`notify/`、`points/`）通过 `@TransactionalEventListener(phase = BEFORE_COMMIT)` 订阅，确保扣分 / 退积分 / 状态联动 **与源头操作在同一本地事务内** 完成；
  - 通知 / 站内信 / 数据归档等 **非关键路径** 可使用 `@TransactionalEventListener(phase = AFTER_COMMIT) + @Async`，允许异步与最终一致；
- **不引入** RabbitMQ / Kafka / RocketMQ 等外部消息中间件。

### 理由
1. **强一致性硬约束**：信用分 < 80 限单 1 / < 60 禁发禁接是 P1 钉死的实时规则；外部 MQ 引入的秒级延迟会形成业务漏洞。
2. **解耦诉求被精确满足**：`ApplicationEvent` 让源头模块只 import 事件类，不 import 下游 Service，达成与外部 MQ 同等的代码级解耦。
3. **运维零成本**：无需多进程部署、无需消息可靠性调优、无需死信队列治理；4 人团队的运维带宽极度有限。
4. **保留路径开放**：将来若某条链路真的需要跨进程异步（如全站站内信群发、数据归档），可在 **该单条链路** 切换到 MQ，不需要全局改造。

### 后果
- **正面影响**：
  - 业务规则一致性强保障；
  - 学习成本几乎为零（团队课程已涉及 Spring）；
  - 链路完整可追溯，单进程日志即可串起整条业务流。
- **负面影响**：
  - 单进程内若某下游 Listener 抛异常，整条事务回滚；需要在 Listener 层做异常分级（业务异常回滚 / 通知失败仅打日志）；
  - 异步路径（`AFTER_COMMIT + @Async`）需要业务方自行保证幂等。
- **需要关注的风险**：
  - **`@TransactionalEventListener` 默认在事务提交后触发**，与"必须同事务内完成"语义冲突；缓解措施：扣分类必须显式声明 `phase = BEFORE_COMMIT`，并在 PR 模板中加入校验项；
  - **事件命名失控**：随着模块增多，事件类型可能膨胀。缓解措施：事件类必须放在源头模块的 `event/` 子包，命名遵循"主语 + 动词过去式"（如 `OrderCanceledEvent`），由 ADR-002 约束。

### AI 辅助记录

- **AI 初稿内容摘要**（来自 `架构辩论赛-成员记录/架构辩论赛_成员D.md`）：
  > 异步：RabbitMQ / Kafka / Spring Events，倾向「Spring 应用事件 + 数据库轮询」；单体内不需要重型 MQ。

- **`[人工修订]` 修订点 1：把"用 Spring Event 替代 MQ"从一句倾向升级为正式决策，并补充"为什么外部 MQ 在本项目里是漏洞"**  
  - AI 只说"单体内不需要重型 MQ"——理由弱，容易被反推（"那万一以后想要呢？"）。  
  - 人工补充：外部 MQ 的根本问题不是"重型"，而是 **它会让信用规则在秒级窗口内失效，形成可被利用的业务漏洞**。把决策依据从"运维成本"上升到"业务正确性"。
  - 修订理由：AI 容易把"运维成本"当成万能挡箭牌，但工程审查者真正信服的是"功能正确性"层面的论证。

- **`[新增]` 新增"`@TransactionalEventListener` 的 phase 必须显式声明"作为风险与缓解项**  
  - AI 完全没提 `@TransactionalEventListener` 的默认 phase 是 `AFTER_COMMIT`，即"提交后才触发"——这与"必须同事务内完成"的语义直接冲突，**新手照抄文档会写出"先提交再扣分"的严重 Bug**。
  - 人工新增：在 PR 模板中加入"扣分类 Listener 必须显式声明 `BEFORE_COMMIT`"的校验项。
  - 修订理由：这是 AI 最容易遗漏的"工程实现细节"层面的质量属性陷阱——它知道概念、不知道默认值的方向。

- **`[新增]` 新增"事件命名规范 + 包位置规范"作为长期可维护性约束**  
  - AI 没提及命名 / 放置约束，只是说"通过事件解耦"。
  - 人工新增：事件类必须放在源头模块的 `event/` 子包，命名遵循"主语 + 动词过去式"。
  - 修订理由：模块化单体的命脉是工程纪律。事件命名一旦失控，半年内就会变成无人能读的"事件大泥球"。

- **`[人工修订]` 修订点 2：把"非关键路径"和"关键路径"显式拆开**  
  - AI 一刀切说"用 Spring Event"，但实际工程中"通知"和"扣分"对一致性的要求完全不同。
  - 人工拆分：扣分类用 `BEFORE_COMMIT`（同事务），通知类用 `AFTER_COMMIT + @Async`（异步、可最终一致）。
  - 修订理由：质量属性权衡的核心动作就是"识别每条链路的 SLA 不同"，AI 倾向于给"统一答案"，工程师必须做"分层答案"。

## ADR-003：鉴权采用"手机号 + 短信验证码 + 学生证人工审核 + JWT 无状态"，不引入 SSO/OAuth/CAS

### 状态
**已接受**（在 P1 阶段已锁定，本 ADR 仅做架构层正式记录）

### 背景
- 调研访谈中 4 名核心受访者全部担忧"学号被公开 = 社死风险"；
- 学校教务处 SSO 接口审批流程超出 10 周项目周期；
- 一旦接入学校 SSO，**学籍数据合规责任会被甩到学生团队头上**（《个人信息保护法》下的赔偿主体）；
- 项目无支付牌照，鉴权也无需对接金融级 KYC；
- 候选方案：A 学校 CAS/SSO；B OAuth2.0（微信/支付宝）；C 手机号 + 短信验证码 + 人工审核学生证。

### 决策
- 注册登录链路：**手机号 + 短信验证码** 是唯一登录入口，不开放第三方登录；
- 校园身份验证：用户上传学生证 / 校园卡照片 → 管理员后台 **人工审核** → 标记 `verifyStatus = approved`，原始证件图片在审核完成后 **30 日内删除**，仅保留审核结论与图片 hash；
- 会话机制：**JWT 无状态**（Access Token 30 分钟、Refresh Token 7 天）；服务端不存 Session，水平扩展时无 sticky session 负担；
- 限流：单手机号 60s 内至多 1 条短信，单 IP 60s 内至多 5 条，单手机号 24h 至多 20 条，单 IP 24h 至多 200 条。

### 理由
1. **法务责任边界清晰**：学生团队不能承担学籍数据合规责任，**绝对回避** SSO/CAS 路径；
2. **可交付性**：人工审核 + 短信验证码完全在团队能力范围内，第 3 周即可上线；
3. **隐私一致性**：手机号在数据库存储 + 前台脱敏（`138****1234`），与"前台弱展示"原则同步；
4. **无状态会话适配模块化单体演进**：JWT 不依赖会话存储，未来某模块剥离为独立服务时，鉴权链路不需要重写。

### 后果
- **正面影响**：
  - 法务责任收敛在平台自身，不牵连学校；
  - 短信成本可控（预算 ≤ 300 元/月）；
  - 鉴权与水平扩展解耦。
- **负面影响**：
  - 人工审核引入审核时延（≤ 24h），影响新用户首次发单体验；缓解措施：未审核用户可浏览，仅"发单 / 接单"需审核通过；
  - 短信通道依赖第三方稳定性；缓解措施：同步重试 ≤ 2 次（指数退避 1s/3s），失败后明确返回 `SMS_SEND_FAILED` + 前端 60 秒重试提示。
- **需要关注的风险**：
  - **JWT 泄漏**风险：缓解措施：Refresh Token 滚动签发 + 异常 IP 登录强制下线；
  - **审核员瓶颈**：缓解措施：管理员后台支持多人并发审核 + 审核积压超过 24h 自动告警。

### AI 辅助记录

- **AI 初稿内容摘要**（来自 `架构辩论赛-成员记录/架构辩论赛_成员B.md` 与 `架构辩论赛_成员D.md`）：
  - DeepSeek-V4：建议 Spring Security + JWT + 手机号短信验证码；
  - Claude Opus 4.7：明确警告"绝对不要碰学校 SSO"，因为会"把学籍数据合规责任拽到学生团队头上"。

- **`[AI 初稿]` 直接采纳：手机号 + JWT 的技术骨架**

- **`[人工修订]` 修订点 1：把"原始证件图片审核完成后 30 日内删除"写进决策正文**  
  - AI 初稿建议"原始证件照在审核完成后不长期存储（仅留 hash + 审核结论）"，但没给保留期限。
  - 人工补充：明确 **30 日** 保留期 + 仅留 hash，让运维有可执行的清理任务。

  - 人工补充：60s/24h × 单手机号/单 IP 的四象限限流策略。
  - 修订理由：限流是"短信轰炸 + 短信成本失控"两大风险的唯一防线，不写参数等于没决策。

- **`[新增]` 新增"未审核用户可浏览，仅发/接单需审核通过"的渐进披露策略**  
  - AI 一刀切建议"未审核用户禁止操作"。
  - 人工补充：浏览态权限放开，发/接单门槛收紧，平衡审核时延与首次体验。
  - 修订理由：AI 在合规与体验权衡上倾向于过保守。让"未审核用户能预览社区"是新人留存的关键，是产品判断，不是技术判断。

- **`[人工修订]` 修订点 2：明确"短信限流的 4 个值"对应的具体业务漏洞**  
  - AI 只给了限流概念，没说"为什么是这 4 个数"。
  - 人工补充：60s/单手机号是防单用户连按、60s/单 IP 是防工具批量、24h/单手机号是防长期骚扰、24h/单 IP 是防整段宿舍楼共用 IP 引发误杀。
  - 修订理由：每个具体阈值都应有"反向漏洞"对应，否则就是拍脑袋。

## ADR-004：隐私输出采用 DTO/VO 强制转换，架构级阻断 Entity 直出

### 状态
**已接受**

### 背景
- P1 锁定的隐私红线："后台强实名 / 前台弱展示"——前端绝不展示真实姓名 / 学号；
- User Entity 字段中包含 `realName`、`studentNo`、`idCardNo`、`phone` 等敏感字段；
- 中国大学生对"被同学认出来"有强烈的社死焦虑，是该平台的关键产品风险；
- 单纯依靠 Code Review 检查"是否漏出敏感字段"在 4 人团队下不可持续，需要架构层强约束。

### 决策
- **架构级强约束**：所有 Controller 出参禁止使用 Entity 类型；必须使用 `XxxVO` / `XxxDTO`；
- **公开用户对象统一结构**：`PublicUserVO = { nickname, avatarUrl, verifiedTag }`，**任何前台 API 返回的用户对象必须是该结构或其超集**；
- **黑名单字段**：`realName`、`studentNo`、`idCardNo`、`phone`（前台仅可展示脱敏值如 `138****1234`）四个字段在所有非"用户本人 / 管理员"接口的响应体中必须缺失；
- **默认隐藏开关**：`hidePublishedHistory=true`、`hideAcceptedHistory=true`、`hideCourseReviews=true` 是注册时的默认值，需用户主动开启才公开；
- **CI 校验**：使用 ArchUnit 静态规则在 CI 中扫描 `@RestController` 方法返回值，**禁止任何 `*Entity` 类型直接出现在 Controller 返回值签名中**，违规直接打回。

### 理由
1. **隐私是架构级约束，不是代码风格问题**：单靠 Review 在团队规模 4 人 + 周期 10 周下漏检率必然 > 0；架构级强约束把漏检率降为 0；
2. **DTO 转换层与"模块化单体"的包结构相互加强**：每个业务包内的 `dto/` 子包可作为对外 API 契约的真源；
3. **可审计**：黑名单字段集中定义后，安全检查只需对照清单 grep 即可，不依赖"读懂业务"。

### 后果
- **正面影响**：
  - 隐私泄漏的工程下界被拉到接近 0；
  - 接口契约清晰，对前端联调友好；
  - 可被自动化工具（ArchUnit、OpenAPI 校验）持续守护。
- **负面影响**：
  - 每个业务对象需要维护 Entity / DTO / VO 三类，编码工作量增加约 15%；缓解措施：用 MapStruct 自动生成转换代码；
  - 字段新增需要同步更新 DTO，遗忘会导致"前端拿不到字段"；缓解措施：CI 加 OpenAPI 契约校验。
- **需要关注的风险**：
  - **管理员后台接口**也走同一框架，但需要返回真实姓名 / 学号；缓解措施：管理员接口使用独立的 `Admin*VO` 命名空间，CI 规则对 `/api/admin/**` 路径放行黑名单字段，但要求接口必须有 `@PreAuthorize` 注解；
  - **日志输出**也需要纳入脱敏框架：缓解措施：业务日志统一用脱敏过的 DTO 打印。

  - DeepSeek-V4：建议数据库存真实姓名+学号，但接口返回时仅含昵称+认证标签；
  - Claude Opus 4.7：建议"任何前台返回的用户对象，必须经过脱敏 DTO 转换才能出域"。

  - AI 给出了"应该用 DTO"的建议，但停留在编码约定层面，没有自动化兜底。

## ADR-005：Redis 在 P2 阶段默认不启用，仅保留配置开关

### 状态
**已接受**

### 背景
- 性能目标 2000 并发 / P95 ≤ 2s，未做压测前无法判断是否需要缓存；
- 4 人团队若引入 Redis，将承担额外的运维成本（部署、监控、缓存一致性）；
- AI 的默认建议倾向于"先把 Redis 加上以防万一"，是典型的过早优化反模式；
- 业务侧暂未识别出"必须缓存"的强需求场景。

### 决策
- **P2 阶段实现不依赖 Redis 路径**：所有热点查询（任务大厅、课程评价列表）首版直接走 MySQL；
- **保留配置开关**：在 `application.yml` 中保留 `cache.redis.enabled=false` 配置，类路径下保留 Spring Cache 抽象但默认 NoOp；
- **触发启用条件**（ADR 续作签发条件）：
  1. 压测显示 2000 并发下任务大厅 P95 > 2s；
  2. 数据库连接池 Wait Time P95 > 100ms；
  3. CPU / IO 出现明确的查询热点。
- 满足任一条件后，再发新 ADR-00X 启用 Redis 并明确缓存的对象 / TTL / 失效策略。

### 理由
1. **过早优化反模式回避**：在没有压测数据前引入缓存是猜测，缓存一致性问题反而拖慢交付；
2. **运维带宽守护**：4 人团队的运维带宽是稀缺资源，每多一个组件就多一个故障域；
3. **可逆决策**："先不引入"是 24h 内可反悔的决策，损失低；"已引入"则需要清理代码 + 数据 + 部署，损失高。

### 后果
- **正面影响**：
  - 部署拓扑简化，仅 Nginx + Spring Boot + MySQL；
  - 业务实现不会出现"缓存与 DB 不一致"类 Bug；
  - 工时聚焦在业务正确性。
- **负面影响**：
  - 若压测发现性能不足，需要补做缓存改造；预估改造时间 2~3 人日，仍可控；
- **需要关注的风险**：
  - **业务方私自加缓存**：缓解措施：在工程规范中明确"未走 ADR 续作流程的缓存改动一律打回"；
  - **首次压测发现性能不足时**已经临近交付：缓解措施：W7 即开始压测，留足缓冲。

### AI 辅助记录

- **AI 初稿内容摘要**（来自 `架构辩论赛-成员记录/架构辩论赛_成员B.md`）：
  > 热点只读数据（如首页信息流）使用 Redis 缓存（可选，视性能测试结果决定，非强制）。

- **`[AI 初稿]` 直接采纳：可选 + 视压测结果决定的总体方向**

- **`[人工修订]` 修订点 1：把"可选"翻译为可执行的"启用触发条件"**  
  - AI 说了"非强制"，但没说"什么时候必须强制启用"。
  - 人工补充：明确三条触发条件（P95 > 2s / 连接池 Wait > 100ms / 出现热点），并要求满足任一条件需发新 ADR。
  - 修订理由：决策必须有可观测的触发条件；否则团队会陷入"是不是应该加 Redis"的循环讨论。

  - 人工新增：把"先不引入是可逆的、引入了是不可逆的"作为决策依据写入 ADR。
  - 修订理由：ADR 不仅记录"决定了什么"，还应记录"用什么方法论决的"，便于将来其他决策复用同一方法论。
