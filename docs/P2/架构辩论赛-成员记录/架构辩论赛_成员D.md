## 1. 实验设计意图（为何要这样问）

> **只给 AI 一个"资深架构师"的角色身份，而不主动喂入 P1 已定稿的硬性约束，AI 是否会自发地避开那些常见的过度设计陷阱？**

它的对照价值：

1. **测"角色"这一维度的独立贡献**：与策略 A（零上下文）的差异**仅仅多了一个角色头衔**。如果回复质量明显提升，说明"角色"是一个低成本高收益的 Prompt 技巧。
2. **预测 AI 的"自我审查能力"**：扮演资深架构师后，AI 是否会主动质疑业务规模、提示工时风险、警告法务责任？还是依旧吐"微服务 + SSO + 支付分账"？
3. **与策略 B（喂详细约束）做"性价比对比"**：B 是显式硬塞约束，D 是靠角色诱导；若 D 接近 B 的质量，说明"角色法"是更优雅的方案。
4. **形成质量梯度**：A < D ≈ C < B（预期），为团队反思日志 Q3"Prompt 改进计划"提供数据。

> ⚠️ **本策略的核心区别**：**不**贴 P2 前置 Prompt、**不**给 P1 硬性约束清单、**不**贴调研数据；只设角色 + 让架构师"自己判断什么是过度设计"。
> ⚠️ 角色头衔故意写得**笼统**（资深 / 10+ 年），不暗示"学生团队"语境，否则会污染对照。

## 一、判断：模块化单体（Modular Monolith）+ 前后端分离

**核心结论**：直接拒绝"微服务"，采用**模块化单体**作为初始架构，保留向微服务演进的退路。

### 论证

1. **业务模块虽多，但用户基数与流量与微服务运维成本严重不匹配**
   校园 O2O 单校 DAU 通常 1k~10k，5 校也才 5k~50k。这种量级，单台 4C8G 服务器 + MySQL 单库即可支撑。微服务的运维收益（独立扩缩容）在这个量级根本兑现不了。

2. **数据强耦合，拆完会被分布式事务反噬**
   跑腿单的"发布者"= 二手交易的"卖家"= 信用体系的"同一用户"= 树洞的"同一账号"。如果按业务拆 6~10 个微服务，跨服务事务必然出现，被迫引入 Seata / TCC / Saga，复杂度指数级上升，对中小团队是灾难。

3. **康威定律的残酷应用**
   业内经验法则：**团队人数 < 服务数量 × 2 时，微服务架构必然崩坏**。换言之，10 个微服务最少需要 20 人持续支撑。中小团队上微服务 = 给自己挖坟。

4. **模块化单体保留演进路径**
   在单体内部用清晰的包结构 + 接口隔离做"逻辑微服务"，未来某个模块（如 IM 私信、推荐）真的成了瓶颈，可以单独剥离成独立服务。这比"先拆后合"安全 N 倍。

### 模块划分（Bounded Context）

| 模块 | 职责 | 备注 |
|------|------|------|
| `user` | 用户、鉴权、个人资料 | 强实名 / 弱展示边界在此模块强约束 |
| `task` | 跑腿、组队、失物——所有"发布-接单-完成"形态的撮合 | 用统一的任务状态机抽象，不同业务做策略实现 |
| `trade` | 二手交易（含商品上下架、订单流转） | 涉及金钱场景，**强烈建议平台不介入资金** |
| `community` | 学习辅导、课程评价、资料分享、树洞 | 内容社区共性放此模块 |
| `credit` | 信用分体系 | 横切模块，被多模块订阅事件 |
| `im` | 站内私信 | 用 WebSocket，独立线程池 |
| `notify` | 通知（站内信 / 短信） | 异步队列驱动 |
| `admin` | 后台管理（人工审核 / 内容审核 / 申诉处理） | 单独前端，复用后端域 |

模块间通过**应用服务接口**调用，**禁止跨模块直接读写表**。这是模块化单体能不能撑到 5 万 DAU 的命脉。

## 二、关键架构决策点（Trade-off 表）

| 决策点 | 候选选项 | 我的倾向 | 关键理由 |
|--------|---------|---------|---------|
| 架构风格 | 单体 / 模块化单体 / 微服务 | **模块化单体** | 可演进，避免运维负担 |
| 鉴权方案 | 学校 SSO / 自建账号 / 第三方登录 | **手机号 + 人工审核学生证** ⚠️ | 学校 SSO 拿授权极难，且数据合规风险大 |
| 资金模型 | 真实货币 / 虚拟积分 / 不介入资金 | **虚拟积分 + 信息撮合** | 真实货币需"二清"牌照，团队拿不到 |
| 数据库 | MySQL 单库 / 主从 / 分库分表 | **MySQL 单库起步** | 几十万行数据，单库可用很久 |
| 缓存 | Redis 集群 / 单 Redis / 不用 | **单 Redis** | 真有热点再加，过早优化是万恶之源 |
| 搜索 | ES / MySQL FullText / LIKE | **MySQL FullText 起步** | ES 是远期方案，初期负担过重 |
| 部署 | K8s / Docker Compose / 物理机 | **Docker Compose** | 中小团队运维成本敏感 |
| 实时通讯 | WebSocket / SSE / 轮询 | **WebSocket（im 模块）** | IM 必需，其他场景轮询足够 |
| 异步 | RabbitMQ / Kafka / Spring Events | **Spring 应用事件 + 数据库轮询** | 单体内不需要重型 MQ |

## 三、隐藏风险（新手团队最容易翻车的几个）

### 风险 1：学校 SSO 的法律责任陷阱（强警告）

接入学校 CAS / 教务系统 OAuth，看似省力，**实则把学籍数据合规责任拽到了你们头上**。一旦发生数据泄露——

- 学校先甩锅给你们；
- 教育部 / 网信办约谈对象是你们；
- 个人信息保护法下的赔偿责任是你们。

**强烈建议绝对不要碰学校 SSO**。改用"手机号 + 人工审核上传学生证 / 校园卡"模式，把"校园身份"作为**标签**而非**数据源**，原始证件照在审核完成后**不长期存储**（仅留 hash + 审核结论）。

### 风险 2：资金场景的"二清"红线

只要平台撮合双方真实货币流水（哪怕只是经手 1 秒），就触碰央行《非银行支付机构网络支付业务管理办法》的"二清"红线。**没有支付牌照的平台介入资金 = 违法**。

可行方案两条：
- **平台只跑积分**：所有"酬劳"以平台积分计价，积分**只能用于平台内权益**（如优先接单、解锁高级功能），不与现金挂钩。
- **平台只做信息撮合**：发布方与接单方在线下自行用微信 / 支付宝转账结算，平台不经手。

避免任何形式的"代收代付""资金池""担保交易"——这是支付牌照机构才能做的事。

### 风险 3：防社死的产品风险

高校 O2O 平台死亡率最高的一类原因不是技术——是**用户怕被同学认出来**。

- 学号绝不能在前台展示；
- 真实姓名只在双方私聊时显示，且可一键隐藏；
- 历史发布 / 接单 / 评价记录**默认对外不可见**，仅本人可查；
- 课程评价**强制匿名**，但后台保留实名以备申诉与合规。

把这条写进架构层的"领域不变量"——**任何前台返回的用户对象，必须经过脱敏 DTO 转换才能出域**。

### 风险 4：信用分体系被滥用

差评 / 投诉 / 信用扣分一旦没有反向制衡，就会被滥用：
- 报复性差评（卖家被买家恶意差评）；
- 群体性举报（同学之间恶作剧）；
- 信用通缩（人人扣分，最后整个体系不可信）。

**必须**内置：
- 7 日申诉窗口 + 人工复核通道；
- 差评率超过阈值时反向降低投诉者权重；
- 信用分恢复机制（连续 N 次履约可恢复 X 分）。

### 风险 5：UGC 内容合规

匿名树洞 / 课程评价 / 失物招领描述，是涉政 / 涉黄 / 涉黑 / 人身攻击的高发地带。

- **必须**接文本审核 API（阿里云 / 腾讯云内容安全，几分钱一次）；
- 图片上传**必须**做内容识别 + EXIF 清洗（剥离 GPS / 设备 / 时间）；
- 树洞匿名只是"前台匿名"，后台强实名可追溯，并明确告知用户。

不做这些，平台被举报封禁只是时间问题。

### 风险 6：性能目标过于激进的诱惑

很多团队第一版就追"P99 200ms / 99.9% 可用"。**别追**。

- 学生团队没有 7×24 oncall，做不到 99.9%；
- 单体应用 + 单 Redis + 单 MySQL，自然就在 P99 500ms 量级；
- 校园用户对 1~2 秒的延迟容忍度远高于电商。

合理目标：**月可用 99% + 接口 P99 < 1 秒 + 同时在线 2000**。这个目标，单台 8C16G 就能跑得很舒服。

## 四、建议的下一步

1. **先做"硬性决策清单"**：在动手画架构图之前，团队先用半天 review 一遍 6 个关键决策（鉴权 / 资金 / SLA / 隐私 / 内容审核 / 部署模式），把红线钉死。**这一步比选架构更重要**。

2. **用 DDD 画一遍模块边界**：每个核心域有清晰聚合根 + 应用服务接口，模块之间**只通过接口调用 + 应用事件**通信，禁止跨模块直读对方表。这是模块化单体的命脉。

3. **引入 ADR 机制**：每个架构决策都用 ADR（Architecture Decision Record）记录"上下文 / 候选 / 决策 / 后果"，避免半年后忘了为什么这么选导致返工。

4. **保守定 SLA**：99% 月可用 + 2000 同时在线 + P99 < 1s。不要被"工业级指标"绑架，量力而行。

5. **写一份"反 AI 默认建议"清单**：当 AI 推荐微服务、SSO、第三方支付、99.9% SLA、K8s 多 AZ 时，**直接打回**。这是中小团队的常识防御。
