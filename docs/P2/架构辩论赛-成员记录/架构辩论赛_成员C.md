# 一、三种架构核心思路（先统一语境）

* **单体分层架构（Monolith）**

  * 一个 Spring Boot 应用
  * Controller / Service / DAO 分层
  * 模块逻辑在代码层隔离（非物理隔离）

* **微服务架构（Microservices）**

  * 拆成多个服务：用户服务 / 订单服务 / 交易服务 / 跑腿服务 等
  * 每个服务独立部署 + 独立数据库
  * 通信：HTTP / RPC（如 Feign）

* **事件驱动架构（Event-Driven）**

  * 基于消息队列（如 Kafka / RabbitMQ）
  * 服务之间通过“事件”解耦（下单 → 发布事件 → 多方消费）
  * 常与微服务组合使用

---

# 二、6 个维度对比（重点）

## 1. 开发复杂度

* **单体：低**

  * 一个项目，统一调试
  * 不涉及服务拆分、网络通信
  * 最适合快速开发

* **微服务：高**

  * 服务划分本身就很难
  * 需要解决：

    * 服务注册与发现
    * 负载均衡
    * 分布式事务
    * 接口版本管理

* **事件驱动：很高**

  * 除了微服务问题，还要：

    * 消息队列搭建
    * 消息可靠性（重复消费/丢失）
    * 事件设计（很容易设计崩）

👉 **结论：**
单体 ≪ 微服务 < 事件驱动

---

## 2. 可维护性

* **单体：中**

  * 初期清晰
  * 后期容易变“大泥球”（God Object）

* **微服务：高（前提是设计好）**

  * 模块边界清晰
  * 每个服务职责单一

* **事件驱动：中-高（但风险大）**

  * 解耦很好
  * 但**事件链路难追踪（debug 地狱）**

👉 **现实修正：**
在学生项目里：

* 微服务/事件驱动**不一定更可维护**，反而可能更乱

---

## 3. 可扩展性

* **单体：低-中**

  * 只能整体扩展（加机器）
  * 模块无法独立扩容

* **微服务：高**

  * 可以单独扩展“高负载模块”
  * 比如跑腿订单服务单独扩容

* **事件驱动：非常高**

  * 天然支持异步扩展
  * 高并发场景优势明显

👉 但注意：
你们这个项目：

> 校园级应用 ≠ 高并发互联网平台

所以扩展性**不是当前核心矛盾**

---

## 4. 性能

* **单体：高**

  * 无网络调用（本地方法调用）
  * 延迟最低

* **微服务：中**

  * 网络调用增加延迟
  * 需要缓存、熔断等优化

* **事件驱动：中（吞吐高，但延迟高）**

  * 异步 → 响应变慢
  * 但吞吐能力强

👉 对你们来说：

* 单体性能完全够用，甚至过剩

---

## 5. 团队学习成本

* **单体：低**

  * Spring Boot + MySQL
  * 基本就是课程内容

* **微服务：高**

  * 要学：

    * Spring Cloud
    * 服务治理
    * 分布式问题

* **事件驱动：很高**

  * 再加：

    * Kafka / RabbitMQ
    * 消息模型
    * 最终一致性

👉 很现实的一点：

> 学不会 ≠ 做不出来，而是做出来也不稳定

---

## 6. 10 周内落地可行性（最关键）

* **单体：极高**

  * 可以保证功能完整上线
  * 风险最低

* **微服务：低**

  * 很容易：

    * 服务没拆好
    * 联调崩溃
    * 时间耗在基础设施

* **事件驱动：极低**

  * 很可能：

    * 消息系统还没跑稳，项目就结束了

# 四、结合你们项目的“真实约束”给评价

你们的约束是：

* 时间短（10 周）
* 人力少（<10h/周/人）
* 技术栈固定（Spring Boot）
* 场景不复杂（校园服务）

👉 这会导出一个很明确的结论：

## ❌ 微服务 / 事件驱动的问题

不是“做不了”，而是：

* 会**吞掉你们 70% 时间在架构本身**
* 最终：

  * 功能做不完
  * 系统还不稳定
  * 展示效果反而更差

---

## ✅ 推荐方案（务实版本）

### **主方案：单体分层 + 模块化设计（强烈推荐）**

具体建议：

* 单体 Spring Boot
* 但**按业务拆模块**：

  * user
  * order（跑腿）
  * marketplace（二手）
  * lost-found
* 使用：

  * 接口分层（Controller / Service / Repository）
  * DTO / VO 分离
* 数据库：

  * 可以**逻辑分表，但不必分库**

👉 本质：
**“伪微服务（代码分层） + 单体部署”**

---

### **进阶（如果你想体现架构思考）**

可以加一点“轻量事件驱动”：

* 不引入 Kafka
* 用：

  * Spring Event
  * 或简单消息队列（RabbitMQ 单节点）

比如：

* 下单 → 发布事件 → 通知模块处理
* 发布商品 → 异步审核

👉 优点：

* 写在报告里很好看
* 实现成本可控

---

# 五、一句话结论

> 在本项目的时间、人力与复杂度约束下，单体分层架构在开发效率、系统稳定性与落地可行性方面具有显著优势；相比之下，微服务架构与事件驱动架构虽在可扩展性上更优，但其高开发复杂度与学习成本使其不适合在本项目周期内采用。因此，本项目选择以单体架构为基础，并通过模块化设计提升可维护性与后续演进能力。
