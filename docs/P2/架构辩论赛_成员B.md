## 3. 关键技术决策

### 3.1 鉴权与安全

- **方案**：Spring Security + 无状态 JWT（Access Token 30 分钟，Refresh Token 7 天）。
    
- **注册流程**：手机号 → 发送短信验证码（对接第三方平台如阿里云短信/腾讯云短信）→ 验证码校验 → 创建用户 → 签发 JWT。
    
- **校园认证**：用户上传学生证/校园卡图片 → 管理员后台人工审核 → 标记 `campus_verified = true`。
    
- **前弱后强实名**：数据库存真实姓名+学号，但接口返回时仅含昵称+认证标签；姓名学号字段不进入 DTO。
    
- **禁用项**：不引入 OAuth2.0、SAML、CAS、LDAP 等协议（直接违反约束1）。
    

### 3.2 积分体系

- **方案**：单张 `points_account` 表，字段 `user_id`（唯一）、`balance`（INT/bigint，不做小数精度）。积分变动通过数据库事务保证一致性（`UPDATE ... SET balance = balance + ? WHERE user_id = ? AND balance + ? >= 0`）。
    
- **不引入**：分布式事务、TCC、Saga、对账系统（约束2）。
    
- **积分获取与消耗规则**完全由 Service 层逻辑控制，无需对接任何外部支付渠道。
    

### 3.3 信用体系

- **方案**：信用分计算在订单状态变更时同步完成，直接在同一事务中更新 `user` 表的 `credit_score` 字段。无需异步事件驱动。
    
- **接单限制**：查询订单前检查信用分阈值（< 60 禁止发布/接单；< 80 每日接单数限制）。每日接单计数可通过 `COUNT` 查询当日记录或缓存实现。
    
- **申诉流程**：独立表 `credit_appeal`，状态机为 `待处理 → 通过/驳回`，7 日时限和 3 次上限通过业务逻辑校验。
    

### 3.4 隐私设计

- **数据库**：`users` 表包含 `real_name`、`student_id`（明文或对称加密存储，加密密钥在应用配置中）。
    
- **API 返回**：`UserPublicDTO` 仅含 `nickname`、`avatar_url`、`campus_verified`；`UserPrivateDTO`（用户本人查看）可含更多字段。
    
- **历史记录**：默认不对外暴露；仅当用户主动开启"显示历史"时才对外可见（约束3）。
    

### 3.5 性能与可用性

- **目标**：并发 2000（同时在线请求数），月可用性 99%（每月停机不超过 7.2 小时）。
    
- **措施**：
    
    - 数据库连接池使用 HikariCP，配置最大连接数 50~100，按 2000 并发 / 平均单请求耗时 200ms 估算，连接池充足。
        
    - 热点只读数据（如首页信息流）使用 Redis 缓存（可选，视性能测试结果决定，非强制）。
        
    - 单实例部署 + 定时备份即可满足 99% 可用性；无需热备、多活等高可用方案。
        
- **不引入**：Nginx 负载均衡多后端、数据库读写分离、分布式缓存集群等（约束5）。

- **部署方式**：
    
    - 前端：`vite build` 产物上传到 Nginx 静态目录
        
    - 后端：`mvn package` 生成 fat JAR，通过 `systemd` 或 `supervisor` 守护运行
        
    - 数据库：同机部署 MySQL 8 实例（或独立低配云数据库）
        
- **不引入**：Docker Swarm、Kubernetes、CI/CD 流水线等（4 人团队工时有限，手动部署 + 简单 Shell 脚本即可）。
    

## 5. 不推荐的架构方案（明确排除）

|排除方案|违反的约束|原因|
|---|---|---|
|微服务拆分|约束5|增加服务间通信、部署、治理复杂度，远超 2000 并发所需|
|引入消息队列（RocketMQ/Kafka）|约束5|信用积分计算等场景无需异步解耦，同步事务即可|
|API 网关（Kong/Spring Cloud Gateway）|约束5|单体应用无需统一入口层|
|接入 CAS/OAuth2.0 统一认证|约束1|明确禁止，且无需预留（人工审核方案已定稿）|
|对接支付宝/微信支付|约束2|平台仅虚拟积分，真实支付场景为线下自行交付|
|分布式事务框架（Seata）|约束2+5|无真实资金、无跨服务调用，不需要|
