# CampusHub 架构设计文档

## 1. 架构概览

### 1.1 架构风格与硬约束映射 `[人工修订]`

CampusHub 后端最终采用 **模块化单体（Modular Monolith）+ 分层架构（Controller/Service/Repository 三层）**，单仓库、单 Spring Boot 进程部署。具体方案对比与拒绝理由见 `架构候选方案对比表.md` §5；正式决策见 `ADR.md` §ADR-001。

| 核心约束（来自 P1 / 辩论会） | 在架构层的落地 |
| :--- | :--- |
| 4 人团队 / 周期 10 周 / 人均 ≤ 12 小时/周 | 单体部署、零外部基础设施依赖；技术栈与团队既有储备完全一致 |
| 后端栈固定：Java 17 + Spring Boot + MySQL 8 | 全部模块同进程同库，单库本地事务 |
| 信用分 < 80 限单 1 / < 60 禁发禁接，**实时生效** | 跨模块联动用 `ApplicationEvent` + `BEFORE_COMMIT` 同事务执行（见 ADR-002） |
| 隐私"后台强实名 / 前台弱展示"，禁止真实姓名 / 学号外泄 | 架构层强制 DTO/VO 转换 + ArchUnit CI 校验（见 ADR-004） |
| 不接受真实货币托管 / 第三方支付分账 | 平台仅"虚拟积分"流转，无支付通道接入 |
| 性能目标 2000 并发 / 月可用 99% / P95 ≤ 2s | 单 Spring Boot 实例 + HikariCP + MySQL 8 即可达标，Redis 默认不启用（见 ADR-005） |
| 鉴权不引入 SSO / OAuth / CAS | 手机号 + 短信验证码 + 学生证人工审核 + JWT 无状态（见 ADR-003） |

### 1.2 总体架构（文字描述）`[人工修订]`

整体系统由 **4 类逻辑组件** 构成，按数据流自上而下排列：

1. **客户端层（Client）**
   - 学生端：H5 / Web 单页应用（React 19 + TS 5.9 + Vite 8 构建产物，由 Nginx 提供静态托管）；
   - 管理端：独立 Web 单页应用，与学生端共用一套后端但走 `/api/admin/**` 前缀路径；
   - 通信协议：HTTPS + RESTful JSON；私信模块在长会话上叠加 WebSocket 通道（可选启用，见 §3.1 模块 `im`）。

2. **接入层（Edge）**
   - **Nginx**：单一入口，承担 TLS 终止、静态资源托管、API 反向代理、基础限流（按 IP & URI）三类职责；
   - 不引入独立 API Gateway（如 Spring Cloud Gateway）——理由见 ADR-001。

3. **应用层（Application）**
   - **单一 Spring Boot 进程**，内部按业务域切分为 11 个顶层包：`auth`、`user`、`task`、`trade`、`edu`、`team`、`im`、`notify`、`credit`、`report`、`admin`、`search`；
   - 每个包内严格保持 Controller / Service / Repository 三层；
   - 跨包通信只允许走两条路径：① 应用服务接口 `XxxApi`（同步、强一致）；② Spring `ApplicationEvent` + `@TransactionalEventListener`（同步事务内 / 异步可最终一致，见 ADR-002）；
   - **明确禁止**：跨包直接 `@Autowired` 他人的 Repository、跨包共享 Entity、跨包外键。

4. **资源层（Resource）**
   - **MySQL 8**：单实例、单库；按业务域用表名前缀（`user_*`、`task_*`、`credit_*` 等）做逻辑分区；事务级别 `READ COMMITTED`；
   - **对象存储 MinIO**：三个固定桶（`verify-material`、`task-proof`、`study-resource`），权限按桶隔离；
   - **第三方短信通道（阿里云短信）**：仅用于鉴权验证码下发；
   - **Redis 7（可选）**：P2 阶段默认关闭，仅保留配置开关，启用条件由 ADR-005 控制；【不用】
   - **可观测性**：基础日志（应用日志 + 审计表）+ Spring Boot Actuator 健康检查端点。

## 2. 架构关键不变量

下面 6 条不变量被提升到架构级强约束，违反者**必须**在 PR 阶段被打回，不得进入主干：

1. **跨模块通信只能走 `XxxApi` 接口或 `ApplicationEvent`**；任何 `module-A` 直接 `@Autowired module-B.SomeRepository` 的代码 = 违规。
2. **业务表归属唯一**：每张表在物理上只属于一个业务模块；模块 A 想读模块 B 的数据，必须通过 B 的 `XxxApi` 接口。
3. **Controller 出参禁止使用 Entity**；公开用户对象统一为 `PublicUserVO = { nickname, avatarUrl, verifiedTag }`（见 ADR-004）。
4. **扣信用分 / 改积分类的事件 Listener 必须显式声明 `phase = BEFORE_COMMIT`**；通知 / 站内信类 Listener 才允许 `AFTER_COMMIT + @Async`（见 ADR-002）。
5. **管理员后台接口必须挂 `@PreAuthorize` 注解**；`/api/admin/**` 路径下才可放行真实姓名 / 学号字段。
6. **日志输出必须使用脱敏 DTO**；禁止直接 `log.info(user)`（见 ADR-004 §3 修订点）。

## 3. 模块划分说明

### 3.1 模块清单与职责边界 `[人工修订]`

| 模块 | 核心职责 | 不负责的事情（边界外） | 关键数据表前缀 |
| :--- | :--- | :--- | :--- |
| `auth` | 手机号 + 短信验证码登录、JWT 签发与续签、学生证人工审核状态机 | 不做用户资料 / 不做权限 RBAC | `auth_*` |
| `user` | 昵称管理、头像、隐私开关（默认隐藏 3 项）、前台脱敏视图 | 不做认证 / 不做信用 | `user_*` |
| `task` | 跑腿任务发单、抢单（乐观锁）、状态机流转（待接单→进行中→待确认→已完成）、自接限制 | 不做内容审核 / 不做仲裁 | `task_*` |
| `trade` | 二手商品上架、库存（数量字段）、字段扩展（新旧成色 / 配送时限）、图片 EXIF 清洗 | 不做资金（无支付） / 不做物流 | `trade_*` |
| `edu` | 课程评价、学习资料上传、辅导任务发布、违禁词同步拦截 | 不做学籍 / 不做成绩 | `edu_*` |
| `team` | 招募发布、技能标签匹配、申请审核、限频 | 不做即时通讯（走 `im`） | `team_*` |
| `im` | 站内私信、任务关联会话、未读计数 | 不做通知（走 `notify`） | `im_*` |
| `notify` | 系统通知 / 站内信 / （可选）短信广播 | 不做 IM 长会话 | `notify_*` |
| `credit` | 信用分计算、积分账户、冻结/结算/解冻、阈值限制（< 80 限单 1 / < 60 禁发禁接） | 不做仲裁裁决 / 不做举报 | `credit_*` |
| `report` | 举报受理、差评申诉（7 日 / 3 次）、证据管理、管理员裁决执行 | 不做积分变动（委托 `credit`） | `report_*` |
| `admin` | 认证审核、内容审核、封禁、配置中心、操作审计 | 不做业务逻辑 / 仅做"操作触发" | `admin_*` |
| `search` | 多维筛选、关键词检索、热门榜（低优先级） | 不做推荐算法 / 不做画像 | `search_*` |

### 3.2 模块依赖关系（文字描述）`[人工修订]`

模块间依赖按"调用方向"分为三层（自下而上调用、不允许反向）：

**Layer L1 — 基础域（无下游依赖）**
- `auth`：所有模块的鉴权前置；
- `user`：被绝大多数模块查询"昵称 + 认证标签"；
- `credit`：信用分 / 积分账户的唯一权威。

**Layer L2 — 业务域（依赖 L1）**
- `task` ← 依赖 `auth`、`user`、`credit`；
- `trade` ← 依赖 `task`（继承通用任务字段）、`user`、`credit`；
- `edu` ← 依赖 `auth`、`user`、`credit`、`task`（辅导任务复用任务状态机）；
- `team` ← 依赖 `auth`、`user`；
- `im` ← 依赖 `auth`、`user`、`task`（任务关联会话）。

**Layer L3 — 横切域（依赖 L1 + L2）**
- `notify` ← 监听 L2 各业务的 `ApplicationEvent`，向用户推送通知；
- `report` ← 依赖 `task`、`credit`、`im`（取证），并向 `credit` 请求执行扣分 / 解冻；
- `admin` ← 依赖 `auth`、`report`、`credit`，承载后台审核与运营操作；
- `search` ← 只读依赖 `task`、`edu`、`trade`，自身维护倒排或定时构建。

**关键规则（强制约束）**：
- 所有依赖必须**单向**，不得形成环；
- 严禁出现"L1 模块依赖 L2/L3 模块"——这是模块化单体最容易出现的"反向腐坏"；
- 跨层调用必须通过 `XxxApi` 接口或 `ApplicationEvent`，详见 §4.1。

## 4. 模块间接口规范

### 4.1 跨模块通信的两种合法路径 `[人工修订]`

| 路径 | 适用场景 | 一致性语义 | 典型代码形态 |
| :--- | :--- | :--- | :--- |
| **`XxxApi` 同步接口** | 调用方需要立即获得返回值（如查询信用分、查询用户昵称） | 强一致（同进程、本地事务内） | `creditApi.getScoreOf(userId)` |
| **`ApplicationEvent` 事件通知** | 源头模块触发联动（如发单后扣冻结积分、违约后扣信用分） | 默认强一致（`BEFORE_COMMIT` 同事务）；通知 / 归档类才走 `AFTER_COMMIT + @Async` | `eventPublisher.publishEvent(new TaskAcceptedEvent(...))` |

### 4.2 模块对外接口（`XxxApi`）的契约规范 `[人工补充]`

每个业务包必须提供一份对外接口（接口包路径：`com.campushub.<module>.api`），命名为 `<Module>Api`，作为该模块对其他模块的唯一同步入口：

```java
// 仅作示意，详细实现见 P3 编码阶段
public interface CreditApi {
    int getScoreOf(long userId);           // 查询信用分
    void deduct(long userId, int delta, String reasonCode);  // 扣分（带原因码）
    void freeze(long userId, int points);  // 冻结积分
    void unfreeze(long userId, int points);
    void settle(long userId, int points);  // 结算（冻结→消费）
}
```

**契约约束**：
1. **入参 / 返回值禁止使用 Entity 类型**，必须使用基础类型或 DTO；
2. **方法必须幂等或显式标注 `@NotIdempotent`**（如 `deduct` 必须标注 reasonCode + 业务上下文 ID 用于去重）；
3. **跨模块异常必须翻译**：`CreditApi.deduct` 内部抛 `CreditNotEnoughException`，对外暴露为 `BizException("CREDIT_NOT_ENOUGH")`，下游不依赖具体异常类。

### 4.3 事件契约规范（`ApplicationEvent`）`[人工补充]`

事件类必须放在源头模块的 `event/` 子包，命名遵循"主语 + 动词过去式"：

| 事件类 | 发布者 | 订阅者 | 触发时机 / phase |
| :--- | :--- | :--- | :--- |
| `TaskAcceptedEvent` | `task` | `credit`（冻结积分） | `BEFORE_COMMIT`（同事务） |
| `TaskCompletedEvent` | `task` | `credit`（结算）、`notify`（站内信） | `BEFORE_COMMIT` + `AFTER_COMMIT` 分别订阅 |
| `TaskCanceledEvent` | `task` | `credit`（解冻）、`notify` | `BEFORE_COMMIT` + `AFTER_COMMIT` |
| `BadReviewSettledEvent` | `report` | `credit`（扣信用分）、`notify` | `BEFORE_COMMIT` + `AFTER_COMMIT` |
| `UserVerifiedEvent` | `auth` | `user`（更新认证标签）、`notify` | `AFTER_COMMIT`（弱一致即可） |
| `ReportSubmittedEvent` | `report` | `notify`（通知管理员）、`admin`（落审计表） | `AFTER_COMMIT + @Async` |

**事件设计纪律**：
- 事件类**必须**包含业务幂等键（如 `taskId + version`），方便下游做去重；
- 事件类**必须** `@Immutable`，禁止下游 Listener 修改字段；
- 事件 Listener 中**禁止再次发布会闭环的事件**（防死循环）。

### 4.4 关键 REST API 清单（按 `OpenAPI 3.1` 契约定义）`[人工修订]`

#### 4.4.1 `auth` 模块

- `POST /api/auth/send-code`
  - 请求：`{ "phone": "string(11)" }`
  - 响应：`{ "requestId": "string(32)", "expireSeconds": 300 }`
  - 限流：单手机号 60s 内 ≤ 1 次；单 IP 60s 内 ≤ 5 次；单手机号 24h 内 ≤ 20 次；单 IP 24h 内 ≤ 200 次（见 ADR-003）。
- `POST /api/auth/login-by-code`
  - 请求：`{ "phone":"string(11)", "code":"string(6)" }`
  - 响应：`{ "token":"jwt", "expiresIn": 7200, "verifyStatus":"pending|approved|rejected" }`
- `POST /api/auth/student-verification`
  - 请求：`multipart/form-data`，`cardType:enum`、`realName:string(2..20)`、`studentNo:string(6..20)`、`images<=3`
  - 响应：`{ "verifyTicket":"string(32)", "status":"pending" }`
  - 合规：原始证件图片审核通过后 30 日内自动删除，仅留 SHA-256 + 审核结论。

#### 4.4.2 `task` 模块

- `POST /api/tasks`
  - 请求：`taskType:enum`、`title:string(5..60)`、`detail:string(10..1000)`、`rewardPoint:int(>=0)`、`deadline:datetime`
  - 响应：`{ "taskId":"long", "status":"PENDING_ACCEPT" }`
  - 校验：调用 `creditApi.getScoreOf(userId) < 60` 返回 `403`；积分不足返回 `409`。
- `POST /api/tasks/{taskId}/accept`
  - 并发控制：基于 `version` 字段乐观锁（`UPDATE ... WHERE version = ?`），保证同一任务仅 1 人成功接单；
  - 同事务内调用 `creditApi.freeze(...)` 冻结接单方押金；
  - 响应：`200 OK` 或 `409 TASK_ALREADY_ACCEPTED`。
- `POST /api/tasks/{taskId}/complete-proof`
  - 请求：完成凭证图片 ≤ 3 张、说明 ≤ 300 字
  - 响应：`{ "status":"WAIT_CONFIRM" }`

#### 4.4.3 `credit` 模块

- `POST /api/credits/appeals`
  - 请求：`badReviewId:long`、`evidenceImageUrls:list<=5`、`statement:string(<=500)`
  - 规则：差评后 7 日内可发起；同事件最多 3 次。
  - 响应：`{ "appealId":"long", "status":"PENDING" }`
- `GET /api/credits/me`
  - 响应：`{ "creditScore":int, "dailyAcceptLimit":int, "canPublish":bool, "canAccept":bool }`
  - 规则映射：`creditScore < 80` → `dailyAcceptLimit=1`；`< 60` → `canPublish=false, canAccept=false`。

#### 4.4.4 全局公共输出契约（`PublicUserVO`）

```json
{
  "userId": 123456,
  "nickname": "校园路人甲",
  "avatarUrl": "https://oss.example.com/avatars/...",
  "verifiedTag": true
}
```

**严禁**在前台 API 返回字段中出现：`realName`、`studentNo`、`idCardNo`；`phone` 字段如必须返回则强制脱敏为 `138****1234`。详见 ADR-004。

### 4.5 数据一致性与异常补偿 `[人工修订]`

| 场景 | 一致性方案 | 异常补偿 |
| :--- | :--- | :--- |
| 发单 → 冻结积分 | 同库本地事务（`@Transactional`） | 抛异常 → 整体回滚 |
| 接单 → 冻结押金 | 乐观锁 + 同库本地事务 | `version` 冲突 → 返回 409，前端重试 |
| 任务完成 → 结算积分 | `TaskCompletedEvent` + `BEFORE_COMMIT` | 事件 Listener 异常 → 整体回滚 |
| 短信发送失败 | 同步重试 ≤ 2 次（指数退避 1s/3s）| 失败返回 `SMS_SEND_FAILED`，前端 60 秒后重试 |
| 对象存储上传失败 | 两阶段：先上传文件、后落库 | 任一阶段失败立即回滚业务事务 + 删除已上传临时对象；后台每 60 分钟扫描临时桶清理 24 小时以上孤儿文件 |
| 仲裁后扣分 | 同事务（`BEFORE_COMMIT`） | 异常 → 整体回滚，不留中间态 |
| 通知 / 站内信 | `AFTER_COMMIT + @Async` | 失败仅打日志、不影响主流程；通知失败补偿任务每 10 分钟重投 |

## 5. 技术选型说明

### 5.1 完整技术栈表（按 P2 §2.2 模板）`[人工修订]`

| 层次 | 选择 | 选择理由（可验证） | 与约束的映射 |
| :--- | :--- | :--- | :--- |
| **前端框架** | React 19 + TypeScript 5.9 + Vite 8 + ESLint 9 | 与 P1 锁定栈一致；可直接复用既有脚手架与规范 | 技术栈基线不可更改 |
| **后端框架** | Java 17 + Spring Boot 3.x + Maven | 团队课程已覆盖；Spring 原生支持 `ApplicationEvent` + `@Transactional` | 4 人团队可维护、零外部学习成本 |
| **数据库（主）** | MySQL 8 单实例、单库 | 单库本地事务即可保证信用 / 积分 / 任务状态强一致 | 禁止分布式事务；并发 ≤ 2000 单库够用 |
| **数据库（次）** | 无 | 当前规模无需读写分离 / 分库分表 | 避免运维超额复杂度 |
| **缓存中间件** | Redis 7 *（可选，默认关闭）* | P2 默认走 MySQL；ADR-005 触发条件下再启用 | 避免过早优化 |
| **消息中间件** | 不引入；用 Spring `ApplicationEvent` 替代 | 异步解耦诉求被进程内事件完美满足；信用规则强一致也得以保留 | 见 ADR-002 |
| **对象存储** | MinIO（自部署 / 校园内网或云服务器） | 学生证、资料附件、凭证图片需持久化；可控、低成本 | 资料上传 / 审核流程需求 |
| **短信服务** | 阿里云短信 | 鉴权硬约束要求短信验证码；阿里云通道稳定 + 校园场景成本可控（≤ 300 元/月） | 见 ADR-003 |
| **网关 / 反向代理** | Nginx（不引入 API Gateway） | TLS 终止 + 静态托管 + 反向代理 + 基础限流 一站搞定 | 4 人团队运维带宽紧张 |
| **鉴权框架** | Spring Security + JWT（无状态） | 与模块化单体演进路径兼容；服务端不存 Session | 见 ADR-003 |
| **可观测性** | Spring Boot Actuator + 应用日志 + 审计表 | 关键流程（认证审核、积分流转、仲裁）可追踪 | 满足验收需要的最小可观测性 |
| **部署方式** | 单机 Docker Compose（Nginx + Spring Boot + MySQL 8 + MinIO + 可选 Redis） | 部署步骤可脚本化；可在校园内网或单台云服务器落地 | 满足 99% 月可用 + 4 人运维 |
| **CI / 校验** | GitHub Actions + ArchUnit + 自定义 PMD 规则 + OpenAPI 契约校验 | 守护 §2 列出的 6 条架构不变量 | 防止模块化单体退化 |

### 5.2 技术选型的"显式拒绝清单"`[人工修订]`

为避免后续人员怀疑"为什么不用 X"，把团队明确**拒绝**的技术与拒绝理由钉在文档里：

| 拒绝项 | 拒绝理由 |
| :--- | :--- |
| Spring Cloud Alibaba（Nacos / Gateway / Sentinel / Seata） | 微服务过度设计，违反 ADR-001 |
| RabbitMQ / Kafka / RocketMQ | 异步窗口期会让"信用分实时生效"规则失效，违反 ADR-002 |
| Redis Cluster / Redis 哨兵 | 无热点数据 + 4 人团队运维带宽紧张，违反 ADR-005 |
| Elasticsearch | 当前并发与查询模式 MySQL FullText 已够用；ES 是远期方案 |
| Kubernetes / Docker Swarm | 4 人团队无运维带宽支撑容器编排 |
| 学校 CAS / SSO / 教务 OAuth | 法务责任陷阱 + 接入审批超过项目周期，违反 ADR-003 |
| 第三方支付（支付宝 / 微信支付） | 平台无支付牌照，违反 P1 资金红线 |
| 分布式事务（Seata / TCC / Saga） | 单库本地事务已满足；引入即过度设计 |

### 5.3 部署拓扑（文字描述）`[人工修订]`

部署拓扑采用**单机 Docker Compose** 模式，所有组件运行在同一台云服务器（建议规格 4C8G / 100GB SSD）：

```
[ 公网 / 校园网 ]
        │ HTTPS:443
        ▼
┌────────────────────────────────────────────────────┐
│            云服务器（4C8G / Ubuntu 20.04）          │
│                                                    │
│   ┌──────────────────────────────────────────┐    │
│   │ Nginx (容器:80/443)                       │    │
│   │  ├── 静态资源托管 (FE_Student / FE_Admin) │    │
│   │  ├── 反向代理 → Spring Boot:8080         │    │
│   │  └── 基础限流（按 IP & URI）              │    │
│   └──────────────────────────────────────────┘    │
│                       │                            │
│                       ▼                            │
│   ┌──────────────────────────────────────────┐    │
│   │ Spring Boot Monolith (容器:8080)          │    │
│   │  └── fat-jar（11 个业务包内嵌）           │    │
│   └──────────────────────────────────────────┘    │
│         │             │              │             │
│         ▼             ▼              ▼             │
│   ┌──────────┐  ┌───────────┐  ┌────────────┐    │
│   │ MySQL 8  │  │  MinIO    │  │ Redis 7    │    │
│   │ (3306)   │  │  (9000)   │  │ (6379)     │    │
│   │          │  │  3 buckets│  │ (默认关闭) │    │
│   └──────────┘  └───────────┘  └────────────┘    │
│                                                    │
│   日志卷 / 备份卷 / Compose 编排文件挂载到宿主机  │
└────────────────────────────────────────────────────┘
        │
        ▼
[ 阿里云短信 SMS API（外网） ]
```

**关键部署要点**：
- 所有容器同 docker-compose 定义，`docker compose up -d` 一键启停；
- MySQL 数据卷与 MinIO 数据卷挂载到宿主机，**严禁**只存在容器内（防容器删除即数据丢失）；
- 每日 03:00 自动 `mysqldump` 全量备份到独立磁盘（保留 7 天）+ MinIO 副本复制到独立桶；
- Spring Boot 容器配置健康检查（`/actuator/health`），失败 3 次自动重启；
- Nginx 容器开启 access_log / error_log，按日期切割并保留 30 天。

## 7. 架构验收要点（验收 / 测试用例蓝本）`[人工修订]`

### 7.1 性能验收

- **VPF-01**：`POST /api/tasks/{id}/accept` 在 500 并发下抢同一批任务，**重复接单率 = 0**（乐观锁有效性验证）；
- **VPF-02**：任务大厅与课程评价查询在 2000 并发下，P95 ≤ 2s，错误率 < 1%；
- **VPF-03**：写接口（发单 / 接单 / 评价）在 2000 并发下，P95 ≤ 1s。

### 7.2 安全 / 合规验收

- **VSF-01**：抓包 + OpenAPI 契约校验，**前台所有响应体不含 `realName / studentNo / idCardNo`**；`phone` 字段强制脱敏；
- **VSF-02**：构造管理员越权场景，未挂 `@PreAuthorize` 的 `/api/admin/**` 接口必须 CI 检测失败；
- **VSF-03**：日志中 grep 真实姓名 / 学号 / 11 位手机号原文，**命中数 = 0**。

### 7.3 业务规则验收

- **VBR-01**：信用分 79 / 59 账号分别验证"每日限接 1 单"与"禁止发布 / 接单"是否生效；
- **VBR-02**：差评第 8 天发起申诉应失败；同事件第 4 次申诉应失败；
- **VBR-03**：跑腿订单违约后，**信用扣分必须在事务提交前完成**（即与订单状态变更同事务）；
- **VBR-04**：任务超时状态流转的实际触发时间与截止时间偏差 ≤ 5 分钟。

### 7.4 可用性 / 故障演练

- **VAV-01**：模拟 MySQL 短暂 1 分钟不可用，应用层应能在恢复后自动重连，无需人工干预；
- **VAV-02**：阿里云短信通道失败注入测试，前端 60 秒后允许重试，无重复扣费；
- **VAV-03**：MinIO 上传失败时业务事务必须回滚，数据库与对象存储无孤儿数据。
