**hyw**：大家都到了，那咱们就开始吧。今天这个会很重要，主要是把咱们软工二大作业 CampusHub 的后端架构定下来，这是接下来几周开发的基础。
在大家提方案之前，我作为队长，有必要再重申一下咱们在 P1 阶段定死的几条硬性规则。
第一，咱们团队就 4 个人，大家这学期还有其他专业课，平均下来每个人每周能投入在这个项目上的有效工时差不多只有 12 个小时。项目周期满打满算不到 10 周。时间非常紧。
第二，平台里绝对不碰真实资金，只做虚拟积分和信息撮合。所以千万不要考虑去接第三方支付接口，也尽量别碰复杂的金融级分布式事务方案。
第三，工程指标方面，我们目标做出的并发是 2000，月可用性 99%，不用按照大厂那种 99.99% 的高可用或者毫秒级延迟的指标来要求自己，没必要过度设计。
第四，隐私和信用机制非常严格。后台必须强实名，但前端绝对不能展示用户的真实姓名和学号。另外，信用分低于 80 每天只能接一单，低于 60 直接封号，这种类似的规则必须是实时生效的。
目前候选的架构有四个：纯 MVC、分层架构、微服务、事件驱动。大家评估一下，咱们到底用哪个比较合适？

**czh**：那我先说一下我的想法。我个人非常倾向于使用微服务架构。
大家看咱们的需求规格说明书，CampusHub 的业务模块其实挺复杂的，包括了跑腿代取、二手交易、学习辅导、组队匹配、失物招领、树洞论坛等等很多，再加上底层的用户、积分、信用模块。这算下来差不多有将近十个相对独立的业务领域了。
如果我们把这么多业务全塞在一个工程里，代码量肯定会成倍增加，后期维护起来经常会牵一发而动全身。如果我们采用 Spring Cloud Alibaba 这一套成熟的微服务架构，把跑腿、交易、用户等核心域拆分成独立的服务，用 Nacos 做注册中心，再挂一个 API Gateway 当网关。这样咱们每个人负责两三个独立的服务，开发和部署完全互不干扰，连 Git 冲突都能少很多。而且，掌握微服务架构对咱们以后找实习非常有帮助，这也是一个很好的实战锻炼机会。

**hyw**：czh，我非常理解你想在项目里应用前沿技术的心情，能把微服务落地确实是一个很大的加分项。但是作为队长，时间和风险方面可能不太行。
咱们每周的工时只有 12 个小时。如果要搞微服务，第一两周咱们可能连一行核心业务代码都写不了，全在折腾服务器环境、Docker 部署、排查跨域问题啥啥的。
最要命的是，微服务会带来分布式事务的痛点。举个例子，一个跑腿订单违约了，你需要调用跑腿服务去改订单状态，调用信用服务去扣分，还要调用积分服务退还押金。在单体架构里，这就是一个本地事务的事，一旦某个步骤出错，直接抛异常全部回滚。但在微服务里，这就跨了三个服务，需要引入 Seata 这样的分布式事务框架，或者手写 TCC 补偿逻辑来保证数据一致性。咱们 P1 明确说了不碰企业级的过度设计，为了一个虚拟积分去搭一套分布式事务机制，如果出了 Bug 导致数据不一致，咱们这十几周的努力可能就白费了，连个能跑通的完整链路都拿不出来。

**cxf**：我也同意 hyw 的看法。从写前端的角度来说，最怕的就是后端接口不稳定、链路太长。如果你们搞微服务，服务之间互相调用，万一网络超时或者某个子服务挂了，联调起来简直是噩梦，都不知道是谁的锅。
既然咱们时间这么紧，为什么不干脆用最简单的纯 MVC 架构呢？
就是前端发 HTTP 请求过来，后端 Controller 接收，然后在 Controller 里面直接写 SQL 查数据库或者更新数据库，查完直接把数据转成 JSON 返回。没有中间那些繁琐的 Service 层、DAO 层，逻辑直来直去，大家写得也快，咱们也能尽早进入前后端联调阶段。

**lcy**：cxf，你这个想法其实比微服务还要危险。
我感觉如果是做个简单的图书管理系统，纯 MVC 确实够了。但咱们 CampusHub 的业务逻辑其实并不简单。如果你把所有 SQL 和判断逻辑都写在 Controller 里，代码会变得极其臃肿。
比如“扣信用分”这个动作，跑腿违约要扣分，二手交易被举报成立要扣分，树洞发违规帖子也要扣分。你难道要在三个不同的 Controller 里复制粘贴三遍一模一样的 SQL 吗？以后要是修改扣分规则，漏改了一个地方就是一个严重的 Bug。
而且，刚刚 hyw 也说了，前端绝不能展示用户的真实姓名和学号。
如果你在 Controller 里直接查数据库，拿到的 User 实体类里是包含真实姓名和学号的。按照纯 MVC 的写法，开发人员为了省事，很容易顺手就把这个 User 对象直接 return 出去了。这就造成了极其严重的隐私泄露。咱们必须得有一层来专门做 DTO（数据传输对象）的转换，把敏感信息全部过滤掉。

**cxf**：哦，对对对，你提醒我了，隐私数据暴露确实是个大问题，如果不小心把学号漏出去了，平台肯定会被投诉。那看来 Controller 里不能直接写业务和查库了，确实得把表现层和逻辑层分离开。

**lcy**：是的，必须要有独立的 Service 层来处理复杂的业务逻辑。不过，就算是采用分层架构，如果按照传统的紧耦合写法，Service 层也会变得不堪重负。
顺着刚才那个订单违约的例子，在跑腿服务（`ErrandService`）的 `cancelOrder` 方法里，你得写：更新订单状态 -> 调用 `CreditService` 扣分 -> 调用 `PointsService` 退还虚拟积分 -> 调用 `NotifyService` 发送站内信。
这就导致跑腿模块强耦合了其他三个不相关的模块。如果以后我们要加一个新的联动逻辑，比如违约后还要做记录归档，你就得接着在这个方法里加代码。
所以我倾向于采用**事件驱动架构（Event-Driven）**。
我们可以引入 RabbitMQ 或者 Kafka。当跑腿订单违约后，跑腿模块什么都不用管，只要往消息队列里发一条“订单已取消”的消息，然后就可以直接给前端返回成功了。剩下的扣分、退钱、发通知的操作，由信用模块和积分模块自己去监听这个消息，异步处理。这样各个模块之间就彻底解耦了，而且系统的响应速度会非常快，用户体验很好。

**hyw**：lcy，你的解耦思路非常清晰，事件驱动在处理复杂的业务状态联动时确实是一种很优雅的设计模式。但是，引入外部 MQ（比如 RabbitMQ）在这个项目里同样存在过度设计的问题，并且会带来一个无法接受的业务漏洞。
首先，部署和维护一个高可用的 RabbitMQ 节点，对咱们现有的服务器资源和运维精力都是个不小的挑战。
其次，我们刚说了，信用分低于 80 每天限接 1 单，信用分低于 60 禁止接单。这是强一致性的业务要求。
如果你用 RabbitMQ 异步去处理扣分，这中间是存在网络延迟和消息排队时间的。如果某个用户违约了，系统异步去扣分，在这个扣分动作还没执行完的几秒钟甚至几十秒内，他在数据库里的信用分依然是满分。这就产生了一个时间差漏洞。如果有人利用脚本，完全可以在被扣分限流之前，瞬间接走几十个跑腿单，咱们的信用限制机制就彻底失效了。

**lcy**：这点确实是我疏忽了。异步解耦虽然降低了耦合度、提升了响应速度，但确实牺牲了事务的强一致性。如果我们的核心信用机制必须保证本地事务的强一致，那依赖外部消息队列这条路是不是就走不通了？我们要怎么在不引入大组件的情况下解决代码强耦合的问题呢？

**hyw**：其实 Spring 框架本身就给我们提供了一个很好的折中方案，可以采用**基于 Spring ApplicationEvent 的内部事件驱动机制**，也就是依然在单体架构下运作。
我们不需要引入任何外部的中间件。在跑腿模块处理完状态变更后，直接发布一个 Spring 内部的事件对象。然后让信用模块和积分模块分别写一个监听器（Listener）来处理这个内部事件。
因为它们都是在同一个 JVM 进程里运行的，Spring 默认会在同一个线程、同一个数据库事务中同步执行这些监听器。也就是说，一旦后面的扣分或者退积分抛出异常报错，整个最开始的订单违约操作也会被一起回滚，这就保证了绝对的数据强一致性。
这样一来，在代码的物理结构上，跑腿模块没有直接去 import 信用模块的 Service 类，实现了你想要的业务解耦；而在运行时环境里，它们又被包裹在一个本地事务中，保证了数据的安全性。

**czh**：我明白了。hyw 你的意思就是，咱们在最后的项目部署上依然是一个朴实无华的单体 Spring Boot 应用程序，但在代码目录结构的组织上，我们按照微服务的领域去划分好不同的业务 Package（比如 `user`、`errand`、`credit`），并且在开发规范里定死：各个 Package 之间尽量通过内部 Event 或者专门的公共 Service 接口交互，绝对不能直接越权去查对方底层的表。

**hyw**：理解得完全正确，这对于咱们团队目前的状况来说是最优选。
对于咱们的系统目标并发 2000，一个单体的 Spring Boot 加上配置合理的 HikariCP 数据库连接池，配合单节点的 MySQL 数据库，处理起来绰绰有余。完全没有网络通信的额外开销，性能反而比微服务更具优势，也不用去折腾那些复杂的分布式事务组件，大家可以把精力花在把业务逻辑写对、把 DTO 转换写严谨上。

**czh**：听你这么一说，确实有道理。微服务和外部的重型 MQ 对我们现在的工时预算来说，风险太高了。我同意用这种模块化单体的分层架构，既保证了我们的开发交付效率，又能让代码结构保持清晰和易于维护。

**lcy**：我也同意。利用内部 Spring Event 完美解决了我刚刚提到的模块强耦合问题，同时没有牺牲业务逻辑要求的强一致性，这个方案非常务实，落地性很强。

**cxf**：我也完全赞同。这么定下来的话，就能很快拿到稳定、链路清晰的接口了。而且有了专门的 Service 层和 Controller 层来做 DTO 数据转换，前端展示数据也不怕不小心暴露用户的隐私信息了。

**hyw**：好，既然大家从各自的视角出发都达成了共识，那我们的整体架构就正式拍板了。我们采用单体分层架构，融合模块化单体和内部事件驱动的思想。稍后我会把咱们讨论的结论和规则红线整理成文档，大家按照这个架构规范开始搭建工程结构并划分接口吧。

## 第二部分：最终决定

经过团队四人的充分讨论与辩论，结合 CampusHub 项目的具体约束条件，针对后端系统架构做出了最终决策：

### 1. 最终选择了什么方案？

本项目最终决定采用：**单体分层架构（Layered Architecture）**，并在代码结构上贯彻 **模块化单体（Modular Monolith）** 的设计思想。

具体技术落地上：
- 系统作为一个单一的 Spring Boot 进程部署，连接一个独立的 MySQL 数据库。
- 代码工程内部严格划分为三层：表现层（Controller）、业务逻辑层（Service）和数据访问层（Repository/DAO）。
- 在复杂业务逻辑的处理与多模块解耦上，不引入外部消息中间件，而是采用 Spring 框架原生的 `ApplicationEvent` 机制进行应用内部的事件发布与监听，并配合 `@Transactional` 注解保证业务数据的本地强一致性。

### 2. 为什么选择该方案？

该方案是契合项目现状与团队资源的最优解，主要原因如下：
- **符合工时与团队规模约束**：作为 4 人学生团队，且人均投入为 12 小时/周。单体架构的运维和部署成本极低，避免了将大量时间消耗在基础设施搭建上，团队可以将有限的精力全部集中在核心业务逻辑的实现上，确保项目能高质量按时交付。
- **满足性能目标**：项目的目标并发为 2000。在单体架构下，利用合理的线程池和数据库连接池，由于没有跨网络进程的 RPC 调用损耗，足以轻松应对该量级的并发访问。
- **保障数据强一致性**：业务中存在大量依赖信用分和积分的强一致性场景（如“信用分低于 80 限流”规则）。单体分层架构依靠数据库的本地 ACID 事务，能够有效杜绝分布式环境下的数据不一致问题，保证平台信用的权威性。
- **坚守隐私保护底线**：分层架构强制要求底层的业务实体（Entity）与展现给前端的数据传输对象（DTO）严格分离。在 Controller 层进行专门的数据脱敏转换，从根本上防止了包含学号、真实姓名等底层敏感数据被意外暴露。
- **兼顾代码解耦与演进能力**：通过模块化单体的包隔离规范以及内部的 Spring Event，系统在单体内部实现了业务领域间的逻辑解耦，避免了 Service 层出现错综复杂的方法，保证了代码的长期可维护性。

### 3. 为什么不选其他的方案？

- **为什么不选微服务（Microservices）？**
  这是典型的过度设计。对于短工时的 4 人小团队而言，微服务会带来灾难级的运维负担（需要维护网关、注册中心、容器化部署等环境）。更重要的是，微服务会将原本简单的积分和信用流转撕裂为分布式事务，而团队并无多余精力引入 Seata 等重型框架来处理异常补偿，这会极大地增加系统崩溃的风险。

- **为什么不选事件驱动架构（引入 RabbitMQ/Kafka）？**
  虽然外部消息队列能带来更彻底的异步解耦和响应速度提升，但在我们的业务中，由于信用分限制机制要求实时生效，异步处理不可避免存在的网络延时会产生严重的业务漏洞（用户可利用消息排队的时间差狂刷订单）。同时，引入沉重的外部消息中间件也可能超出服务器的承载能力。

- **为什么不选纯 MVC 架构（无 Service 层的极简模式）？**
  纯 MVC 模式将所有的 SQL 操作和业务规则校验杂揉在 Controller 层，这会导致核心的业务算法无法被多处复用，只能到处复制粘贴。此外，代码极度臃肿，逻辑混乱，后续难以进行单元测试，并且缺少严谨的 DTO 映射防线，极易因为某位开发人员的疏忽将带有敏感隐私的数据库模型直接返回给客户端，造成严重的安全事故。
