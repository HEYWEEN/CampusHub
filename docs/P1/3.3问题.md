## 核心用例详细描述（3个）

### 用例 UC-01：发布互助需求

* **参与者**：学生用户（需求方）
* **前置条件**：用户已登录
* **后置条件**：需求成功发布并进入系统

#### 基本流程：

1. 用户进入“发布需求”页面
2. 输入标题、描述、分类、地点、时间、报酬
3. 点击“发布”
4. 系统校验信息合法性
5. 系统保存需求并展示

#### 替代流：

* 4a. 信息不完整 → 提示用户补充
* 4b. 内容违规 → 提交管理员审核或拒绝发布

---

### 用例 UC-02：接单并完成服务

* **参与者**：服务方用户
* **前置条件**：需求存在且未被接单
* **后置条件**：订单完成

#### 基本流程：

1. 用户浏览需求列表
2. 选择一个需求
3. 点击“接单”
4. 需求方确认
5. 双方进入“进行中”状态
6. 服务完成
7. 双方确认完成

#### 替代流：

* 4a. 需求方拒绝 → 接单失败
* 6a. 任一方取消 → 订单终止

---

### 用例 UC-03：评价与信用更新

* **参与者**：需求方 & 服务方
* **前置条件**：订单已完成
* **后置条件**：信用分更新

#### 基本流程：

1. 用户进入订单页面
2. 提交评分（1-5星）+ 评价
3. 系统记录评价
4. 系统更新信用分

#### 替代流：

* 2a. 用户未评价 → 系统提醒


# 与人工对比

### 一、 遗漏异常流

AI生成的用例遗漏了关键且常见的业务异常流

在ai的用例接单并完成服务里，AI 仅考虑了需求方拒绝和任一方取消两种极其宽泛的替代流。

遗漏了并发冲突，即如果两人同时点击接单，或者刚点接单发起人就下架的情况。并且未考虑服务方不能接自己发的单。遗漏了信用分过低或者账户被冻结的情况。

此外，UC-01「发布互助需求」仅在 4a 写了"信息不完整 → 提示用户补充"，但未覆盖：
- **内容风控异常流**：发布辅导需求时命中"代考/代写"等违禁词应被立即拦截并写入风控日志；
- **资金/积分异常流**：积分悬赏任务在发布者积分余额不足时应阻止发布；
- **任务超时异常流**：任务到达"最晚送达时间"未完成时，系统应自动进入"异常中止"并触发仲裁队列（参见 `用户故事.md` US-19）。

UC-03「评价与信用更新」只考虑了"用户未评价→系统提醒"一条替代流，**完全没有恶意差评申诉路径**，这恰是调研访谈 3 中被反复强调的关键诉求（参见 `用户故事.md` US-15）。

### 二、 验收标准是否具体可测试

AI 生成的用例描述只给出了"基本流程 + 替代流"，**整体缺少可被测试用例直接映射的、具体可测量的验收标准**，集中体现在 3 方面：

**1. 字段颗粒度缺失 —— 无法写出表单校验用例**
AI 版 UC-01 中写的是"输入标题、描述、分类、地点、时间、报酬"，但：
- 没写字段是否必填、类型、长度上限；
- 没写"报酬"是积分还是金额、取值范围；
- 没写"时间"是 `DateTime` 还是文本。

对照人工版 US-01 的验收标准（取件点下拉、悬赏积分 ≥ 0 整数、最晚送达时间为 DateTime 选择器），测试用例可以直接编写"空值 / 极值 / 非法类型"三类断言，AI 版则无从下手。

**2. 数量/时间/并发指标缺失 —— 无法写出性能和并发用例**
AI 版 UC-02「接单并完成服务」只说"点击接单→需求方确认→双方进入进行中"，没有：
- 并发抢单的一致性要求（两人同秒抢单必须只有一人成功）；
- 响应时间上限；
- 接单者最大在进行中任务数。

而人工版 US-02 的验收标准明确写了"总点击次数 ≤ 3 次""并发场景下有且只有一人成功""进行中任务数 > 3 时拒绝接单"，**每一条都可以映射到一个自动化测试用例**。

**3. 后置条件模糊 —— 无法写出断言**
AI 版 UC-03 后置条件只写"信用分更新"，但没有：
- 更新的幅度规则（成功 +1？违约 -5？严重违规 -30？）；
- 触发的副作用（信用分 < 80 自动限制每日接单 1 单？信用分 < 60 禁止发布？）。

对照 SRS 的 FR-CRED-01 与人工故事 US-15 / US-16，都明确写出了可验证的阈值与副作用，测试可针对每条阈值构造边界用例。

**举例对比小结：**

| 维度     | AI 生成用例                     | 人工用户故事（US-02 为例）                          |
| ------ | --------------------------- | ------------------------------------------- |
| 输入     | "选择一个需求，点击接单"                | 列表→接单 ≤ 3 次点击，任务 ID 必选                      |
| 并发     | 未提及                         | 两人同秒抢单仅一人成功，另一人提示"手慢了"                      |
| 性能     | 未提及                         | 接单动作响应 ≤ 500 ms（另见 SRS §4.1）                |
| 上限     | 未提及                         | 进行中任务 > 3 时拒绝                               |
| 后置副作用  | "订单完成"                      | 私信会话 2 秒内创建 + 系统通知                          |

### 三、 小结

> **AI 产出是"骨架"，不是"体检报告"。** 它能快速列出用例名称与主流程，但不会主动填充字段级约束、并发/时间/数量阈值、以及领域内的非主流异常分支。这些正是测试团队需要的"验收标准"——必须由熟悉校园场景与本产品信用/积分规则的人工来补齐。

# 人工修订后的核心用例（改进版）

> 依据上述三类问题针对 UC-01、UC-02、UC-03 进行补充。新增内容用 `[human-written]` 标记。

---

## UC-01（改）：发布互助需求

* **参与者**：已认证学生用户（需求方）
* **前置条件**：用户已登录且完成校园实名认证，信用分 ≥ 60
* **后置条件**：需求单生成并进入“任务大厅”公共列表

### 基本流程：

1. 用户进入“发布需求”页面
2. 选择任务类型并填写必填字段（标题、描述、报酬方式、精准标签 ≥ 1 个）
3. 点击“发布”
4. 系统校验字段完整性与内容合规性
5. 若选择积分悬赏，系统冻结对应积分
6. 生成任务单，状态置为“待接单”，广播至任务大厅

### 替代流 `[human-written]`：

* **4a. 字段缺失**：任一必填字段为空，在对应字段旁显示红色警示标，阵止提交。
* **4b. 违禁词拦截**：内容命中“代考”“代写”“替考”等遥词或常见绕过词，立即拦截并写入风控日志，拒绝发布并提示原因。连续 3 次触发违禁词的账号冷静 24 小时禁止发布辅导需求。
* **4c. 积分不足**：选择积分悬赏时余额不足，系统拒绝发布并提示“积分不足，无法发布悬赏任务”。
* **4d. 信用分不足**：用户信用分 < 60，系统拒绝并提示“信用分不足，请先完成申诉或加分任务”。
* **5a. 冻结失败**：积分冻结失败时，任务不得发布成功，向用户提示错误原因。

### 验收标准 `[human-written]`：

1. 表单包含 5 个必填字段，任一缺失则字段旁显示红色警示标，禁止提交。
2. 发布成功后 1 秒内任务卡片出现在任务大厅，状态为“待接单”。
3. 选择积分悬赏时，“我的积分流水”中可见一条“冻结”记录。
4. 命中违禁词拦截的情况下，页面显示拦截提示，任务不入库。

## UC-02（改）：接单并完成服务

* **参与者**：已认证学生用户（接单者）
* **前置条件**：需求已存在且处于“待接单”状态；接单者信用分 ≥ 60；进行中任务数 < 个人配置上限
* **后置条件**：订单状态更新为“进行中”，双方广披客窗口自动创建

### 基本流程：

1. 接单者浏览任务列表（列表页到接单按鈕 ≤ 3 次点击）
2. 查看任务详情
3. 点击“接单”，系统加锁任务状态为“进行中”
4. 接单者完成服务后提交完成凭证
5. 发布者确认完成，触发积分结算

### 替代流 `[human-written]`：

* **3a. 并发抗状**：两人同秒点击“接单”，系统通过乐观锁确保仅一人接单成功，另一人收到“手慢了，已被抢走”提示，不产生重复订单。
* **3b. 自接限制**：系统检测到接单者 ID 与发布者 ID 相同，拒绝接单并提示“不可接取自己发布的任务”。
* **3c. 信用分不足**：接单者信用分 < 60，系统拒绝接单。
* **3d. 上限达到**：进行中任务数已达个人配置上限，系统拒绝并提示“当前进行中任务已达上限”。
* **3e. 任务已下架**：点击接单时任务已被取消，提示“任务不存在或已下架”。
* **5a. 超时未完成**：任务到达最晚送达时间前 10 分钟，系统先向接单者推送提醒；达时后状态自动进入“异常中止”，冻结积分不自动结算。
* **5b. 发布者主动延长**：发布者在超时前可延长最晚送达时间（最多 2 次，每次 ≤ 2 小时），超时判定顺延。

### 验收标准 `[human-written]`：

1. 列表页到接单成功的总点击次数 ≤ 3 次。
2. 并发抟单场景下有且只有一人成功，不产生重复订单。
3. 接单成功后 2 秒内双方会话列表出现以任务标题命名的会话窗口。
4. 超时判定精度 ≤ 5 分钟。

## UC-03（改）：评价与信用更新

* **参与者**：需求方、接单者
* **前置条件**：订单处于“已完成”状态
* **后置条件**：信用分更新并写入日志

### 基本流程：

1. 双方分别进入订单页面提交评分（1–5 星）+ 文字评价
2. 系统记录评价并更新双方信用分（各 +1 分）
3. 系统向双方推送“评价已提交”系统通知

### 替代流 `[human-written]`：

* **2a. 用户未评价**：订单完成 48 小时后未提交评价，系统发送一次温柔提醒；连续 7 天未评价，系统自动关闭评价入口。
* **2b. 恶意差评 → 申诉**：被评价方收到差评后，可在 7 日内提交证据发起申诉（最多 3 次）。申诉期间该差评在公开页面打码显示为“该评价正在申诉中”。申诉通过后自动恢复信用分并删除评价。
* **2c. 议价不得导致差评**：买卖双方在私信中发起穿价并被拒绝，**不得将该行为作为差评理由**；如发现此类恶意差评经核实则 -10 分并删除评价。

### 验收标准 `[human-written]`：

1. 成功完成任务后双方各 +1 信用分，可在“我的信用分趋势”中看到该条变动记录。
2. 负评旁显示申诉入口，点击后可上传≤ 5 张图片与 ≤ 500 字说明。
3. 申诉期间该差评在个人主页打码，无法被搜索到。
4. 信用分 < 80 时，系统自动限制每日接单 1 单；信用分 < 60 时，禁止发布和接单。
